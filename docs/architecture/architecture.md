# Архитектура бэкенда

## 1. Назначение

Этот документ определяет архитектуру бэкенда MVP+ Mini E-commerce.

Бэкенд следует принципам Clean Architecture и разделяет бизнес-правила,
прикладные сценарии использования, инфраструктурные задачи и
HTTP-представление.

Архитектура должна оставаться понятной для проекта, который разрабатывает один
разработчик. Она не должна вводить абстракции или слои без конкретной
необходимости.

Документ описывает целевую архитектуру M1–M14. Детали платежей и событий
вынесены в `payments.md` и `events.md`; утверждённые решения фиксируются в
ADR и `../DECISIONS.md`.

## 2. Структура решения

Бэкенд расположен в `src/Backend/PS.MiniEcommerce/`. Файл решения —
`src/Backend/PS.MiniEcommerce/PS.MiniEcommerce.slnx`; используется формат
`.slnx`.

Бэкенд состоит из четырёх проектов:

```text
src/Backend/PS.MiniEcommerce/
├── PS.MiniEcommerce.slnx
├── PS.MiniEcommerce.Domain/
├── PS.MiniEcommerce.Application/
├── PS.MiniEcommerce.Infrastructure/
└── PS.MiniEcommerce.API/
```

Автоматизированные тесты поддерживаются отдельно:

```text
tests/
├── PS.MiniEcommerce.UnitTests/
└── PS.MiniEcommerce.IntegrationTests/
```

Префикс `PS.` является частью согласованного именования и сохраняется в именах
проектов, пространствах имён и путях (см. `../DECISIONS.md`, раздел 1.1).

### 2.1 PS.MiniEcommerce.Domain

Содержит основную бизнес-модель и бизнес-инварианты.

Обязанности:

- Доменные сущности и объекты-значения, включая `Money`.
- Явная state machine заказа: `Created`, `Paid`, `Shipped`, `Delivered`,
  `Cancelled`, `Returned`.
- Доменные события как обычные неизменяемые `record`/`class` без зависимости от
  MediatR.
- Бизнес-правила, независимые от HTTP, EF Core и инфраструктуры.
- Специфичные для предметной области исключения, включая
  `invalid_order_transition`.

Домен включает:

- `Product` с `Available` и `Reserved` вместо `StockQuantity`;
- `Cart` и `CartItem.IsSelected`;
- `Order` с `RowVersion` и nullable `PaymentId`;
- `OrderItem` со снимками названия и цены и вычисляемым
  `CancelledQuantity`;
- `OrderItemCancellation` как историю полной и частичной отмены;
- `Payment` и `Refund` с денежными значениями `Money`;
- доменные события заказа, платежа и admin-изменений.

Переходы заказа выполняются только явными методами `MarkPaid()`, `Ship()`,
`Deliver()`, `Cancel()` и `Return()`. Публичного setter статуса нет. `Cancel()`
поддерживает полную и частичную отмену; частичная отмена не меняет статус
заказа. Недопустимый переход выбрасывает `DomainException` с кодом
`invalid_order_transition` (ADR-004).

`Money` — неизменяемый value object с `Amount` (`decimal`) и `Currency`
(`USD`). Он обеспечивает округление `MidpointRounding.AwayFromZero` до двух
знаков, неотрицательность, проверку валюты и переполнения `decimal(18,2)`
(ADR-003).

Domain не должен зависеть от Application, Infrastructure, API, MediatR,
EF Core или ASP.NET Core. Он не содержит `DbContext`, HTTP-контроллеров,
SQL-запросов и обработчиков MediatR.

Доменные события описывают уже произошедшие факты. Domain не публикует их
самостоятельно и не ссылается на MediatR; публикация выполняется в Application
после успешного commit по ADR-007.

### 2.2 PS.MiniEcommerce.Application

Содержит сценарии использования и оркестрацию на уровне приложения.

Обязанности:

- Команды и запросы MediatR.
- Обработчики команд и запросов.
- `INotification`-обёртки доменных событий и их handlers.
- `IPaymentProvider` как абстракция платежного провайдера.
- Audit handlers, которые создают `AuditLog` после commit.
- Admin-команды для деактивации товара, изменения запаса, ship, deliver и
  return.
- DTO запросов и ответов приложения.
- Валидаторы FluentValidation.
- Поведения конвейера MediatR.
- Абстракция текущего пользователя `ICurrentUser`.
- Узкие абстракции транзакций, необходимые прикладным сценариям.

Application оркестрирует бизнес-операции, но не содержит EF Core, SQL Server,
HTTP-контроллеров или реализации платёжного провайдера.

Ключевые сценарии:

- просмотр каталога и корзины;
- изменение корзины и выбор позиций;
- частичный checkout только выбранных позиций;
- получение заказов и сведений о заказе;
- полная и частичная отмена;
- подтверждение платежа;
- admin refund как Development-инструмент;
- admin deactivate, stock, ship, deliver и return;
- обработка доменных событий для аудита.

Application зависит от Domain, но не должен зависеть от Infrastructure или API.

MediatR используется для диспетчеризации команд и запросов, а также для
`INotification`-обёрток доменных событий. Он не используется как универсальная
шина для цепочек событий или как замена бизнес-транзакциям.

### 2.3 PS.MiniEcommerce.Infrastructure

Реализует сохранение данных и поведение, специфичное для инфраструктуры.

Обязанности:

- EF Core `DbContext`.
- Конфигурации сущностей и сопоставления с базой данных.
- EF Core value converter `Money` ↔ `decimal(18,2)`; `Currency` не
  персистится, потому что в MVP+ всегда `USD`.
- Миграции EF Core.
- Атомарные резервы и изменения `Available`/`Reserved` на SQL Server.
- Блокировки строк, условные обновления и optimistic concurrency по
  `rowversion`.
- Mock-реализация `IPaymentProvider`.
- Сохранение `PaymentAttempt` и `CheckoutAttempt`.
- Сохранение `AuditLog` и защита append-only.
- Сбор доменных событий и передача их в диспетчер после commit.
- Инициализация базы данных и идемпотентный seed пользователей `alice`, `bob` и
  `admin`.
- Обработка транзакций, специфичная для инфраструктуры.

Infrastructure зависит от Application и Domain.

Требования корректности, специфичные для SQL Server, должны реализовываться
явно. Нельзя предполагать, что одного EF Core LINQ достаточно для генерации
требуемых подсказок блокировки или атомарных условных обновлений.

Infrastructure не должна дублировать прикладные бизнес-процессы. Она реализует
операции сохранения данных и механизмы базы данных, необходимые для соблюдения
согласованных инвариантов.

`AuditLog` append-only защищён триггером `TR_AuditLog_NoUpdateDelete`
(`INSTEAD OF UPDATE, DELETE`), который бросает ошибку. Приложение не выполняет
`UPDATE`/`DELETE` для аудита; триггер является дополнительной защитой
(ADR-010).

Публикация событий выполняется после успешного commit. Infrastructure собирает
события в рамках операции и передаёт их в Application-диспетчер; `INotification`
обёртки и handlers принадлежат Application. Outbox не используется (ADR-007).

### 2.4 PS.MiniEcommerce.API

Проект API — это слой HTTP-представления.

Обязанности:

- Контроллеры ASP.NET Core.
- Контракты HTTP-запросов и ответов.
- Конфигурация аутентификации и авторизации.
- Тестовая аутентификация `X-Test-User` только для Development.
- Роль `admin` и admin endpoints только для Development.
- Payment endpoints для confirm и admin refund.
- Сопоставление кодов состояния HTTP.
- Ответы об ошибках в формате `ProblemDetails`.
- Композиция внедрения зависимостей.
- Промежуточное ПО и конфигурация запуска приложения.

Контроллеры должны оставаться тонкими.

Контроллер должен:

1. Принять HTTP-запрос.
2. Полагаться на привязку и валидацию запроса на уровне фреймворка там, где это
   уместно.
3. Отправить прикладную команду или запрос через MediatR.
4. Сопоставить результат приложения с HTTP-ответом.

Контроллеры не должны:

- Обращаться к `DbContext` напрямую.
- Выполнять SQL-запросы.
- Реализовывать транзакции checkout, confirm, cancel или return.
- Изменять запас или платёж напрямую.
- Содержать бизнес-процессы корзины, заказа или платежа.

API зависит от Application и Infrastructure для композиции и регистрации во
время выполнения. Он не должен становиться местом для доменных бизнес-правил.

Платёжные endpoints:

- `POST /api/payments/{paymentId}/confirm` — владелец платежа,
  `Idempotency-Key`;
- `POST /api/payments/{paymentId}/refund` — только admin в Development,
  `Idempotency-Key`.

Admin endpoints:

- `POST /api/admin/products/{productId}/deactivate`;
- `POST /api/admin/products/{productId}/stock`;
- `POST /api/admin/orders/{orderId}/ship`;
- `POST /api/admin/orders/{orderId}/deliver`;
- `POST /api/admin/orders/{orderId}/return`.

Полные контракты, коды ответов и правила `If-Match`/`Idempotency-Key`
определены в `api.md`.

## 3. Направление зависимостей

Основные зависимости:

```text
PS.MiniEcommerce.Domain
        ↑
PS.MiniEcommerce.Application
        ↑
PS.MiniEcommerce.Infrastructure

PS.MiniEcommerce.API
        ├── PS.MiniEcommerce.Application
        └── PS.MiniEcommerce.Infrastructure
```

Более точно:

- Domain не имеет проектных зависимостей от других проектов приложения.
- Domain не зависит от MediatR, EF Core и ASP.NET Core.
- Application ссылается на Domain.
- Infrastructure ссылается на Application и Domain.
- API ссылается на Application и Infrastructure.
- Модульные тесты могут ссылаться на проекты, поведение которых они проверяют.
- Интеграционные тесты проверяют API и инфраструктуру в связке с SQL Server.

Интерфейсы платежей и событий принадлежат Application. В частности,
`IPaymentProvider` определяется в Application, а его mock-реализация — в
Infrastructure. `INotification`-обёртки и handlers событий также находятся в
Application; Domain содержит только plain-события.

Направление зависимостей должно сохранять независимость бизнес-правил от базы
данных и HTTP-фреймворка.

Не добавляйте проектные ссылки, создающие циклические зависимости. Проект
`PS.MiniEcommerce.Common` не вводится; общие типы принадлежат слою, который ими
владеет.

## 4. Поток обработки запроса в приложении

Типичный запрос проходит следующий путь:

```text
HTTP Request
    ↓
ASP.NET Core Controller
    ↓
MediatR Command or Query
    ↓
Validation Pipeline Behavior
    ↓
Application Handler
    ↓
Application Interface
    ↓
Infrastructure Implementation
    ↓
SQL Server
    ↓
Commit
    ↓
Domain event dispatch (Application/MediatR)
    ↓
Audit handler (separate transaction)
```

Результат возвращается через обработчик и контроллер и преобразуется в
HTTP-ответ.

Точный порядок конвейера и сопоставление исключений должны быть настроены
согласованно с контрактом API.

### 4.1 Checkout

1. Проверяются `Idempotency-Key` и `If-Match` корзины.
2. Вычисляется fingerprint checkout с учётом `If-Match`.
3. Проверяется или резервируется `CheckoutAttempt`.
4. В одной транзакции читаются только выбранные позиции корзины.
5. Выбранные позиции резервируются: `Available -= quantity`,
   `Reserved += quantity`.
6. Создаются `Order` в `Created`, снимки `OrderItem` и `Payment` в `Pending`;
   возвращается `paymentId`.
7. Очищаются только выбранные позиции корзины, изменяется `rowversion`
   корзины.
8. `CheckoutAttempt` завершается, транзакция фиксируется.
9. После commit публикуется `OrderPlaced`.

Невыбранные позиции остаются в корзине без резерва. Если выбранных позиций нет,
возвращается `cart_empty`. Если резерв не удался, откатываются заказ, платёж,
резервы и очистка корзины.

### 4.2 Confirm payment

1. Проверяются владелец платежа и `Idempotency-Key`.
2. В одной транзакции `Payment` переходит `Pending → Confirmed`.
3. `Reserved` уменьшается на количества заказа (consumed).
4. `Order` переходит `Created → Paid` через `MarkPaid()`.
5. Завершается `PaymentAttempt`, транзакция фиксируется.
6. После commit публикуются `PaymentConfirmed` и `OrderPaid`.

`Failed` допускает retry `Failed → Pending → Confirmed` для того же платежа;
`Refunded` терминален.

### 4.3 Cancel: full и partial

1. Проверяются владелец заказа и `If-Match` по `Order.RowVersion`.
2. В одной транзакции блокируется строка заказа.
3. Для каждой отменяемой позиции создаётся `OrderItemCancellation`;
   `OrderItem.Quantity` не уменьшается.
4. Запас корректируется: для `Created` — `Reserved → Available`; для `Paid` —
   `Available += quantity` и refund.
5. При полной отмене заказ переходит в `Cancelled`; при частичной статус не
   меняется.
6. Транзакция фиксируется.
7. После commit публикуется `OrderCancelled` (с признаком полной/частичной
   отмены) и, если был refund, `PaymentRefunded`.

Отмена `Shipped`, `Delivered` или `Returned` невозможна. Повторная отмена
`Cancelled` возвращает `order_already_cancelled`.

### 4.4 Admin ship, deliver, return

- `ship`: `Paid → Shipped`; публикуется `OrderShipped`.
- `deliver`: `Shipped → Delivered`; публикуется `OrderDelivered`.
- `return`: `Delivered → Returned`; возвращается весь заказ, выполняется refund,
  `Available += quantity`; refund, запас и статус фиксируются в одной
  транзакции; публикуются `OrderReturned` и `PaymentRefunded`.

Admin stock и deactivate выполняются отдельными командами; stock использует
optimistic concurrency по `Product.RowVersion`, не изменяет `Reserved` и
публикует `StockAdjusted`; deactivate публикует `ProductDeactivated`.

## 5. Команды и запросы

Используйте разделение команд и запросов в проекте Application.

- **Команды** представляют операции, изменяющие состояние приложения.
- **Запросы** извлекают данные, не изменяя бизнес-состояние.

Команды:

- `AddCartItemCommand`
- `UpdateCartItemQuantityCommand`
- `RemoveCartItemCommand`
- `UpdateCartSelectionCommand`
- `CheckoutCommand`
- `CancelOrderCommand`
- `PartialCancelCommand`
- `ConfirmPaymentCommand`
- `RefundPaymentCommand`
- `AdminShipCommand`
- `AdminDeliverCommand`
- `AdminReturnCommand`
- `AdminStockCommand`
- `AdminDeactivateCommand`

Запросы:

- `GetProductsQuery`
- `GetProductByIdQuery`
- `GetCartQuery`
- `GetOrdersQuery`
- `GetOrderByIdQuery`

Имена приведены для иллюстрации. Окончательные имена и контракты могут быть
скорректированы в соответствии с `api.md`, но разделение команд и запросов
сохраняется.

`CancelOrderCommand` и `PartialCancelCommand` используют один доменный сценарий
отмены и различаются наличием отменяемых позиций. Оба защищены `If-Match` по
заказу; отдельный `Idempotency-Key` для отмены не используется.

`ConfirmPaymentCommand` и `RefundPaymentCommand` используют `PaymentAttempt` и
`Idempotency-Key`. Refund, выполняемый внутри cancel/return, использует тот же
refund-сервис, но не HTTP endpoint.

Не вводите отдельные базы данных для чтения и записи. CQRS здесь — это шаблон
организации прикладного кода, а не распределённая архитектура.

## 7. Валидация

Используйте FluentValidation для валидации прикладных запросов.

Централизованное поведение конвейера MediatR должно выполнять применимые
валидаторы до обработчика.

Валидация должна различать:

- Ограничения формы запроса и входных данных.
- Валидацию бизнес-правил.
- Условия конкурентности и целостности, обеспечиваемые базой данных.

Примеры валидации входных данных:

- `Money.Amount` — неотрицательный `decimal`; валюта только `USD`; значение
  помещается в `decimal(18,2)`.
- Количество в корзине, заказе, отмене и admin stock — положительное или
  неотрицательное целое в соответствии с операцией.
- `OrderItemCancellation.Quantity > 0` и не превышает оставшееся количество
  позиции.
- `Refund.Amount > 0` и не превышает `Payment.Amount - Payment.RefundedAmount`.
- `CartItem.IsSelected` — логическое значение; `productId` выбора существует в
  корзине.
- `Idempotency-Key` соответствует формату из `../DECISIONS.md`.
- Обязательный `If-Match` присутствует и содержит один конкретный тег.
- Параметры пагинации находятся в документированных пределах.

Примеры проверок бизнес-правил:

- Товар активен.
- В корзине есть выбранные позиции при checkout.
- Запрошенное количество допустимо при текущем запасе.
- Заказ может быть отменён, оплачен, отгружен, доставлен или возвращён.
- Платёж находится в статусе, допускающем confirm или refund.
- Частичная отмена не превышает оставшееся количество.

Проверки, зависящие от изменяемого состояния базы данных, должны выполняться
безопасно в рамках соответствующей транзакции и стратегии конкурентного
доступа. Одно правило FluentValidation не может гарантировать согласованность
запаса или статуса заказа.

Переходы состояния заказа проверяются в Domain, а не только в валидаторе.
Итоговое сопоставление ошибок валидации и бизнес-ошибок с кодами состояния HTTP
должно соответствовать `api.md`, §4.1.

## 8. Текущий пользователь и принадлежность

Прикладные сценарии использования должны получать текущего пользователя через
прикладную абстракцию `ICurrentUser`.

Контекст аутентификации API предоставляет аутентифицированную идентичность.
Операции сохранения данных в Infrastructure и обработчики приложения не должны
доверять идентификатору пользователя, переданному в теле запроса, при
определении принадлежности.

Требования:

- Операции с корзиной применяются только к корзине текущего пользователя.
- История заказов содержит только заказы текущего пользователя.
- Сведения о заказе, отмена и confirm платежа проверяют принадлежность.
- Платёж принадлежит пользователю через заказ; admin refund доступен только
  admin.
- Запросы к чужому заказу или платежу следуют утверждённому поведению при
  отсутствии ресурса (`404`).
- Эндпоинты каталога и `GET /health` являются публичными.
- Все остальные эндпоинты требуют аутентификации и отклоняют анонимные запросы.
- `X-Test-User` доступен только в Development; неизвестное значение не
  аутентифицирует запрос.
- `X-Test-User: admin` — предварительно созданный пользователь с ролью admin.
  Не-admin запрос к admin endpoint возвращает `403 forbidden`.
- Admin endpoints не регистрируются в Production и возвращают `404`.

Механизм `X-Test-User` является Development-заглушкой, а не production
аутентификацией. Полное обоснование — см. `../../RATIONALE.md`; см. также
`../DECISIONS.md`, §13.

Абстракция текущего пользователя принадлежит Application. Её реализация во время
выполнения и конфигурация аутентификации подключаются через композицию API.

## 9. Сохранение данных и транзакции

EF Core — технология сохранения данных по умолчанию. Операции, специфичные для
SQL Server, могут использовать явный SQL, когда это требуется для корректности.

### 9.1 Конкурентный доступ к корзине

Изменения корзины и checkout должны следовать утверждённой стратегии
блокировки, описанной в `../adr/ADR-001-cart-concurrency.md`.

Реализация должна:

- Захватывать требуемую блокировку корзины в рамках транзакции и удерживать её
  до завершения транзакции.
- Проверять переданное клиентом значение `If-Match` на соответствие текущему
  `rowversion` и предоставлять `rowversion` как `ETag` корзины.
- Не предполагать, что обычные запросы EF Core автоматически захватывают
  `UPDLOCK`.
- Обновлять строку корзины при каждом изменении содержимого или выбора, в том
  числе во время checkout, чтобы устаревший запрос не мог восстановить
  устаревшее содержимое корзины.

### 9.2 Согласованность запаса

Checkout резервирует только выбранные позиции:

```sql
UPDATE Products
SET Available = Available - @Quantity,
    Reserved  = Reserved  + @Quantity
WHERE Id = @ProductId
  AND Available >= @Quantity
```

Payment confirm уменьшает `Reserved` (consume), не возвращая количество в
`Available`:

```sql
UPDATE Products
SET Reserved = Reserved - @Quantity
WHERE Id = @ProductId
  AND Reserved >= @Quantity
```

Отмена до оплаты возвращает `Reserved → Available`; отмена после оплаты и
возврат после доставки увеличивают только `Available`. Admin stock устанавливает
абсолютное `Available` и не изменяет `Reserved`.

Все изменения запаса должны быть атомарными, проверять количество затронутых
строк и выполняться в одной транзакции с соответствующим изменением заказа,
платежа, отмены или возврата. Строки товаров обрабатываются в стабильном
порядке по `ProductId` для снижения риска взаимоблокировок.

Снимки названия товара и цены за единицу для позиций заказа читаются, пока
строки товаров ещё заблокированы этими обновлениями.

### 9.3 Владение транзакцией

Каждый сценарий использования должен иметь чётко определённую границу
транзакции.

Оркестрация checkout, confirm, cancel, return и admin stock принадлежит слою
Application: обработчик определяет порядок бизнес-проверок и получения
результатов. Сама транзакция открывается, фиксируется и откатывается через
узкий интерфейс, специфичный для сценария, который определён в Application и
реализован в Infrastructure.

Такая организация должна удовлетворять следующим требованиям:

- Слой Application остаётся независимым от EF Core.
- Блокировки и поведение транзакций, специфичные для инфраструктуры, остаются
  явными.
- Сценарий использования не может случайно зафиксировать только часть требуемой
  бизнес-операции.
- Границы транзакций покрываются интеграционными тестами с SQL Server.

Не добавляйте универсальную абстракцию Unit of Work или универсальный репозиторий
только для обёртки `SaveChangesAsync`.

### 9.4 Границы транзакций

- **Checkout:** заказ, `Payment` в `Pending`, снимки позиций, резерв выбранных
  товаров, очистка выбранных позиций, изменение `rowversion` корзины и
  завершение `CheckoutAttempt` — одна транзакция.
- **Confirm:** `Payment.Pending → Confirmed`, consume `Reserved`,
  `Order.Created → Paid` и завершение `PaymentAttempt` — одна транзакция.
- **Cancel:** `OrderItemCancellation`, возврат запаса, refund для `Paid`,
  изменение `Order.RowVersion` и, при полной отмене, `Order → Cancelled` — одна
  транзакция.
- **Partial cancel:** то же, что cancel, но статус заказа не меняется.
- **Return:** refund, `Available += quantity`, `Order → Returned` — одна
  транзакция.
- **Admin stock:** атомарное optimistic-обновление `Available` с ограниченным
  числом повторов; `Reserved` не изменяется.
- **Admin deactivate:** атомарное изменение `IsActive`; снимки заказов не
  меняются.

Транзакции выполняются на уровне изоляции, определённом в `../DECISIONS.md`.
В MVP+ взаимоблокировки не повторяются внутри процесса; запрос завершается
неудачно, а клиент повторяет его с тем же ключом идемпотентности или повторно
получает корзину/заказ.

### 9.5 Идемпотентность

Checkout использует `CheckoutAttempt` по ADR-002. Confirm и refund используют
`PaymentAttempt` по ADR-008. Обе записи уникальны по
`(UserId, IdempotencyKey)` и используют lease и bounded wait; фоновый cleanup не
вводится. Восстановление выполняется по требованию.

Завершённая попытка воспроизводит сохранённый статус и тело. Неожиданные
инфраструктурные ошибки не сохраняются как окончательные бизнес-результаты.
`Payment.Status = Failed` допускает retry для confirm; `Refunded` терминален.

### 9.6 События и аудит

События собираются в рамках операции и публикуются только после успешного
commit, а не после `SaveChanges` и не до commit. Если commit не состоялся,
события не публикуются. Если commit состоялся, но handler упал, бизнес-операция
остаётся закоммиченной.

Handlers выполняются после commit. Audit handler пишет `AuditLog` в отдельной
транзакции, at-most-once. Ошибка аудита не откатывает бизнес-операцию.
Автоматический retry и outbox не используются. Подробнее — `events.md` и
ADR-010.

`AuditLog` append-only; триггер `TR_AuditLog_NoUpdateDelete` запрещает
`UPDATE`/`DELETE`.

## 10. Обработка ошибок

Используйте согласованную модель ошибок во всём приложении.

Ожидаемые сбои должны представляться так, чтобы API мог вернуть согласованный
ответ `ProblemDetails` со стабильным `code`.

Примеры включают:

- Недопустимые значения запроса, `Money`, количества, `amount` или `reason`.
- Отсутствующие товары, заказы или платежи.
- Недостаточный запас.
- Устаревшие обновления корзины или заказа.
- Недопустимый переход статуса заказа.
- Повторное использование ключа идемпотентности с другим содержимым.
- Повторная отмена уже отменённого заказа.
- Повторный confirm уже подтверждённого платежа.
- Refund после полного возврата или на сумму больше остатка.
- Конкурентное изменение admin stock.
- Недостаток прав на admin endpoint.

Новые коды включают `order_version_conflict`, `invalid_order_transition`,
`order_already_cancelled`, `payment_not_found`, `payment_already_confirmed`,
`payment_failed`, `refund_not_allowed`, `admin_stock_conflict`, `forbidden`,
`idempotency_key_reused` и `idempotency_in_progress`. Полный перечень и
HTTP-статусы определены в `api.md`, §4.1; здесь они не дублируются.

Неожиданные исключения должны регистрироваться в журнале должным образом и
сопоставляться с общей ошибкой сервера без раскрытия внутренних деталей
реализации.

Не возвращайте клиентам сообщения исключений базы данных или трассировки стека.

## 11. Внедрение зависимостей и конфигурация

Композиция API отвечает за регистрацию зависимостей приложения во время
выполнения.

- Регистрировать обработчики и поведения конвейера MediatR.
- Регистрировать валидаторы FluentValidation.
- Регистрировать `IPaymentProvider` с mock-реализацией из Infrastructure.
- Регистрировать event handlers и audit handlers.
- Регистрировать `ICurrentUser` и реализации прикладных абстракций из
  Infrastructure.
- Регистрировать транзакционные исполнители checkout, payment, cancel и return.
- Настраивать EF Core с выбранным подключением к SQL Server.
- Регистрировать службы аутентификации и авторизации.
- Регистрировать `X-Test-User` и admin endpoints только в Development.
- Регистрировать проверку работоспособности, используемую `GET /health`.

Строки подключения и секреты должны передаваться через соответствующие механизмы
конфигурации и не должны попадать в систему контроля версий.

Не вводите отдельный фреймворк внедрения зависимостей.

## 12. Границы тестирования

### Модульные тесты

Используйте модульные тесты для проверки изолированного поведения приложения и
предметной области, включая:

- Валидацию входных данных.
- Доменные инварианты `Money`, запаса, отмены и платежа.
- Переходы статусов заказа и запрещённые переходы.
- Расчёты итоговой суммы заказа и сумм refund.
- Выбор позиций корзины и частичный checkout.
- Инвариант `SUM(OrderItemCancellation.Quantity) <= OrderItem.Quantity`.
- Идемпотентность confirm/refund и fingerprint.
- Публикацию событий после commit и отсутствие публикации при rollback.
- Поведение handlers, не требующее реальной конкурентности базы данных.

Используйте NSubstitute, когда полезен тестовый двойник, в том числе для
`IPaymentProvider`. Избегайте имитации поставщиков запросов EF Core или
использования имитаций для доказательства поведения SQL Server.

### Интеграционные тесты

Используйте интеграционные тесты с SQL Server для проверки:

- Сопоставлений и миграций EF Core, включая `Money` ↔ `decimal(18,2)`.
- Ограничений базы данных и триггера `TR_AuditLog_NoUpdateDelete`.
- Транзакций и отката.
- Блокировки корзины, валидации `If-Match` и обработки устаревших обновлений.
- Создания корзины при первом обращении в условиях одновременных первых
  запросов.
- Checkout только выбранных позиций и сохранения невыбранных.
- Атомарных резервов, consume, отмены и возврата запаса.
- Подтверждения платежа и перехода заказа в `Paid`.
- Полной и частичной отмены, refund и `OrderItemCancellation`.
- Admin stock, ship, deliver и return.
- Идемпотентности checkout, confirm и refund, включая bounded wait и
  восстановление по требованию.
- Одновременной отмены и одновременного confirm.
- Публикации событий после commit, потери события при сбое handler'а и
  at-most-once аудита.
- Изоляции пользователей через API.
- Отсутствия admin endpoints в Production.

База данных в памяти не заменяет SQL Server, когда тест зависит от блокировок
SQL Server, rowversion, изоляции или поведения затронутых строк.

## 13. Ограничения текущего этапа

MVP+ (M1–M8, M12, M13) реализован; код соответствует MVP+. M9, M10, M11, M14 —
вне объёма. См. `../../RATIONALE.md`, `../ROADMAP.md`. MVP+ не содержит
production-hardening:

- Платёжный провайдер — mock; Stripe, реальные вебхуки и reconciliation не
  поддерживаются.
- `X-Test-User` и admin endpoints доступны только в Development; реальной
  JWT/OAuth-аутентификации и управления ролями нет.
- События и аудит работают at-most-once; outbox, брокеры сообщений и
  гарантированная доставка отсутствуют.
- Нет TTL резервов, фонового cleanup и автоматического истечения.
- Нет частичного возврата после доставки и частичных платежей.
- Нет мультивалютности; все суммы — USD.
- Нет admin UI, API чтения аудита и реальных уведомлений.
- Нет фоновой обработки, кроме стандартного жизненного цикла приложения.
- При сбое audit handler запись аудита может потеряться; бизнес-операция не
  откатывается.
- Взаимоблокировки не повторяются внутри процесса; клиент повторяет запрос.

Эти ограничения являются осознанными для MVP+ и не должны обходиться
альтернативными реализациями без утверждённого решения.

## 14. Будущее развитие

Вне MVP+ и только после отдельного утверждения:

- outbox и гарантированная доставка событий;
- TTL резервов и фоновый cleanup;
- reconciliation платежей;
- реальная JWT/OAuth-аутентификация и управление ролями;
- Stripe или другой реальный платёжный провайдер;
- уведомления и admin UI;
- частичный возврат после доставки и другие расширения жизненного цикла.

Будущие изменения не должны ломать текущие границы транзакций, идемпотентность и
append-only аудит без соответствующего ADR.
