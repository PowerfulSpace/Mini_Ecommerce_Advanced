# Контракт API

## 1. Назначение

Этот документ определяет контракт HTTP API для MVP+ Mini E-commerce.

API реализуется с помощью контроллеров ASP.NET Core. Сценарии использования
приложения предоставляются через команды и запросы MediatR. Бизнес-правила
остаются в слоях Application и Domain; контроллеры обрабатывают вопросы HTTP и
сопоставляют результаты приложения с HTTP-ответами.

API спроектирован так, чтобы бизнес-результаты, конфликты конкурентности и
поведение при повторных попытках были явными.

## 2. Соглашения

- Базовый путь: `/api`, кроме `GET /health`.
- Тип содержимого: `application/json`.
- Денежные значения используют USD и передаются как JSON-числа (`decimal`), без
  объекта `{ "amount", "currency" }`.
- Метки времени возвращаются в UTC в формате ISO 8601.
- Идентификаторы ресурсов непрозрачны для клиентов.
- DTO запросов и ответов отделены от сущностей домена.
- Ошибки используют `ProblemDetails` с полем `instance` (путь запроса) и
  стабильным расширением `code`, зависящим от приложения, кроме успешного
  ответа `GET /health`.
- Предоставленные клиентом идентификаторы пользователей никогда не используются
  для определения принадлежности ресурса.
- Числовые параметры, такие как размеры страниц, длительности ожидания и lease,
  определены один раз в `../DECISIONS.md`, раздел 10, и ссылаются здесь вместо
  повторения.

### 2.1 Аутентификация

Конечные точки, требующие аутентификации, отклоняют анонимные запросы с
`401 Unauthorized` и кодом `unauthenticated`.

| Конечная точка | Аутентификация |
|---|---|
| `GET /health` | Не требуется |
| `GET /api/products` | Не требуется |
| `GET /api/products/{productId}` | Не требуется |
| Admin endpoints | Только роль admin |
| Все остальные конечные точки | Требуется |

В ходе разработки аутентифицированные запросы используют заголовок
`X-Test-User`:

- `X-Test-User: alice`
- `X-Test-User: bob`
- `X-Test-User: admin`

`admin` — предварительно созданный пользователь с ролью admin. Запрос от
`alice` или `bob` к admin endpoint возвращает `403 Forbidden` с кодом
`forbidden`. Неизвестные значения `X-Test-User` не аутентифицируют запрос.

Механизм `X-Test-User` и admin endpoints предназначены только для среды
разработки и не должны регистрироваться в среде Production. В Production
admin endpoints недоступны и возвращают `404 Not Found`. API определяет
текущего пользователя через контекст аутентификации и предоставляет его
приложению через `ICurrentUser`.

### 2.2 Версия корзины и заказа через ETag и If-Match

Каждое представление корзины возвращается с заголовком ответа `ETag`. Значение —
это заключённый в кавычки строгий тег сущности, содержащий Base64-кодирование
8-байтового `rowversion` SQL Server строки корзины, например:

```http
ETag: "bmV3dmVyc2lvbg=="
```

Заказ также имеет версию через `Order.RowVersion`. `GET /api/orders/{orderId}`
возвращает `ETag` заказа в том же формате. Ответы, изменяющие заказ, возвращают
новый `ETag`.

Клиенты не должны разбирать или конструировать значение.

`If-Match` требуется для следующих операций:

- `POST /api/cart/items`
- `PUT /api/cart/items/{productId}`
- `DELETE /api/cart/items/{productId}`
- `PUT /api/cart/selection`
- `POST /api/orders`
- `POST /api/orders/{orderId}/cancel`

Правила:

- Отсутствующий обязательный `If-Match` возвращает `428 Precondition Required` с
  кодом `precondition_required`.
- Принимается только один конкретный тег сущности. `If-Match: *` не
  поддерживается и отклоняется как недопустимый запрос с кодом
  `validation_error`.
- Устаревшее значение корзины возвращает `412 Precondition Failed` с кодом
  `cart_version_conflict`. Устаревшее значение заказа возвращает
  `412 Precondition Failed` с кодом `order_version_conflict`.
- Операция с устаревшим `If-Match` не применяется и не повторяется
  автоматически.
- Каждое успешное изменение корзины возвращает обновлённую корзину с новым
  `ETag`.
- Успешное оформление заказа изменяет строку корзины, поэтому ранее выданный
  `ETag` корзины становится недействительным.
- `POST /api/orders/{orderId}/cancel` требует `If-Match` с текущим
  `Order.RowVersion`; отдельный `Idempotency-Key` для отмены не используется.

Версия — это дополнительная проверка устаревшего состояния. Она не заменяет
транзакцию базы данных и стратегию блокировки строки корзины или заказа,
определённые в `../adr/ADR-001-cart-concurrency.md` и
`../adr/ADR-006-partial-checkout-and-cancellation.md`.

### 2.3 Пагинация

`GET /api/products` и `GET /api/orders` принимают одни и те же параметры
запроса:

| Параметр | Значение по умолчанию | Максимум | Правила |
|---|---|---|---|
| `page` | см. `../DECISIONS.md`, раздел 10 | — | Целое число, `>= 1` |
| `pageSize` | см. `../DECISIONS.md`, раздел 10 | см. `../DECISIONS.md`, раздел 10 | Целое число, в пределах задокументированных границ |

Значения вне диапазона или нецелые значения возвращают `400 Bad Request` с
кодом `validation_error`. Страница за последней доступной страницей возвращает
пустой массив `items`.

Пагинированные ответы используют один и тот же конверт:

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "totalCount": 0
}
```

### 2.4 Версия заказа через If-Match

`POST /api/orders/{orderId}/cancel` требует `If-Match` с текущим значением
`Order.RowVersion`. `If-Match` передаётся только в заголовке; тело отмены
содержит только необязательный список отменяемых позиций.

- Отсутствующий `If-Match` возвращает `428 Precondition Required` с кодом
  `precondition_required`.
- Устаревший `If-Match` возвращает `412 Precondition Failed` с кодом
  `order_version_conflict`.
- `If-Match: *` отклоняется как недопустимый запрос с кодом `validation_error`.
- Успешная полная или частичная отмена изменяет `Order.RowVersion` и возвращает
  новый `ETag`.

### 2.5 Идемпотентность платежей

`POST /api/payments/{paymentId}/confirm` и
`POST /api/payments/{paymentId}/refund` требуют заголовок `Idempotency-Key`.
Для них не используется `If-Match`: конкурентность платежа защищается
идемпотентностью и транзакцией. Правила идемпотентности платежей определены в
`../adr/ADR-008-payments-and-idempotency.md` и разделе 6.2.

## 3. Конечные точки

### 3.1 Проверка работоспособности

#### `GET /health`

Сообщает, может ли приложение получить доступ к базе данных. Конечная точка
является публичной и не требует аутентификации.

Ответы:

- `200 OK` — база данных доступна.

```json
{
  "status": "Healthy"
}
```

- `503 Service Unavailable` — база данных недоступна. Тело использует
  стандартный формат `ProblemDetails` с `instance = /health` и кодом
  `health_unavailable`.

Это единственная конечная точка, успешное тело которой не является частью
процесса покупки. Она не раскрывает конфигурацию, строки подключения или
сведения об исключениях.

### 3.2 Каталог

Конечные точки каталога являются публичными.

#### `GET /api/products`

Возвращает активные товары для запрошенной страницы.

Пример ответа:

```json
{
  "items": [
    {
      "id": "product-id",
      "name": "Example Product",
      "description": "Product description",
      "price": 19.99,
      "available": 10
    }
  ],
  "page": 1,
  "pageSize": 20,
  "totalCount": 1
}
```

Правила:

- Возвращаются только активные товары.
- Неактивные товары не включаются в каталог.
- `price` — денежное значение `decimal`; `available` — доступный запас.
- `reserved` не раскрывается в публичном API.
- Результаты упорядочены по названию товара для стабильной пагинации.
- В MVP+ публичные конечные точки записи каталога не предоставляются.

#### `GET /api/products/{productId}`

Возвращает один активный товар.

Ответы:

- `200 OK` — товар найден и активен. Тело — это один объект товара без конверта
  пагинации; поля совпадают с элементом `GET /api/products`.
- `404 Not Found` — товар не существует или неактивен, с кодом
  `product_not_found`.

### 3.3 Корзина

У каждого пользователя не более одной корзины. Корзина создаётся при первом
обращении во время `GET /api/cart`, когда у пользователя её нет. Изменения
корзины и оформление заказа никогда не создают корзину.

Пустая корзина остаётся доступной после оформления заказа; оформление заказа
удаляет только выбранные позиции, но не удаляет саму корзину.

#### `GET /api/cart`

Возвращает корзину текущего пользователя, создавая её, когда она не существует.

Пример ответа:

```json
{
  "items": [
    {
      "productId": "product-id",
      "productName": "Example Product",
      "unitPrice": 19.99,
      "quantity": 2,
      "lineTotal": 39.98,
      "isSelected": true,
      "isAvailable": true
    }
  ],
  "totalAmount": 39.98,
  "selectedTotalAmount": 39.98
}
```

Правила:

- Корзина принадлежит аутентифицированному пользователю и возвращается с
  заголовком `ETag`, в том числе когда корзина пуста.
- Только что созданная корзина пуста и имеет новый `ETag`.
- Повторные запросы возвращают ту же корзину.
- Одновременные первые запросы для одного пользователя безопасны: уникальное
  ограничение базы данных на владельца корзины определяет, какая строка
  побеждает, а проигравший запрос повторно читает и возвращает выигравшую
  корзину.
- `unitPrice` и итоговые суммы используют текущую цену каталога.
- `isSelected` показывает, участвует ли позиция в checkout.
- `totalAmount` — стоимость всей корзины; `selectedTotalAmount` — стоимость
  только выбранных позиций.
- Неактивные товары могут оставаться в корзине и помечаются как недоступные.
- Недоступный товар нельзя добавить, обновить его количество или оформить его в
  заказе. Его можно удалить.

#### `POST /api/cart/items`

Добавляет товар в корзину.

Требуется `If-Match`.

Запрос:

```json
{
  "productId": "product-id",
  "quantity": 1
}
```

Правила:

- `quantity` должно быть положительным целым числом.
- Добавление товара, уже находящегося в корзине, увеличивает его существующее
  количество и не меняет `isSelected`.
- Новая позиция создаётся с `isSelected = true`.
- Полученное количество не должно превышать доступный запас.
- Товар должен существовать и быть активным.
- Переданное значение `If-Match` должно соответствовать текущей версии корзины.
- Если проверки валидации или конкурентности завершаются неудачно, операция не
  должна частично изменять корзину.

Ответы:

- `200 OK` — обновлённая корзина и новый `ETag`.
- `400 Bad Request` — недопустимая полезная нагрузка, с кодом `validation_error`.
- `404 Not Found` — у пользователя ещё нет корзины, с кодом `cart_not_found`, или
  товар не существует, с кодом `product_not_found`.
- `409 Conflict` — недостаточный запас или неактивный товар.
- `412 Precondition Failed` — устаревший `If-Match`, с кодом
  `cart_version_conflict`.
- `428 Precondition Required` — `If-Match` отсутствует.

#### `PUT /api/cart/items/{productId}`

Устанавливает количество существующей позиции корзины.

Требуется `If-Match`.

Запрос:

```json
{
  "quantity": 3
}
```

Правила:

- `quantity` должно быть положительным целым числом. Нулевые и отрицательные
  значения отклоняются; используйте `DELETE` для удаления позиции.
- Товар должен быть активным.
- Запрошенное количество не должно превышать доступный запас.
- Изменение количества не меняет `isSelected`.
- Переданное значение `If-Match` должно соответствовать текущей версии корзины.
- Неудачная операция не должна частично изменять корзину.

Ответы: тот же набор, что и у `POST /api/cart/items`, с кодом
`cart_item_not_found`, когда товара нет в корзине.

#### `DELETE /api/cart/items/{productId}`

Удаляет товар из корзины.

Требуется `If-Match`. Запрос не имеет тела; версия корзины передаётся только
через `If-Match`.

Правила:

- Переданное значение `If-Match` должно соответствовать текущей версии корзины.
- Удаление недоступного товара разрешено.
- Неудачная операция не должна частично изменять корзину.

Ответы:

- `200 OK` — обновлённая корзина и новый `ETag`.
- `404 Not Found` — у пользователя нет корзины или позиция не существует.
- `412 Precondition Failed` — устаревший `If-Match`, с кодом
  `cart_version_conflict`.
- `428 Precondition Required` — `If-Match` отсутствует.

#### `PUT /api/cart/selection`

Изменяет выбор позиций корзины для частичного checkout.

Требуется `If-Match`.

Запрос:

```json
{
  "items": [
    {
      "productId": "product-id",
      "isSelected": true
    }
  ]
}
```

Правила:

- Обновляются только перечисленные позиции; позиции, отсутствующие в `items`,
  сохраняют текущее значение `isSelected`.
- `productId` должен быть непустым идентификатором; `isSelected` должен быть
  логическим значением.
- Изменение выбора является мутацией корзины: оно изменяет `rowversion` корзины
  и требует `If-Match`.
- Выбор сам по себе не резервирует запас; резерв создаётся только при checkout.
- Неудачная операция не должна частично изменять корзину.

Ответы:

- `200 OK` — обновлённая корзина с `isSelected`, `totalAmount`,
  `selectedTotalAmount` и новым `ETag`.
- `400 Bad Request` — недопустимый `productId` или тело запроса, с кодом
  `validation_error`.
- `404 Not Found` — позиции нет в корзине, с кодом `cart_item_not_found`.
- `412 Precondition Failed` — устаревший `If-Match`, с кодом
  `cart_version_conflict`.
- `428 Precondition Required` — `If-Match` отсутствует.

#### Оформление заказа

`POST /api/orders` оформляет только выбранные позиции корзины. Невыбранные
позиции остаются в корзине без резерва. Если ни одна позиция не выбрана,
checkout возвращает `409 Conflict` с кодом `cart_empty`; `detail` содержит
`no selected items`. Отдельный код для пустого выбора не вводится.

### 3.4 Оформление заказа и заказы

#### `POST /api/orders`

Создаёт заказ из выбранных позиций корзины текущего пользователя.

Обязательные заголовки:

```http
Idempotency-Key: <client-generated key>
If-Match: "<cart ETag>"
```

Тело запроса пустое.

Правила оформления заказа:

1. Аутентифицировать пользователя.
2. Проверить формат `Idempotency-Key` и наличие `If-Match`. Неудача здесь
   возвращает `400` или `428` и не резервирует ключ.
3. Вычислить отпечаток запроса из целевого запроса и переданного значения
   `If-Match`. `selection` явно не включается: `IsSelected` меняет `rowversion`
   корзины, а `rowversion` уже входит в `If-Match` и отпечаток.
4. Найти существующую запись идемпотентности для текущего пользователя и ключа
   **до чтения текущей корзины**.
5. Если завершённая запись существует и её отпечаток совпадает, вернуть
   сохранённые HTTP-статус и тело ответа. Не создавать другой заказ.
6. Если ключ существует с другим отпечатком, вернуть `409 Conflict` с кодом
   `idempotency_key_reused`.
7. Если совпадающая запись находится в процессе выполнения, подождать в течение
   ограниченного периода. Если окончательный результат не становится доступным
   вовремя, вернуть `503 Service Unavailable` с кодом `idempotency_in_progress` и
   указать клиенту повторить тот же ключ и запрос. Если срок резервирования истёк,
   восстановление по требованию может захватить попытку.
8. Только когда не применяется ни одна существующая запись, зарезервировать ключ
   в короткой транзакции, затем прочитать корзину в соответствии с требуемой
   стратегией транзакции и блокировки.
9. Проверить, что есть выбранные позиции, товары активны, количества допустимы и
   остаётся достаточный запас. Если выбранных позиций нет, вернуть
   `409 cart_empty`.
10. Создать заказ и снимки только выбранных позиций, используя текущие названия
    и цены товаров, и создать `Payment` в состоянии `Pending`. Вернуть
    `paymentId` в представлении заказа.
11. Зарезервировать выбранные позиции, очистить только выбранные позиции
    корзины, изменить строку корзины так, чтобы изменилась её версия, и
    атомарно пометить запись идемпотентности завершённой в успешной транзакции
    оформления заказа.

Переданное значение `If-Match` является частью отпечатка запроса. Повторение той
же попытки должно использовать тот же ключ идемпотентности и то же значение
`If-Match`.

Если бизнес-валидация завершается неудачно, транзакция оформления заказа должна
откатиться: заказ не создаётся, запас не списывается, а корзина остаётся
неизменной. Окончательные ответы об ошибках бизнес-правил сохраняются для ключа
идемпотентности, чтобы повторение той же попытки получало тот же результат.
После сохранённой окончательной ошибки бизнес-правила новая попытка требует
нового ключа идемпотентности.

Неожиданные инфраструктурные ошибки не сохраняются как окончательные
бизнес-результаты. Если результат фиксации в базе данных неизвестен, клиент
должен повторить попытку с тем же ключом. Сервер должен проверить устойчивое
состояние, прежде чем решать, возвращать ли сохранённый результат или разрешать
восстановление; он не должен предполагать, что неизвестное оформление заказа
завершилось неудачно.

Ответы:

- `201 Created` — заказ создан. Тело — это представление заказа с `paymentId`, а
  заголовок `Location` указывает на `/api/orders/{orderId}`. Ответ содержит
  `ETag` созданного заказа.
- `400 Bad Request` — некорректный запрос или недопустимый `Idempotency-Key`.
- `401 Unauthorized` — неаутентифицированный запрос.
- `404 Not Found` — у пользователя нет корзины, с кодом `cart_not_found`.
- `409 Conflict` — конфликт бизнес-правила (`cart_empty`, `product_unavailable`,
  `insufficient_stock`) или конфликт идемпотентности.
- `412 Precondition Failed` — устаревший `ETag` корзины, с кодом
  `cart_version_conflict`.
- `428 Precondition Required` — `If-Match` отсутствует.
- `503 Service Unavailable` — совпадающая попытка всё ещё выполняется после
  ограниченного ожидания, или сервер не может безопасно разрешить неизвестное
  состояние оформления заказа.

Точный статус ответа и тело для окончательной ошибки бизнес-правила должны
сохраняться и воспроизводиться согласованно. Неожиданные инфраструктурные ошибки
`5xx` не должны представляться как окончательные сбои оформления заказа.

#### `GET /api/orders`

Возвращает заказы, принадлежащие текущему пользователю, для запрошенной
страницы.

Пример ответа:

```json
{
  "items": [
    {
      "id": "order-id",
      "status": "Created",
      "createdAtUtc": "2026-01-15T12:30:00Z",
      "totalAmount": 39.98,
      "paymentId": "payment-id"
    }
  ],
  "page": 1,
  "pageSize": 20,
  "totalCount": 1
}
```

Правила:

- Заказы, принадлежащие другим пользователям, никогда не возвращаются.
- `status` принимает одно из шести значений: `Created`, `Paid`, `Shipped`,
  `Delivered`, `Cancelled`, `Returned`.
- `paymentId` всегда не-null для заказов, созданных через checkout (`Payment`
  создаётся в той же транзакции). `null` не встречается в MVP+; поле оставлено
  nullable на уровне схемы для будущей совместимости.
- Результаты упорядочены по времени создания, сначала новые, для стабильной
  пагинации.
- Позиции заказа не включаются в список; используйте конечную точку сведений о
  заказе.

#### `GET /api/orders/{orderId}`

Возвращает один заказ, принадлежащий текущему пользователю.

Ответы:

- `200 OK` — заказ найден и принадлежит текущему пользователю. Ответ содержит
  `ETag` заказа.
- `404 Not Found` — заказ не существует или принадлежит другому пользователю, с
  кодом `order_not_found`.

Пример ответа:

```json
{
  "id": "order-id",
  "status": "Created",
  "createdAtUtc": "2026-01-15T12:30:00Z",
  "totalAmount": 39.98,
  "paymentId": "payment-id",
  "items": [
    {
      "orderItemId": "order-item-id",
      "productId": "product-id",
      "productName": "Example Product",
      "unitPrice": 19.99,
      "quantity": 2,
      "cancelledQuantity": 0,
      "lineTotal": 39.98
    }
  ],
  "payment": {
    "id": "payment-id",
    "orderId": "order-id",
    "amount": 39.98,
    "refundedAmount": 0.00,
    "status": "Pending",
    "createdAtUtc": "2026-01-15T12:30:00Z",
    "confirmedAtUtc": null,
    "refundedAtUtc": null
  }
}
```

Правила:

- `cancelledQuantity` вычисляется как сумма количеств в
  `OrderItemCancellation` и не хранится отдельным полем.
- `OrderItem.Quantity` — неизменяемый снимок исходного количества;
  `cancelledQuantity <= quantity`.
- `Order.TotalAmount` остаётся снимком исходного заказа и не уменьшается при
  частичной отмене.
- Позиции заказа сохраняют название товара и цену за единицу на момент
  оформления заказа. Последующие изменения каталога не должны изменять
  исторические сведения о заказе.
- `payment` — объект платежа или `null`, если платежа нет.

#### `POST /api/orders/{orderId}/cancel`

Отменяет заказ полностью или частично.

Обязательный заголовок:

```http
If-Match: "<order ETag>"
```

Тело необязательно:

```json
{
  "items": [
    {
      "orderItemId": "order-item-id",
      "quantity": 1
    }
  ]
}
```

Правила:

- Только владелец может отменить заказ.
- Отсутствие тела означает полную отмену заказа.
- Если тело содержит `items`, выполняется частичная отмена перечисленных
  количеств.
- Пустой массив `items: []` не является полной отменой и отклоняется как ошибка
  валидации.
- `quantity` должна быть положительным целым числом и не превышать оставшееся
  количество позиции (`quantity - cancelledQuantity`).
- Неизвестный `orderItemId` отклоняется как ошибка валидации.
- Для каждой отмены создаётся запись `OrderItemCancellation`.
  `OrderItem.Quantity` не уменьшается; `cancelledQuantity` вычисляется.
- Полная отмена переводит заказ в `Cancelled` (из `Created` или `Paid`).
- Частичная отмена не меняет статус заказа; «частично отменён» определяется
  наличием записей `OrderItemCancellation`.
- Отмена `Created` возвращает отменяемое количество из `Reserved` в
  `Available`.
- Отмена `Paid` возвращает количество в `Available` и выполняет refund по
  `../adr/ADR-008-payments-and-idempotency.md`; для частичной отмены сумма
  refund рассчитывается по снимкам `OrderItem.UnitPrice`.
- Если refund завершается неудачно, транзакция отмены откатывается: заказ,
  отмены, запас и платёж не должны остаться в частично изменённом состоянии.
- Отмена не изменяет корзину.
- Успешная отмена изменяет `Order.RowVersion` и возвращает новый `ETag`.
- Отдельный `Idempotency-Key` для отмены не используется.

Ответы:

- `200 OK` — обновлённый заказ с новым `ETag`.
- `400 Bad Request` — недопустимое тело, пустой `items` или количество больше
  оставшегося, с кодом `validation_error`.
- `404 Not Found` — заказ не существует или принадлежит другому пользователю, с
  кодом `order_not_found`.
- `409 Conflict` — заказ уже отменён (`order_already_cancelled`), недопустимый
  переход (`invalid_order_transition`) или refund невозможен
  (`refund_not_allowed`).
- `412 Precondition Failed` — устаревший `If-Match`, с кодом
  `order_version_conflict`.
- `415 Unsupported Media Type` — непустое тело с неподдерживаемым
  `Content-Type`, с кодом `unsupported_media_type`.
- `428 Precondition Required` — `If-Match` отсутствует.

Отмена `Shipped`, `Delivered` или `Returned` возвращает `409` с кодом
`invalid_order_transition`. Отмена уже `Cancelled` возвращает `409` с кодом
`order_already_cancelled`.

### 3.5 Платежи

#### Представление платежа

```json
{
  "id": "payment-id",
  "orderId": "order-id",
  "amount": 39.98,
  "refundedAmount": 0.00,
  "status": "Pending",
  "createdAtUtc": "2026-01-15T12:30:00Z",
  "confirmedAtUtc": null,
  "refundedAtUtc": null
}
```

`status` принимает значения `Pending`, `Confirmed`, `Failed`, `Refunded`.
`Refunded` устанавливается только при полном возврате
(`refundedAmount == amount`). Частичный возврат оставляет `Confirmed`.
`reserved` и провайдерские детали в API не раскрываются.

#### `POST /api/payments/{paymentId}/confirm`

Подтверждает платёж текущего пользователя.

Обязательный заголовок:

```http
Idempotency-Key: <client-generated key>
```

`If-Match` не требуется. Платёж не принадлежит admin; используется
идемпотентность по ключу.

Правила:

- Только владелец платежа может подтвердить платёж.
- Mock-провайдер выполняет `Pending → Confirmed`, заказ переходит
  `Created → Paid`, `Reserved` списывается.
- Подтверждение платежа, списание `Reserved`, перевод заказа в `Paid` и
  завершение записи идемпотентности выполняются в одной транзакции.
- Если `Payment.Status = Failed`, повтор с тем же ключом и отпечатком выполняет
  retry `Failed → Pending → Confirmed` для того же `Payment`. `Failed` не
  является терминальным.
- `Refunded` терминален; повторный confirm не меняет платёж.
- Если платёж уже `Confirmed` и отпечаток совпадает, возвращается сохранённый
  успешный ответ. Если отпечаток отличается, возвращается `409` с кодом
  `payment_already_confirmed`.

Ответы:

- `200 OK` — представление платежа.
- `400 Bad Request` — недопустимый `Idempotency-Key` или тело, с кодом
  `validation_error`.
- `401 Unauthorized` — неаутентифицированный запрос.
- `404 Not Found` — платёж не существует или принадлежит другому пользователю,
  с кодом `payment_not_found`.
- `409 Conflict` — `payment_already_confirmed` (другой отпечаток),
  `payment_failed` (mock вернул `Failed`), `invalid_order_transition` (заказ не
  в `Created`) или `idempotency_key_reused`.
- `503 Service Unavailable` — `idempotency_in_progress` после ограниченного
  ожидания.

#### `POST /api/payments/{paymentId}/refund`

Выполняет административный возврат средств.

Доступ: только admin (`X-Test-User: admin`), только Development.

Обязательный заголовок:

```http
Idempotency-Key: <client-generated key>
```

Запрос:

```json
{
  "amount": 5.00,
  "reason": "Customer request"
}
```

Правила:

- `amount` должен быть положительным `decimal` и не превышать
  `Payment.Amount - Payment.RefundedAmount`.
- `reason` необязателен.
- Mock-провайдер выполняет `Confirmed → Refunded` при полном возврате или
  оставляет `Confirmed` при частичном.
- Для каждой операции создаётся запись `Refund`; `Payment.RefundedAmount`
  увеличивается на `amount`. `RefundedAtUtc` устанавливается только при полном
  возврате.
- Refund не изменяет заказ и запас. Возврат для `Paid → Cancelled` и
  `Delivered → Returned` выполняется внутренними операциями cancel/return, а не
  этим endpoint.
- Endpoint является admin-инструментом ручного возврата.

Ответы:

- `200 OK` — представление платежа.
- `400 Bad Request` — недопустимый `amount`, `reason` или тело, с кодом
  `validation_error`.
- `401 Unauthorized` — неаутентифицированный запрос.
- `403 Forbidden` — не admin, с кодом `forbidden`.
- `404 Not Found` — платёж не существует, с кодом `payment_not_found`.
- `409 Conflict` — `refund_not_allowed` (статус не `Confirmed` или `amount`
  больше остатка) или `idempotency_key_reused`.
- `503 Service Unavailable` — `idempotency_in_progress` после ограниченного
  ожидания.

### 3.6 Admin API

Все admin endpoints доступны только в Development и требуют роль admin
(`X-Test-User: admin`). В Production они не регистрируются и возвращают
`404 Not Found`. Запрос от `alice` или `bob` возвращает `403 Forbidden` с кодом
`forbidden`.

#### `POST /api/admin/products/{productId}/deactivate`

Устанавливает `Product.IsActive = false`.

Правила:

- Операция идемпотентна: повторная деактивация не меняет результат.
- Деактивация разрешена при наличии активных заказов.
- Снимки названия и цены в существующих заказах не меняются.
- Деактивированный товар нельзя добавить в корзину или оформить; существующие
  позиции корзины остаются видимыми как недоступные и могут быть удалены.

Ответы:

- `200 OK` — представление товара.
- `403 Forbidden` — не admin, с кодом `forbidden`.
- `404 Not Found` — товар не существует, с кодом `product_not_found`.

#### `POST /api/admin/products/{productId}/stock`

Устанавливает абсолютное значение `Product.Available`.

Запрос:

```json
{
  "available": 10
}
```

Правила:

- `available` — целое число, `>= 0`.
- `Reserved` не изменяется.
- Операция атомарна и использует optimistic concurrency по `Available` и
  `rowversion`; конкурентные изменения не должны теряться.
- При исчерпании ограниченного числа повторных попыток возвращается `409` с
  кодом `admin_stock_conflict`.

Ответы:

- `200 OK` — представление товара.
- `400 Bad Request` — `available < 0` или нецелое значение, с кодом
  `validation_error`.
- `403 Forbidden` — не admin, с кодом `forbidden`.
- `404 Not Found` — товар не существует, с кодом `product_not_found`.
- `409 Conflict` — конкурентное изменение admin stock, с кодом
  `admin_stock_conflict`.

#### `POST /api/admin/orders/{orderId}/ship`

Выполняет `Paid → Shipped`.

Ответы:

- `200 OK` — обновлённое представление заказа с новым `ETag`.
- `403 Forbidden` — не admin, с кодом `forbidden`.
- `404 Not Found` — заказ не существует, с кодом `order_not_found`.
- `409 Conflict` — заказ не в `Paid`, с кодом `invalid_order_transition`.

#### `POST /api/admin/orders/{orderId}/deliver`

Выполняет `Shipped → Delivered`.

Ответы:

- `200 OK` — обновлённое представление заказа с новым `ETag`.
- `403 Forbidden` — не admin, с кодом `forbidden`.
- `404 Not Found` — заказ не существует, с кодом `order_not_found`.
- `409 Conflict` — заказ не в `Shipped`, с кодом `invalid_order_transition`.

#### `POST /api/admin/orders/{orderId}/return`

Выполняет `Delivered → Returned`, выполняет refund и возвращает запас.

Правила:

- Возвращается весь заказ; частичный возврат после доставки в MVP+ не
  поддерживается.
- Refund выполняется по `../adr/ADR-008-payments-and-idempotency.md`.
- Запас возвращается в `Available` на количества заказа.
- Refund, изменение запаса и переход статуса выполняются в одной транзакции.
- Если refund падает, вся операция откатывается.

Ответы:

- `200 OK` — обновлённое представление заказа с новым `ETag`.
- `403 Forbidden` — не admin, с кодом `forbidden`.
- `404 Not Found` — заказ не существует, с кодом `order_not_found`.
- `409 Conflict` — заказ не в `Delivered` (`invalid_order_transition`) или
  refund невозможен (`refund_not_allowed`).

## 4. Формат ошибок

Ошибки используют стандартную форму `ProblemDetails` со стабильным расширением
`code`.

Пример:

```json
{
  "type": "https://example.invalid/problems/cart-version-conflict",
  "title": "Cart version conflict",
  "status": 412,
  "detail": "The cart changed after it was retrieved. Fetch the latest cart and retry with an updated request.",
  "instance": "/api/orders",
  "code": "cart_version_conflict"
}
```

Поле `instance` присутствует во всех ответах `ProblemDetails`, включая
воспроизводимые сохранённые ошибки оформления заказа и `GET /health` при `503`.

Пример URI `type` является иллюстративным. Реализация должна использовать
согласованное соглашение о типах проблем.

### 4.1 Коды ошибок

Следующие коды являются частью контракта API:

| Код | HTTP-статус | Значение |
|---|---:|---|
| `validation_error` | 400 | Поля запроса, заголовки или параметры запроса недопустимы |
| `unauthenticated` | 401 | Аутентификация отсутствует или недопустима |
| `forbidden` | 403 | Недостаточно прав, включая не-admin доступ к admin endpoint |
| `product_not_found` | 404 | Товар не существует или неактивен |
| `cart_not_found` | 404 | У пользователя ещё нет корзины |
| `cart_item_not_found` | 404 | Позиция корзины не существует |
| `order_not_found` | 404 | Заказ не существует или не принадлежит текущему пользователю |
| `payment_not_found` | 404 | Платёж не существует или не принадлежит текущему пользователю |
| `cart_version_conflict` | 412 | Переданное значение `If-Match` корзины устарело |
| `order_version_conflict` | 412 | Переданное значение `If-Match` заказа устарело |
| `unsupported_media_type` | 415 | Запрос с неподдерживаемым Content-Type для эндпоинта, принимающего тело |
| `precondition_required` | 428 | Обязательный заголовок `If-Match` отсутствует |
| `cart_empty` | 409 | Оформление заказа запрошено без выбранных позиций |
| `product_unavailable` | 409 | Товар нельзя использовать для запрошенной операции |
| `insufficient_stock` | 409 | Для одного или нескольких товаров недостаточно запаса |
| `idempotency_key_reused` | 409 | Тот же ключ был использован с другим запросом |
| `invalid_order_transition` | 409 | Недопустимый переход статуса заказа |
| `order_already_cancelled` | 409 | Заказ уже отменён |
| `payment_already_confirmed` | 409 | Платёж уже подтверждён с другим отпечатком |
| `payment_failed` | 409 | Mock-провайдер вернул `Failed` |
| `refund_not_allowed` | 409 | Refund невозможен по статусу или сумме |
| `admin_stock_conflict` | 409 | Конкурентное изменение admin stock |
| `idempotency_in_progress` | 503 | Совпадающая попытка оформления заказа или платежа всё ещё разрешается |
| `checkout_retry` | 503 | Временная ошибка: состояние изменилось конкурентно; попытка остаётся `InProgress`, клиент повторяет тот же запрос с тем же ключом идемпотентности |
| `health_unavailable` | 503 | База данных недоступна |

Реализация может добавлять коды при необходимости, но существующие коды и их
значения должны оставаться стабильными. В частности, `cart_version_conflict`
сохраняет своё имя, хотя его статус изменился с `409` на `412`, когда версия
перешла на `If-Match`.

`insufficient_reserved` и `order_already_shipped` не входят в контракт:
`available < 0` для admin stock возвращает `400 validation_error`, а ship из
состояния, отличного от `Paid`, возвращает `409 invalid_order_transition`.

Ответ `503` является временным. Он никогда не означает, что оформление заказа
или платёж окончательно завершились неудачно, и не должен сохраняться как
окончательный бизнес-результат.

При недостаточном запасе ответ должен указывать каждый затронутый товар с
помощью его идентификатора и названия товара, прочитанных после отката неудачной
транзакции оформления заказа. Список не должен подразумевать, что запас
зарезервирован после ответа.

Известные отклонения от этого контракта ошибок, которые сознательно приняты и
отложены для MVP+, перечислены в `../DECISIONS.md`, раздел 13.

## 5. Требования к конкурентности и согласованности

HTTP-ответы должны отражать результат нижележащей транзакции.

- Изменения корзины и оформление заказа используют согласованную стратегию
  блокировки строки корзины.
- Изменения корзины и оформление заказа проверяют переданный `ETag` корзины
  через `If-Match`.
- Успешное оформление заказа изменяет строку корзины так, что предыдущий `ETag`
  становится недействительным.
- Checkout резервирует только выбранные позиции, создаёт `Payment` в `Pending` и
  заказ в `Created`, очищает только выбранные позиции корзины; резервирование,
  создание заказа и платежа, очистка выбранных позиций, изменение версии
  корзины и завершение идемпотентности фиксируются атомарно.
- Списания запаса используют атомарные условные обновления, которые выполняются
  успешно, только когда остаётся достаточный запас.
- Неудачное оформление заказа не должно оставлять частичный заказ, частичные
  списания запаса, платёж или очищенную корзину.
- Confirm фиксирует `Payment.Confirmed`, `Order.Paid` и списание `Reserved`
  атомарно.
- Полная и частичная отмена используют `If-Match` с `Order.RowVersion`.
  Изменение статуса при полной отмене, записи `OrderItemCancellation`, возврат
  запаса и refund фиксируются атомарно.
- Одновременные попытки отмены не должны возвращать запас или выполнять refund
  более одного раза.
- Admin stock выполняет атомарное optimistic-обновление `Available` и не
  изменяет `Reserved`.
- Ship, deliver и return выполняются атомарно; return объединяет refund,
  возврат запаса и смену статуса в одной транзакции.
- Audit-записи создаются в отдельной транзакции после commit и не влияют на
  успешность бизнес-операции; см. `../adr/ADR-007-domain-events.md` и
  `../adr/ADR-010-audit.md`.
- Одновременное обновление корзины не должно воскрешать старое содержимое
  корзины после завершения оформления заказа.
- Взаимоблокировки не повторяются внутри процесса; клиент повторяет попытку с
  тем же ключом идемпотентности или повторно получает корзину/заказ.

## 6. Жизненный цикл идемпотентности

### 6.1 Оформление заказа

Механизм идемпотентности оформления заказа следует этим правилам:

- Ключи имеют область действия аутентифицированного пользователя и должны
  соответствовать формату, определённому в `../DECISIONS.md`, раздел 10.
- Ключ связан с отпечатком целевого запроса и переданного значения `If-Match`.
- Fingerprint не включает `selection` явно: `IsSelected` меняет `rowversion`
  корзины, а `rowversion` уже входит в `If-Match` и fingerprint.
- Совпадающий завершённый запрос возвращает сохранённый ответ без чтения текущей
  корзины или создания другого заказа.
- Совпадающий выполняющийся запрос ожидает в течение ограниченного периода, а
  затем возвращает `503` с `idempotency_in_progress`; он не должен выполнять
  оформление заказа самостоятельно.
- Ключ, связанный с другим запросом, возвращает `idempotency_key_reused`.
- Окончательные ошибки бизнес-правил сохраняются и воспроизводятся. Новая
  попытка после сохранённой окончательной ошибки бизнес-правила требует нового
  ключа.
- Неожиданные инфраструктурные ошибки не сохраняются как окончательные
  бизнес-результаты.
- Восстановление старой записи `InProgress` происходит по требованию во время
  повторной попытки и требует истёкшего срока резервирования и проверки
  устойчивого состояния базы данных. Фоновая служба восстановления не
  существует.
- Если результат фиксации неизвестен, устойчивое состояние должно быть
  проверено, прежде чем решать, завершилась ли попытка или её можно безопасно
  повторить.

Точная схема базы данных и процедура восстановления определены в `data-model.md`
и `../adr/ADR-002-checkout-idempotency.md`.

### 6.2 Идемпотентность платежа

`POST /api/payments/{paymentId}/confirm` и
`POST /api/payments/{paymentId}/refund` используют `PaymentAttempt`:

- `(UserId, IdempotencyKey)` уникален.
- Ключ имеет область действия аутентифицированного пользователя и должен
  соответствовать формату из `../DECISIONS.md`, раздел 10.
- Для `confirm` fingerprint — это
  `SHA-256("POST /api/payments/{id}/confirm\n{id}")`: входят метод, путь и
  идентификатор платежа. `Idempotency-Key` не входит в fingerprint, потому что
  ключ уже является частью уникального ограничения.
- Для `refund` fingerprint включает метод, путь, идентификатор платежа и
  нормализованные `amount` и `reason`; иначе повтор с другой суммой ошибочно
  воспроизвёл бы сохранённый ответ. `Idempotency-Key` не входит в fingerprint.
- Совпадающий завершённый запрос возвращает сохранённые статус и тело без
  повторного изменения платежа, заказа или запаса.
- Ключ с другим fingerprint возвращает `409` с кодом
  `idempotency_key_reused`.
- Совпадающий выполняющийся запрос ожидает ограниченное время, затем возвращает
  `503` с `idempotency_in_progress`; восстановление выполняется по требованию,
  как у checkout, и не должно независимо повторять операцию.
- `Payment.Status = Failed` не терминален: повтор с тем же ключом и fingerprint
  выполняет retry `Failed → Pending → Confirmed` для того же `Payment`.
- `Payment.Status = Refunded` терминален.
- Окончательные бизнес-ошибки сохраняются для идемпотентного воспроизведения;
  неожиданные инфраструктурные ошибки не сохраняются как окончательные
  результаты.

Точная схема `PaymentAttempt` и процедура восстановления определены в
`data-model.md` и `../adr/ADR-008-payments-and-idempotency.md`.

## 7. Вне области охвата

API MVP+ не включает:

- Реальную аутентификацию и авторизацию (JWT/OAuth), регистрацию пользователей
  производственного уровня
- Реальный платёжный провайдер, Stripe, webhooks и reconciliation
- Уведомления
- Промо, купоны, скидки и налоги
- Outbox, внешний обмен сообщениями и фоновую обработку
- TTL и cleanup резервов
- Admin UI
- Мультивалютность
- Складской учёт для нескольких складов
