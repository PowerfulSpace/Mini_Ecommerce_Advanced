# Модель данных

## 1. Назначение

Этот документ определяет планируемую реляционную модель данных для MVP+
Mini E-commerce.

Модель должна поддерживать:

- Каталог товаров.
- Не более одной корзины на пользователя, создаваемой при первом обращении к
  корзине.
- Позиции корзины с проверенными количествами и выбором позиций.
- Заказы с неизменяемыми снимками покупки и частичной отменой.
- Резервирование и восстановление запаса (`Available`/`Reserved`).
- Платежи, частичные refund и идемпотентность подтверждения.
- Идемпотентность оформления заказа.
- Аудит действий по заказам, платежам и admin-изменениям.
- Транзакционную согласованность при одновременных запросах.

SQL Server — целевая реляционная база данных, а Entity Framework Core —
технология сохранения данных по умолчанию.

Этот документ определяет предполагаемую модель и её требования к целостности.
Точные конфигурации EF Core и миграции будут реализованы на этапе
инфраструктуры.

## 2. Принципы проектирования

1. Используйте реляционные ограничения для защиты целостности данных везде, где
   это практически возможно.
2. Представляйте денежные значения в Domain через `Money`, а в SQL Server — с
   помощью `decimal(18,2)`; см. [ADR-003](../adr/ADR-003-money-value-object.md).
3. Храните метки времени в UTC.
4. Используйте первичные и внешние ключи для связей между сущностями.
5. Избегайте физического удаления товаров, на которые ссылаются корзины или
   исторические заказы.
6. Храните названия товаров и цены на момент покупки в позициях заказа.
7. Сохраняйте атомарность операций оформления заказа, оплаты, отмены и возврата.
8. Используйте механизмы конкурентного доступа, специфичные для SQL Server, где
   это требуется.
9. Не рассматривайте валидацию на уровне приложения как замену транзакционным
   операциям базы данных.
10. Ограничьте схему таблицами MVP+, включая `Payments`, `Refunds`,
    `PaymentAttempts`, `AuditLog` и `OrderItemCancellations`; не добавляйте
    таблицы для функций за пределами MVP+.
11. Храните `Available` и `Reserved` как два отдельных поля запаса; см.
    [ADR-005](../adr/ADR-005-stock-reservations.md).
12. `AuditLog` работает append-only: записи не обновляются и не удаляются; см.
    [ADR-010](../adr/ADR-010-audit.md).

## 3. Обзор сущностей

Планируемые сохраняемые сущности:

- `User`
- `Product`
- `Cart`
- `CartItem`
- `Order`
- `OrderItem`
- `CheckoutAttempt`
- `Payment`
- `Refund`
- `PaymentAttempt`
- `OrderItemCancellation`
- `AuditLog`

Эти имена — логические имена сущностей. Точные имена таблиц и соглашения об
именовании могут быть окончательно определены при настройке EF Core.

## 4. Определения сущностей

### 4.1 Пользователь

Представляет идентичность клиента, известную приложению.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `Email` | `nvarchar(320)` | Обязательно; уникально |
| `Role` | `nvarchar(20)` | NOT NULL, CHECK IN ('customer', 'admin'), default 'customer' |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- У каждого пользователя есть стабильный идентификатор.
- Уникальность адреса электронной почты должна обеспечиваться базой данных.
- Начальные данные для Development должны быть повторяемыми и не создавать
  дублирующихся пользователей.
- Роль admin используется для admin endpoints (ADR-009). Seed: alice/bob —
  customer, admin — admin.
- `Role` не меняется через публичный API (в MVP+ нет endpoint смены роли).
- Идентичность пользователя, используемая для принадлежности корзины и заказа,
  берётся из контекста аутентифицированного запроса.
- MVP+ не требует регистрации клиентов или хранения паролей.

Сущность `User` представляет идентичность клиента приложения. Это не означает,
что в MVP+ реализуется полноценная система управления идентификацией.

### 4.2 Товар

Представляет товар каталога и его текущее состояние запаса.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `Name` | `nvarchar(200)` | Обязательно |
| `Description` | `nvarchar(2000)` | Обязательно |
| `Price` | `decimal(18,2)` | Обязательно; `Money` в Domain; неотрицательно |
| `Available` | `int` | Обязательно; неотрицательно |
| `Reserved` | `int` | Обязательно; неотрицательно |
| `IsActive` | `bit` | Обязательно |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- В публичном каталоге отображаются только активные товары.
- Товары деактивируются с помощью `IsActive = false`; физическое удаление не
  входит в MVP+.
- `Available` — запас, доступный для новых заказов; `Reserved` — запас,
  зарезервированный незавершёнными заказами.
- Запас не может быть отрицательным.
- Цена должна быть неотрицательной.
- `Currency` не хранится: в MVP+ все суммы — USD.
- При создании заказа оформление заказа использует текущую цену товара.
- Резервирование и восстановление запаса должны быть атомарными и выполняться
  только при достаточном запасе.

Ограничение CHECK базы данных должно обеспечивать `Available >= 0`,
`Reserved >= 0` и `Price >= 0`. `Description` обязателен; ограничение длины —
2000 символов.

### 4.3 Корзина

Представляет сохраняемую корзину покупок пользователя.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `UserId` | `uniqueidentifier` | Обязательно; внешний ключ на `User` |
| `RowVersion` | `rowversion` | Обязательный токен конкурентности |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `UpdatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- У пользователя не более одной корзины.
- Корзина сохраняется, даже если не содержит позиций.
- Корзина создаётся при первом обращении пользователя через `GET /api/cart`.
- Успешное оформление заказа удаляет только выбранные позиции корзины, сохраняет
  запись корзины и невыбранные позиции.
- Уникальное ограничение на `UserId` обеспечивает правило одной корзины на
  пользователя и разрешает одновременные первые создания: проигравшая вставка
  завершается ошибкой ограничения, а реализация повторно читает выигравшую
  строку.
- `RowVersion` используется как часть стратегии защиты от устаревших обновлений
  и предоставляется клиентам как `ETag` корзины.
- Успешное оформление заказа должно обновлять строку корзины, например
  устанавливая `UpdatedAtUtc`, в той же транзакции. Это гарантирует изменение
  `rowversion` и недействительность ранее выданного `ETag`.

SQL Server автоматически создаёт и обновляет значение `rowversion`. Код
приложения не должен присваивать его вручную.

Изменения корзины и оформление заказа требуют, чтобы клиент передал текущий
`ETag` через `If-Match`. Устаревшие значения отклоняются с
`412 Precondition Failed`, а отсутствие обязательного `If-Match` — с
`428 Precondition Required`.

### 4.4 Позиция корзины

Представляет товар и количество, которые сейчас находятся в корзине.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `CartId` | `uniqueidentifier` | Обязательно; внешний ключ на `Cart` |
| `ProductId` | `uniqueidentifier` | Обязательно; внешний ключ на `Product` |
| `Quantity` | `int` | Обязательно; больше нуля |
| `IsSelected` | `bit` | Обязательно; default 1; NOT NULL |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `UpdatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- Корзина не может содержать несколько строк для одного товара.
- Уникальное ограничение на `(CartId, ProductId)` обеспечивает это правило;
  `IsSelected` в него не входит.
- Количество должно быть положительным.
- `IsSelected` по умолчанию равен `1` (`true`) и является частью состояния
  корзины. Изменение выбора должно обновлять `Cart.RowVersion`.
- Добавление уже присутствующего в корзине товара увеличивает его существующее
  количество.
- Операции с корзиной должны проверять активность товара и запас в соответствии
  со спецификацией.
- Деактивация товара не удаляет автоматически его существующую позицию корзины.
- Позиции корзины удаляются явным удалением или успешным оформлением заказа;
  checkout удаляет только выбранные позиции.

Ограничение CHECK базы данных должно обеспечивать `Quantity > 0`.

Ссылка позиции корзины на товар сохраняется для навигации и проверки. Позиция
корзины не является снимком покупки: её отображаемая цена берётся из текущих
данных каталога в соответствии с утверждёнными бизнес-правилами.

### 4.5 Заказ

Представляет успешно завершённое оформление заказа.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `UserId` | `uniqueidentifier` | Обязательно; внешний ключ на `User` |
| `Status` | `nvarchar(20)` | Обязательно; CHECK по шести статусам |
| `PaymentId` | `uniqueidentifier` | NULL; FK не настроен на этапе 13; FK на `Payment` добавляется на этапе 19 вместе с таблицей `Payment` |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `TotalAmount` | `decimal(18,2)` | Обязательно; неотрицательно |
| `RowVersion` | `rowversion` | Обязательный токен конкурентности |

Поддерживаемые статусы:

- `Created`
- `Paid`
- `Shipped`
- `Delivered`
- `Cancelled`
- `Returned`

Требования:

- Заказ принадлежит одному пользователю.
- Создание заказа, резервирование запаса и создание `Payment` в состоянии
  `Pending` происходят в одной транзакции оформления заказа.
- `PaymentId` допускает null; при оплате заказа он должен быть заполнен.
- `PaymentId` — nullable; FK на `Payment` добавляется на этапе 19 (миграция
  `AddPaymentsAndRefunds`). До этапа 19 поле существует без FK и заполняется
  через `Order.Create(..., Guid? paymentId = null)`.
- Заказ содержит одну или более позиций заказа.
- Общая сумма заказа рассчитывается по сохранённым ценам за единицу и
  количествам позиций заказа и не пересчитывается при частичной отмене.
- Исторические данные заказа должны оставаться независимыми от последующих
  изменений цен каталога или названий товаров.
- Полная отмена, возврат и частичная отмена изменяют заказ и атомарно изменяют
  запас и/или платёж.
- `RowVersion` используется для оптимистической конкурентности полной и
  частичной отмены.
- Заказы не удаляются физически в рамках MVP+.

Ограничение CHECK должно обеспечивать неотрицательность сумм и ограничивать
`Status` набором `('Created', 'Paid', 'Shipped', 'Delivered', 'Cancelled',
'Returned')`.

### 4.6 Позиция заказа

Представляет строку заказа и сохраняет снимок на момент покупки.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `OrderId` | `uniqueidentifier` | Обязательно; внешний ключ на `Order` |
| `ProductId` | `uniqueidentifier` | Обязательно; внешний ключ на `Product` |
| `ProductName` | `nvarchar(200)` | Обязательно; снимок |
| `UnitPrice` | `decimal(18,2)` | Обязательно; снимок |
| `Quantity` | `int` | Обязательно; положительное |

Требования:

- `ProductName` копируется из товара при создании заказа в ходе оформления.
- `UnitPrice` копируется из текущей цены каталога во время оформления заказа.
- `Quantity` копируется из проверенного количества в корзине и является
  неизменяемым снимком; при отмене оно не уменьшается.
- `CancelledQuantity` не хранится отдельным полем: оно вычисляется как
  `SUM(OrderItemCancellation.Quantity)`.
- Частичная отмена представлена дочерними записями `OrderItemCancellation`
  (см. §4.11).
- Сумма строки равна `UnitPrice × Quantity`.
- Общая сумма заказа — сумма всех сумм строк.
- Последующие переименования товаров или изменения цен не должны изменять
  исторические данные заказа.
- Полная и частичная отмена восстанавливают точные количества, записанные в
  позициях заказа и в записях `OrderItemCancellation`.

Ограничение CHECK должно обеспечивать `Quantity > 0` и неотрицательность
`UnitPrice`. Инвариант
`SUM(OrderItemCancellation.Quantity) <= OrderItem.Quantity` проверяется в
приложении.

`ProductId` остаётся ссылкой на товар каталога, а `ProductName` и `UnitPrice`
сохраняют исторические сведения о покупке.

Товары нельзя физически удалять, пока на них ссылаются позиции заказа.

### 4.7 Попытка оформления заказа

Представляет идемпотентную попытку оформления заказа.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `UserId` | `uniqueidentifier` | Обязательно; внешний ключ на `User` |
| `IdempotencyKey` | `nvarchar(128)` | Обязательно; должен соответствовать формату ключа, определённому в `../DECISIONS.md` |
| `RequestFingerprint` | `varbinary(32)` | Обязательно; SHA-256 целевого запроса и переданного значения `If-Match` |
| `Status` | `nvarchar(20)` | Обязательно; `InProgress` или `Completed` |
| `OrderId` | `uniqueidentifier` | Внешний ключ на `Order`; допускает null |
| `ResponseStatusCode` | `int` | Допускает null, пока не записан окончательный результат |
| `ResponsePayload` | `nvarchar(max)` | Допускает null, пока не записан окончательный результат |
| `LeaseExpiresAtUtc` | `datetime2` | Обязательно; используется при восстановлении по требованию |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `UpdatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- Ключ идемпотентности действует в пределах одного пользователя.
- Уникальное ограничение на `(UserId, IdempotencyKey)` предотвращает
  дублирующиеся попытки для одного пользователя и ключа и определяет, какое
  одновременное резервирование побеждает.
- Отпечаток запроса представляет семантически значимое содержимое запроса,
  определённое в `../adr/ADR-002-checkout-idempotency.md`.
- Повторное использование одного и того же ключа с другим отпечатком запроса
  приводит к `409 Conflict` с кодом `idempotency_key_reused`.
- Повторение одного и того же ключа и отпечатка возвращает сохранённый результат,
  если он существует.
- Успешная попытка связывается с созданным заказом.
- `ResponseStatusCode` и `ResponsePayload` хранят ответ, который должен быть
  воспроизведён, включая окончательные ответы об ошибках бизнес-правил.
- Неожиданные внутренние ошибки не должны записываться как окончательные
  бизнес-результаты; запись остаётся в состоянии `InProgress`.
- Восстановление не должно слепо выполнять попытку, устойчивый результат которой
  неизвестен.

Модель состояний:

- `InProgress` — попытка зарезервирована и не имеет устойчивого окончательного
  результата. `ResponseStatusCode` и `ResponsePayload` равны null.
- `Completed` — окончательный ответ сохранён и должен быть воспроизведён.
  `Completed` охватывает как успешные оформления заказа, так и окончательные
  ошибки бизнес-правил; сохранённый код состояния различает их.

Переходы:

- Вставка со статусом `InProgress` при резервировании ключа, при этом
  `LeaseExpiresAtUtc` устанавливается равным текущему времени UTC плюс срок
  резервирования.
- `InProgress` → `Completed` внутри успешной транзакции оформления заказа вместе
  с изменениями заказа, запаса и корзины.
- `InProgress` → `Completed` в отдельной транзакции после отката неудачной
  транзакции оформления заказа с сохранением окончательного ответа об ошибке
  бизнес-правила.
- `InProgress` остаётся `InProgress` после инфраструктурной ошибки или
  неизвестного результата фиксации.

Восстановление по требованию захватывает истёкшую попытку условным обновлением,
которое выполняется успешно, только когда запись всё ещё находится в состоянии
`InProgress`, а `LeaseExpiresAtUtc` находится в прошлом. Продолжает только
запрос, затрагивающий одну строку; все остальные следуют политике ожидания
выполняющейся попытки. Захват продлевает `LeaseExpiresAtUtc` на время попытки
восстановления.

Записи не очищаются автоматически в MVP+, как определено в `../DECISIONS.md`.

### 4.8 Платёж

Представляет платёж заказа.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `OrderId` | `uniqueidentifier` | Обязательно; внешний ключ на `Order`; уникально |
| `Amount` | `decimal(18,2)` | Обязательно; `>= 0` |
| `Status` | `nvarchar(20)` | Обязательно; CHECK по статусам |
| `Provider` | `nvarchar(50)` | Обязательно; `mock` |
| `ProviderPaymentId` | `nvarchar(200)` | NULL |
| `RefundedAmount` | `decimal(18,2)` | Обязательно; default 0; `>= 0`; `<= Amount` |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `ConfirmedAtUtc` | `datetime2` | NULL |
| `RefundedAtUtc` | `datetime2` | NULL |
| `RowVersion` | `rowversion` | Обязательный токен конкурентности |

Поддерживаемые статусы:

- `Pending`
- `Confirmed`
- `Failed`
- `Refunded`

Требования:

- `OrderId` уникален: у заказа не более одного платежа.
- `Payment` создаётся в состоянии `Pending` в транзакции checkout вместе с
  заказом.
- `Amount` соответствует сумме заказа; частичные платежи не поддерживаются.
- `RefundedAmount` накапливается; `SUM(Refund.Amount) == Payment.RefundedAmount`
  проверяется в приложении.
- `Status` изменяется только по допустимым переходам; `Refunded` терминален,
  `Failed` допускает retry.
- `Provider` в MVP+ — `mock`; `ProviderPaymentId` может быть null.
- `Currency` не хранится: все суммы — USD.
- См. [ADR-008](../adr/ADR-008-payments-and-idempotency.md).

### 4.9 Refund

Представляет частичный или полный возврат по платежу.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `PaymentId` | `uniqueidentifier` | Обязательно; внешний ключ на `Payment` |
| `Amount` | `decimal(18,2)` | Обязательно; `> 0` |
| `RefundedAtUtc` | `datetime2` | Обязательно; UTC |
| `Reason` | `nvarchar(500)` | NULL |

Требования:

- Каждый возврат, включая полный, создаёт запись `Refund`.
- Несколько частичных refund допускаются.
- Сумма refund не превышает `Payment.Amount - Payment.RefundedAmount`.
- `SUM(Refund.Amount) == Payment.RefundedAmount` проверяется в приложении.
- `Payment.Status = Refunded` устанавливается только при полном возврате.
- Отдельного статуса `PartiallyRefunded` нет.
- `Refund` не удаляется каскадно вместе с платежом или заказом.
- См. [ADR-008](../adr/ADR-008-payments-and-idempotency.md).

### 4.10 PaymentAttempt

`PaymentAttempt` — идемпотентная попытка confirm и refund.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `UserId` | `uniqueidentifier` | Обязательно; внешний ключ на `User` |
| `IdempotencyKey` | `nvarchar(128)` | Обязательно |
| `RequestFingerprint` | `varbinary(32)` | Обязательно; SHA-256 |
| `Status` | `nvarchar(20)` | Обязательно; `InProgress` или `Completed` |
| `PaymentId` | `uniqueidentifier` | NULL; внешний ключ на `Payment` |
| `ResponseStatusCode` | `int` | NULL |
| `ResponsePayload` | `nvarchar(max)` | NULL |
| `LeaseExpiresAtUtc` | `datetime2` | Обязательно |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `UpdatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- Уникальность `(UserId, IdempotencyKey)` предотвращает дублирующиеся попытки.
- `PaymentAttempt` не обобщает и не заменяет `CheckoutAttempt`.
- `RequestFingerprint` — SHA-256 fingerprint запроса. Для confirm: метод, путь
  и `paymentId`; для refund: метод, путь, `paymentId`, `amount` и `reason`
  (ADR-008).
- `InProgress` использует lease и bounded wait; фоновый cleanup не вводится.
- Завершённая попытка воспроизводит сохранённый результат; окончательный
  `Failed` допускает retry по правилам ADR-008.
- Записи не очищаются автоматически в MVP+.
- См. [ADR-008](../adr/ADR-008-payments-and-idempotency.md).

### 4.11 OrderItemCancellation

Представляет отмену количества по позиции заказа.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `OrderItemId` | `uniqueidentifier` | Обязательно; внешний ключ на `OrderItem` |
| `Quantity` | `int` | Обязательно; `> 0` |
| `CancelledAtUtc` | `datetime2` | Обязательно; UTC |
| `Reason` | `nvarchar(500)` | NULL |

Требования:

- Запись создаётся для полной или частичной отмены позиции заказа.
- `SUM(OrderItemCancellation.Quantity) <= OrderItem.Quantity` проверяется в
  приложении.
- `OrderItem.CancelledQuantity` не хранится и вычисляется по этим записям.
- Записи сохраняются как история отмен и не удаляются каскадно.
- См. [ADR-006](../adr/ADR-006-partial-checkout-and-cancellation.md).

### 4.12 AuditLog

Представляет append-only запись аудита.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `OccurredAtUtc` | `datetime2` | Обязательно; UTC |
| `ActorUserId` | `uniqueidentifier` | NULL; внешний ключ на `User` |
| `Action` | `nvarchar(100)` | Обязательно; например `OrderPlaced` |
| `EntityType` | `nvarchar(100)` | Обязательно |
| `EntityId` | `uniqueidentifier` | Обязательно |
| `Payload` | `nvarchar(max)` | NULL; JSON |
| `CorrelationId` | `nvarchar(100)` | NULL |

Требования:

- `AuditLog` append-only: записи не обновляются и не удаляются.
- Append-only на уровне БД: триггер `TR_AuditLog_NoUpdateDelete`
  (`INSTEAD OF UPDATE, DELETE`) бросает ошибку. Приложение не делает
  `UPDATE`/`DELETE`; триггер — защита от багов и ручных правок.
- `ActorUserId` равен null для системных действий.
- `Payload` не содержит секретов, паролей и лишних персональных данных.
- Аудит пишется после commit бизнес-операции, в отдельной транзакции.
- API чтения или изменения аудита в MVP+ отсутствует.
- `AuditLog` не удаляется каскадно вместе с пользователем, заказом или платежом.
- См. [ADR-010](../adr/ADR-010-audit.md).

## 5. Связи

Предполагаемые связи:

```text
User 1 ─── 0..1 Cart
Cart 1 ─── 0..* CartItem
Product 1 ─── 0..* CartItem

User 1 ─── 0..* Order
Order 1 ─── 1..* OrderItem
Product 1 ─── 0..* OrderItem

User 1 ─── 0..* CheckoutAttempt
Order 1 ─── 0..* CheckoutAttempt

Order 1 ─── 0..1 Payment
Payment 1 ─── 0..* Refund
OrderItem 1 ─── 0..* OrderItemCancellation
User 0..1 ─── 0..* AuditLog
User 1 ─── 0..* PaymentAttempt
Payment 0..1 ─── 0..* PaymentAttempt
```

Связь `Order` с `CheckoutAttempt` необязательна со стороны попытки, поскольку
оформление заказа может завершиться неудачно до создания заказа.

`Payment.OrderId` уникален, поэтому у заказа не более одного платежа.
`Order.PaymentId` — nullable-ссылка на `Payment`; обе стороны взаимной связи
настраиваются явно. `PaymentAttempt` ссылается на пользователя и опционально на
платёж. `AuditLog.ActorUserId` допускает null для системных действий.

Уникальность `Cart.UserId` обеспечивает не более одной корзины на пользователя.
Строка корзины создаётся при первом обращении пользователя к корзине через
`GET /api/cart`; никакая другая операция её не создаёт.

## 6. Ограничения и индексы

Схема базы данных должна обеспечивать следующие ограничения.

| Сущность | Ограничение | Назначение |
|---|---|---|
| `User` | Уникальность `Email` | Предотвращать дублирование идентичностей клиентов |
| `Product` | `Price >= 0` | Не допускать отрицательных цен |
| `Product` | `Available >= 0` | Не допускать отрицательного доступного запаса |
| `Product` | `Reserved >= 0` | Не допускать отрицательного резерва |
| `Cart` | Уникальность `UserId` | Одна корзина на пользователя |
| `CartItem` | Уникальность `(CartId, ProductId)` | Одна строка на товар в корзине |
| `CartItem` | `Quantity > 0` | Не допускать недопустимых количеств |
| `Order` | `TotalAmount >= 0` | Не допускать отрицательных сумм заказа |
| `Order` | `Status IN ('Created', 'Paid', 'Shipped', 'Delivered', 'Cancelled', 'Returned')` | Ограничивать статусы поддерживаемым набором |
| `OrderItem` | `Quantity > 0` | Не допускать недопустимых количеств в заказе |
| `OrderItem` | `UnitPrice >= 0` | Не допускать отрицательных цен покупки |
| `CheckoutAttempt` | Уникальность `(UserId, IdempotencyKey)` | Предотвращать дублирующиеся попытки идемпотентности |
| `CheckoutAttempt` | `Status IN ('InProgress', 'Completed')` | Ограничивать состояния поддерживаемым набором |
| `CheckoutAttempt` | `LeaseExpiresAtUtc IS NOT NULL` | Поддерживать восстановление по требованию |
| `Payment` | Уникальность `OrderId` | Не более одного платежа на заказ |
| `Payment` | `Amount >= 0` | Не допускать отрицательной суммы платежа |
| `Payment` | `RefundedAmount >= 0` | Не допускать отрицательного возврата |
| `Payment` | `RefundedAmount <= Amount` | Не возвращать больше суммы платежа |
| `Payment` | `Status IN ('Pending', 'Confirmed', 'Failed', 'Refunded')` | Ограничивать статусы платежа |
| `Refund` | `Amount > 0` | Не допускать нулевого или отрицательного refund |
| `PaymentAttempt` | Уникальность `(UserId, IdempotencyKey)` | Предотвращать дублирующиеся подтверждения |
| `PaymentAttempt` | `Status IN ('InProgress', 'Completed')` | Ограничивать состояния попытки |
| `PaymentAttempt` | `LeaseExpiresAtUtc IS NOT NULL` | Поддерживать восстановление по требованию |
| `OrderItemCancellation` | `Quantity > 0` | Не допускать недопустимых количеств отмены |

`AuditLog` append-only не выражается ограничением CHECK; отсутствие операций
обновления и удаления обеспечивается приложением и триггером
`TR_AuditLog_NoUpdateDelete`.

Внешние ключи должны защищать предполагаемые связи.

Дополнительные индексы должны поддерживать типичные запросы:

- Запросы активного каталога товаров.
- Поиск корзины по пользователю.
- Поиск позиций корзины по корзине.
- Поиск истории заказов по пользователю и времени создания.
- Поиск позиций заказа по заказу.
- Поиск идемпотентности по пользователю и ключу.
- Поиск платежа по заказу и refund по платежу.
- Индекс `PaymentAttempt.LeaseExpiresAtUtc`.
- Индекс `AuditLog (OccurredAtUtc)`.
- Индекс `AuditLog (EntityType, EntityId)`.
- Индекс `OrderItemCancellation (OrderItemId)`.

Сохраняйте существующие индексы: `Users.Email`, `Carts.UserId`,
`CartItems (CartId, ProductId)`, `Orders (UserId, CreatedAtUtc DESC)`,
`CheckoutAttempts (UserId, IdempotencyKey)`.

Точный порядок индексов и дополнительные включённые столбцы следует выбирать на
основе финальных шаблонов запросов. Не добавляйте предположительные индексы без
явной необходимости.

## 7. Удаление и ссылочная целостность

Физическое удаление товаров не поддерживается в MVP+.

Рекомендуемое поведение:

- Деактивируйте товары с помощью `IsActive = false`.
- Сохраняйте записи товаров, на которые ссылаются позиции корзины или позиции
  заказа.
- Удаляйте позиции корзины явно или во время успешного оформления заказа;
  checkout удаляет только выбранные позиции.
- Сохраняйте записи заказов и позиций заказа после отмены.
- Сохраняйте записи идемпотентности в течение срока, требуемого утверждённой
  политикой повторных попыток и восстановления.
- Не удаляйте каскадно `Payment`, `Refund`, `PaymentAttempt`, `AuditLog` и
  `OrderItemCancellation`.
- `AuditLog` append-only и не удаляется.
- `OrderItemCancellation` сохраняется как история отмен.

Каскадное удаление не должно случайно удалять исторические заказы, снимки
покупок или результаты идемпотентности.

Любое настроенное каскадное поведение должно явно проверяться в сопоставлениях
EF Core.

## 8. Денежные значения и расчёты заказа

Денежные значения представлены `Money` в Domain и `decimal(18,2)` в SQL Server.
`Currency` не хранится: в MVP+ все суммы — USD. См.
[ADR-003](../adr/ADR-003-money-value-object.md).

Для каждой позиции заказа:

`LineTotal = UnitPrice × Quantity`

Для заказа:

`TotalAmount = SUM(LineTotal)`

Требования:

- Используйте десятичную арифметику, а не типы с плавающей запятой, для денежных
  значений.
- Рассчитывайте общую сумму заказа по ценам за единицу и количествам на момент
  покупки.
- Сохраняйте полученную общую сумму заказа при создании заказа.
- `Payment.Amount` соответствует `Order.TotalAmount` на момент создания платежа.
- `Payment.RefundedAmount` накапливается и не превышает `Payment.Amount`;
  `SUM(Refund.Amount)` равен `Payment.RefundedAmount`.
- `Order.TotalAmount` остаётся исходным снимком и не пересчитывается при
  частичной отмене.
- Не применяйте налоги, стоимость доставки, купоны, скидки или конвертацию валют
  в MVP+.
- Проверяйте числовые границы, чтобы вычисление не переполняло молча
  поддерживаемую точность базы данных.

Точное представление на уровне приложения и числовые границы должны
соответствовать контракту API и схеме базы данных.

## 9. Транзакционные инварианты

### 9.1 Оформление заказа

Успешное оформление заказа должно атомарно:

1. Проверить текущую корзину в соответствии с утверждённой стратегией блокировки
   корзины, включая переданное значение `If-Match`.
2. Проверить активность выбранных товаров и запрошенные количества.
3. Зарезервировать только выбранные позиции: `Available -= quantity`,
   `Reserved += quantity`, атомарными условными обновлениями.
4. Создать заказ в состоянии `Created` и снимки позиций заказа, читая названия
   товаров и цены, пока строки товаров заблокированы.
5. Создать `Payment` в состоянии `Pending` и связать его с заказом через
   `Order.PaymentId`.
6. Удалить только выбранные позиции корзины; невыбранные позиции оставить.
7. Обновить строку корзины так, чтобы изменился её `rowversion`.
8. Записать завершённый результат `CheckoutAttempt` согласованно с заказом.

Если резервирование хотя бы одной выбранной позиции завершается неудачно,
транзакция оформления заказа должна откатить все бизнес-изменения: заказ,
платёж, резервы и изменения корзины не остаются частичными.

Резервирование идемпотентности может фиксироваться отдельно в соответствии с
утверждённой гибридной стратегией. Это резервирование не должно приводить к
частичному заказу или частичному резерву запаса.

### 9.2 Подтверждение платежа

Успешное подтверждение платежа должно атомарно:

1. Проверить платёж, заказ, принадлежность и идемпотентность.
2. Перевести `Payment` из `Pending` в `Confirmed`; для `Failed` выполнить retry
   `Failed → Pending → Confirmed`.
3. Уменьшить `Reserved` на оставшееся количество заказа с учётом частичной
   отмены.
4. Перевести заказ из `Created` в `Paid`.
5. Записать завершённый результат `PaymentAttempt`.

Все изменения выполняются в одной транзакции. При ошибке платёж, заказ,
`Reserved` и результат идемпотентности не остаются частично изменёнными.

### 9.3 Отмена, возврат и частичная отмена

Полная отмена до оплаты (`Created`) должна атомарно:

1. Проверить принадлежность и `If-Match` по `Order.RowVersion`.
2. Вернуть `Reserved` в `Available` для оставшихся количеств позиций заказа.
3. Перевести заказ в `Cancelled`.

Полная отмена после оплаты (`Paid`) должна атомарно:

1. Проверить принадлежность и `If-Match` по `Order.RowVersion`.
2. Создать `Refund`, увеличить `Payment.RefundedAmount` и при полном возврате
   установить `Payment.Status = Refunded`.
3. Увеличить `Available` на оставшиеся (не отменённые) количества позиций
   заказа.
4. Перевести заказ в `Cancelled`.

Возврат из `Delivered` должен атомарно:

1. Проверить принадлежность и `If-Match` по `Order.RowVersion`.
2. Создать `Refund`, увеличить `Payment.RefundedAmount` и при полном возврате
   установить `Payment.Status = Refunded`.
3. Увеличить `Available` на оставшиеся (не отменённые) количества позиций
   заказа.
4. Перевести заказ в `Returned`.

Частичная отмена должна атомарно:

1. Проверить принадлежность и `If-Match` по `Order.RowVersion`.
2. Создать записи `OrderItemCancellation`.
3. Для заказа в `Created` вернуть отменяемое количество из `Reserved` в
   `Available`; для заказа в `Paid` создать `Refund` и увеличить `Available`.
4. Не менять статус заказа, пока не отменены все количества; после полной отмены
   всех количеств перевести заказ в `Cancelled`.

`Order.RowVersion` обеспечивает оптимистическую блокировку полной и частичной
отмены. Одновременные попытки не должны восстанавливать запас или создавать
refund повторно; проигравшие попытки получают конфликт версии заказа.

### 9.4 Admin stock

Изменение запаса администратором должно атомарно установить `Available`, не
изменяя `Reserved`. Реализация должна явно выбрать один из вариантов:

- оптимистичное условное обновление
  `UPDATE Products SET Available = @new WHERE Id = @id AND Available = @old`;
- блокировку строки товара через `UPDLOCK` с последующим обновлением.

При конфликте конкурентного изменения операция не должна молча перезаписывать
чужое значение; конкретный код ошибки фиксируется в `api.md`.

### 9.5 Аудит

`AuditLog` создаётся после commit бизнес-операции, в отдельной транзакции.
Сбой записи аудита не откатывает бизнес-операцию; доставка at-most-once,
автоматический retry и outbox отсутствуют. См.
[ADR-007](../adr/ADR-007-domain-events.md) и
[ADR-010](../adr/ADR-010-audit.md).

### 9.6 Конкурентный доступ к корзине

Изменения корзины, включая `IsSelected`, и оформление заказа должны следовать
утверждённой стратегии блокировки.

`rowversion` — это токен конкурентности, а не замена явному механизму блокировки
корзины. Клиенты передают его через `If-Match`; устаревшие значения отклоняются
с `412 Precondition Failed`, а отсутствие обязательного `If-Match` — с
`428 Precondition Required`.

Строка корзины должна обновляться при каждом изменении содержимого корзины или
выбора позиций, в том числе во время оформления заказа, чтобы `rowversion` всегда
отражал логическое состояние корзины.

## 10. Рекомендации по сопоставлению EF Core

- Используйте явные конфигурации сущностей, когда они делают реляционные
  ограничения и поведение проще для проверки.
- Настраивайте точность десятичных значений явно.
- Настраивайте конвертер `Money ↔ decimal(18,2)` для денежных свойств.
- Настраивайте преобразование `OrderStatus`, `PaymentStatus` и
  `PaymentAttemptStatus` в `nvarchar(20)`.
- Настраивайте `RowVersion` с использованием поддержки rowversion в SQL Server
  для `Cart`, `Order` и `Payment`.
- Настраивайте `Product.Available` как optimistic concurrency token либо
  используйте явные SQL-обновления с проверкой `Available`; выбор должен быть
  явным и проверяемым.
- Настраивайте внешние ключи, уникальные индексы и ограничения CHECK явно.
- Используйте миграции для развития схемы.
- Не полагайтесь только на соглашения EF Core для критически важных требований
  уникальности, точности или конкурентного доступа.
- Сохраняйте видимой и тестируемой логику блокировок и условных обновлений,
  специфичную для SQL Server.
- Не используйте поставщик EF Core в памяти для утверждений о корректности
  блокировок SQL Server или поведения транзакций.

## 11. Схема миграций

Новые миграции (в порядке применения):

1. `AddOrderStatusesAndPaymentId` (этап 13) — расширяет CHECK `Order.Status` до
   шести статусов и добавляет `Order.PaymentId` (`uniqueidentifier NULL`) без FK.
2. `AddAvailableReserved` (этап 14) — заменяет `Product.StockQuantity` на
   `Available` и `Reserved`; существующий запас переносится в `Available`,
   `Reserved = 0`.
3. `AddCartItemIsSelected` (этап 15, часть 1) — добавляет `CartItem.IsSelected`
   (`bit NOT NULL DEFAULT 1`) для существующих строк.
4. `AddOrderRowVersionAndCancellations` (этап 15, часть 3) — добавляет
   `Order.RowVersion` (`rowversion NOT NULL`) и создаёт таблицу
   `OrderItemCancellations` (FK `OrderItemId → OrderItems.Id` с `Restrict`,
   CHECK `Quantity > 0`, индекс по `OrderItemId`).
5. `AddPaymentsAndRefunds` (этап 19) — создаёт `Payment` и `Refund`; добавляет FK
   `Order.PaymentId → Payment`. Выполняется после
   `AddOrderStatusesAndPaymentId`.
6. `AddPaymentAttempts` — создаёт `PaymentAttempt`; выполняется после
   `AddPaymentsAndRefunds`.
7. `AddAuditLog` — создаёт `AuditLog`.

Порядок миграций должен соответствовать зависимостям внешних ключей. FK
`Order.PaymentId → Payment` создаётся в `AddPaymentsAndRefunds`. Поле
`Order.PaymentId` уже добавлено в `AddOrderStatusesAndPaymentId`.

## 12. Будущее развитие

Следующие возможности находятся вне MVP+ и не должны добавлять таблицы или
столбцы в текущую схему:

- Outbox и гарантированная доставка событий.
- TTL резервов, cleanup и автоматическое освобождение.
- Reconciliation платежей.
- Реальный платёжный провайдер, Stripe и вебхуки.
- Частичный возврат после доставки.
- Admin UI и реальная аутентификация.

## 13. Оставшиеся детали

Решения, влияющие на схему, зафиксированы в `../DECISIONS.md` и ADR-001…ADR-010:
создание корзины при первом обращении, обработка `If-Match` и `rowversion`,
модель состояний попытки оформления заказа, формат ключа, алгоритм отпечатка,
резервы, платежи, частичная отмена и аудит.

Следующие детали реализации остаются открытыми и не влияют на контракт:

- Окончательный список индексов, выбранный по измеренным шаблонам запросов.
- Точное представление сохраняемого тела ответа при условии, что оно
  воспроизводит задокументированный ответ.

Не придумывайте детали, которые изменили бы совместимость API, безопасность
транзакций или корректность восстановления.
