# Модель предметной области

## 1. Назначение

Этот документ описывает бизнес-домен Mini E-commerce, его основные понятия,
связи, правила жизненного цикла и инварианты.

Он определяет, что приложение означает с точки зрения бизнеса, независимо от
технической реализации.

Подробное функциональное поведение определено в `SPEC.md`. Структура базы
данных определена в `architecture/data-model.md`.

## 2. Обзор предметной области

Mini E-commerce представляет собой небольшой интернет-магазин, в котором
пользователи приобретают товары с помощью корзин и заказов.

Основные понятия предметной области:

- Пользователь
- Товар
- Корзина
- Позиция корзины
- Заказ
- Позиция заказа
- Попытка оформления заказа

Система должна сохранять бизнес-согласованность при сбоях запросов или их
одновременном выполнении.

## 3. Пользователь

Пользователь представляет клиента или администратора, который может вести
корзину и создавать заказы; администратор также выполняет admin-операции.

Пользователь имеет:

- Уникальный идентификатор.
- Уникальный адрес электронной почты.
- Метку времени создания в UTC.
- Роль: `customer` или `admin`.

### Бизнес-правила

- У каждого пользователя не более одной корзины, создаваемой при первом
  обращении пользователя к ней.
- Пользователь может создавать несколько заказов со временем.
- Пользователь может получать доступ только к своей корзине и своим заказам.
- Идентичность пользователя определяется контекстом аутентифицированного
  запроса.
- Клиент не может выбрать другого пользователя в качестве владельца корзины
  или заказа, передав идентификатор пользователя.
- `admin` — третий предварительно созданный тестовый пользователь
  (`X-Test-User: admin`); роль admin доступна только в Development.
  См. [ADR-009](adr/ADR-009-admin-api-and-roles.md).

В MVP+ не входят реальная модель аутентификации, регистрация клиентов,
управление профилем или аутентификация по паролю. `X-Test-User` — осознанное
упрощение; см. `DECISIONS.md` §13. Отдельный `RATIONALE.md` будет создан позже.

## 4. Товар

Товар представляет позицию, доступную для покупки.

Товар имеет:

- Уникальный идентификатор.
- Название.
- Описание.
- Текущую цену `Price` — `Money`.
- Доступный запас `Available`.
- Зарезервированный запас `Reserved`.
- Активное или неактивное состояние.

### Бизнес-правила

- Покупать можно только активные товары.
- `Price` представлена value object `Money`; в MVP+ используется USD.
  См. [ADR-003](adr/ADR-003-money-value-object.md).
- `Available >= 0`, `Reserved >= 0`, `Price >= 0`.
- `Available` — количество, доступное для новых заказов; `Reserved` —
  количество, зарезервированное незавершёнными заказами.
  См. [ADR-005](adr/ADR-005-stock-reservations.md).
- Успешная покупка не может сделать `Available` отрицательным.
- Деактивация товара предотвращает новые покупки, но не удаляет историческую
  информацию о заказах.
- Товары, на которые ссылаются исторические заказы, не должны физически
  удаляться.
- Изменение текущей цены товара не должно изменять цену, зафиксированную в
  существующем заказе.
- Деактивация и изменение `Available` — admin-операции; они не изменяют
  `Reserved` и снимки в существующих заказах. См.
  [ADR-009](adr/ADR-009-admin-api-and-roles.md).

### Доменные операции

- `Deactivate()` — переводит товар в неактивное состояние; повторная
  деактивация идемпотентна. См. ADR-009.
- `AdjustAvailable(newAvailable)` — устанавливает абсолютное значение
  `Available`; `Reserved` не изменяется. Отрицательное значение недопустимо.
  См. ADR-009.

Текущее состояние товара и его историческое представление в заказе служат
разным целям.

## 5. Корзина

Корзина представляет текущий выбор покупок одного пользователя.

Корзина создаётся, когда пользователь впервые обращается к ней, и существует в
течение срока действия учётной записи пользователя. Она остаётся доступной
после оформления заказа.

### Бизнес-правила

- У пользователя не более одной корзины.
- Корзина создаётся при первом обращении пользователя к корзине;
  одновременные первые запросы должны по-прежнему создавать только одну
  корзину.
- Корзина принадлежит ровно одному пользователю.
- Принадлежность корзины нельзя изменить через публичные запросы API.
- Корзина может содержать ноль или более позиций корзины.
- Выбор позиций (`CartItem.IsSelected`) является частью состояния корзины и её
  версии. См. [ADR-001](adr/ADR-001-cart-concurrency.md) и
  [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md).
- Изменение выбора — мутация корзины; доменная операция «изменить выбор»
  соответствует `PUT /api/cart/selection`, HTTP-детали определены в ADR-006.
- `IsSelected` не влияет на валидность позиции: активность товара, количество и
  доступность запаса проверяются отдельно.
- Успешное оформление заказа удаляет только выбранные позиции корзины, но
  сохраняет саму корзину и невыбранные позиции.
- Успешное оформление заказа делает недействительной версию корзины, выданную
  до него, чтобы нельзя было применить одновременные операции, основанные на
  старом состоянии.
- Неудачное оформление заказа должно оставлять корзину без изменений.
- Отмена заказа не должна изменять текущую корзину.

Корзина представляет текущее намерение покупки, а не подтверждённую покупку.

## 6. Позиция корзины

Позиция корзины представляет запрошенное количество товара в корзине
пользователя.

Она связывает корзину с товаром, положительным целочисленным количеством и
признаком выбора.

### Бизнес-правила

- `IsSelected` (`bool`, по умолчанию `true`) — часть состояния позиции корзины
  и версии корзины. См. [ADR-001](adr/ADR-001-cart-concurrency.md) и
  [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md).
- Изменение `IsSelected` — мутация корзины и изменение её версии.
- `IsSelected` не влияет на валидность позиции: активность товара, количество и
  доступность запаса проверяются отдельно.
- Корзина не должна содержать дублирующиеся записи для одного и того же
  товара.
- Добавление уже присутствующего товара увеличивает его существующее
  количество.
- Обновление позиции заменяет её количество запрошенным положительным целым
  числом.
- Нулевые или отрицательные количества недопустимы.
- Удаление позиции — отдельная операция.
- Запрошенное количество не должно превышать текущий доступный запас при
  добавлении или обновлении позиции.
- Запас должен быть повторно проверен при оформлении заказа.
- Неактивный товар может оставаться в корзине.
- Неактивный товар нельзя добавить, изменить его количество или купить.
- Неактивный товар по-прежнему можно удалить из корзины.

Позиция корзины не является резервированием запаса. Доступность может
измениться до оформления заказа.

## 7. Заказ

Заказ представляет покупку, успешно созданную из корзины пользователя.

Заказ принадлежит одному пользователю и содержит одну или более позиций
заказа.

### Состояния заказа

Заказ имеет шесть статусов:

- `Created`
- `Paid`
- `Shipped`
- `Delivered`
- `Cancelled`
- `Returned`

Начальное состояние успешно созданного заказа — `Created`.
`Cancelled` и `Returned` — терминальные. Допустимые переходы определены в
[ADR-004](adr/ADR-004-order-state-machine.md).

| Из | В | Сценарий |
|---|---|---|
| `Created` | `Paid` | Подтверждение платежа |
| `Created` | `Cancelled` | Отмена до оплаты |
| `Paid` | `Shipped` | Admin ship |
| `Paid` | `Cancelled` | Отмена после оплаты с refund |
| `Shipped` | `Delivered` | Admin deliver |
| `Delivered` | `Returned` | Admin return; запас возвращается в `Available` |

### Поля и конкурентность

- `PaymentId` — nullable-ссылка на `Payment`. См.
  [ADR-008](adr/ADR-008-payments-and-idempotency.md).
- `RowVersion` используется для конкурентности полной и частичной отмены.
  См. [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md).

### Явные методы

Переходы выполняются только явными доменными методами:

- `MarkPaid()` — `Created → Paid`;
- `Ship()` — `Paid → Shipped`;
- `Deliver()` — `Shipped → Delivered`;
- `Cancel()` — `Created → Cancelled` или `Paid → Cancelled`;
- `Return()` — `Delivered → Returned`.

`MarkPaid()` требует `PaymentId != null`; иначе выбрасывается
`invalid_order_transition`. См. ADR-004.

### Бизнес-правила

- Заказ создаётся только после успешного оформления заказа.
- Заказ должен содержать как минимум одну позицию.
- Заказ принадлежит пользователю, чья корзина была оформлена.
- Общая сумма заказа рассчитывается по сохранённым ценам позиций и
  количествам.
- Неудачное оформление заказа не должно создавать частичный заказ.
- Пользователь может получать доступ только к своим заказам.
- Заказ нельзя физически удалить в рамках обычного сценария MVP+.
- Заказ в состоянии `Created` или `Paid` можно отменить.
- Полная отмена переводит заказ в `Cancelled`; частичная отмена не меняет
  статус. См. ADR-006.
- Заказ в состоянии `Cancelled` или `Returned` нельзя успешно отменить
  повторно.
- Заказ в состоянии `Shipped` или `Delivered` нельзя отменить; после доставки
  допускается только возврат. См. ADR-004.
- Отменённый заказ остаётся в истории заказов.

## 8. Позиция заказа

Позиция заказа представляет одну купленную товарную строку в заказе.

Она фиксирует ссылку на товар, название товара на момент покупки, цену за
единицу и количество.

### Бизнес-правила

- Каждая позиция заказа принадлежит одному заказу.
- Количество `Quantity` в позиции — положительное целое число и неизменяемый
  снимок; при отмене оно не уменьшается.
- Название товара копируется в позицию заказа при успешном оформлении заказа.
- Цена за единицу копируется в позицию заказа при успешном оформлении заказа.
- Существующие снимки позиций заказа не изменяются при изменении названия
  товара или текущей цены.
- Историческая информация о заказе остаётся значимой, даже если товар позже
  деактивирован.
- `OrderItemCancellation` — дочерняя сущность отмены: `Id`, `Quantity`,
  `CancelledAtUtc`, `Reason?`. См.
  [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md).
- `CancelledQuantity` вычисляется как `SUM(OrderItemCancellation.Quantity)` и не
  хранится отдельным полем.
- Инвариант: `SUM(CancelledQuantity) <= Quantity`.
- Частичная отмена не меняет статус заказа; «частично отменён» вычисляется по
  наличию записей `OrderItemCancellation`.
- Отмена и частичная отмена восстанавливают точные количества, записанные в
  позициях заказа.

Снимок позиции заказа представляет покупку в том виде, в каком она произошла,
а не текущее состояние каталога.

## 9. Оформление заказа

Оформление заказа — бизнес-операция, которая преобразует корзину пользователя
в заказ.

### Предварительные условия

- Пользователь аутентифицирован.
- Корзина принадлежит аутентифицированному пользователю.
- Корзина содержит как минимум одну выбранную позицию (`IsSelected = true`).
- Каждый выбранный товар активен.
- Для каждого выбранного количества доступен достаточный запас.
- Попытка оформления заказа удовлетворяет правилам идемпотентности.
- Если выбранных позиций нет, оформление завершается ошибкой `cart_empty`.

### Успешный результат

Успешное оформление заказа должно:

1. Проверить выбранные позиции и их товары.
2. Подтвердить текущее наличие запаса для выбранных позиций.
3. Зарезервировать выбранные количества: `Available → Reserved`.
4. Создать заказ в состоянии `Created`.
5. Сохранить снимки позиций заказа.
6. Рассчитать общую сумму заказа.
7. Создать `Payment` в состоянии `Pending` в той же транзакции. См.
   [ADR-008](adr/ADR-008-payments-and-idempotency.md).
8. Удалить только выбранные позиции из корзины; невыбранные остаются.
9. Изменить корзину так, чтобы ранее выданная версия стала недействительной.
10. Записать завершённый результат идемпотентности.

Эти изменения должны быть согласованы как одна бизнес-операция.

### Неудачный результат

Неудачное оформление заказа не должно оставлять частичных бизнес-изменений.

Если оформление заказа завершается неудачно из-за нарушения бизнес-правила:

- В результате этой неудачной попытки заказ не создаётся.
- Частичный резерв запаса не сохраняется.
- `Payment` не создаётся.
- Корзина остаётся без изменений.
- Ошибка возвращается в соответствии с контрактом API.

Если результат фиксации транзакции в базе данных неизвестен, приложение не
должно предполагать, что оформление заказа завершилось неудачно. Оно должно
определить результат с использованием того же ключа идемпотентности и
устойчивого состояния.

## 10. Попытка оформления заказа и идемпотентность

Попытка оформления заказа представляет один логический запрос на оформление
заказа, идентифицируемый ключом идемпотентности и аутентифицированным
пользователем.

### Бизнес-правила

- Ключ идентифицирует одну попытку для одного пользователя.
- Один и тот же ключ и один и тот же запрос не должны создавать несколько
  заказов.
- Повторный запрос должен возвращать сохранённый результат, если он существует.
- Повторное использование ключа с другим запросом является конфликтом.
- Новая попытка после окончательного отказа из-за нарушения бизнес-правила
  требует нового ключа.
- Одновременные запросы с одним и тем же ключом не должны запускать
  независимые выполнения оформления заказа.
- Соответствующую попытку, которая всё ещё выполняется, можно ожидать
  ограниченное время; если результат не становится доступным вовремя, запрос
  временно завершается неудачно, и клиент повторяет ту же попытку.
- Окончательные бизнес-ошибки сохраняются для повторных запросов.
- Неожиданные внутренние ошибки сервера автоматически не рассматриваются как
  окончательные бизнес-результаты.
- Попытка, оставшаяся в состоянии `InProgress`, не должна слепо выполняться
  повторно без проверки устойчивого состояния.
- Восстановление выполняется по требованию во время повторной попытки, только
  после истечения срока резервирования попытки. Фоновый процесс восстановления не
  входит в MVP+.
- Fingerprint не включает selection явно: `IsSelected` меняет `rowversion`
  корзины, а `rowversion` уже входит в `If-Match` и fingerprint.

Технические механизмы резервирования, сохранения и восстановления определены в
`adr/ADR-002-checkout-idempotency.md`; изменения для M5/M7 — в его
`## Amendments`.

## 11. Согласованность запаса и товарных остатков

Запас представлен двумя величинами: `Available` (доступно для новых заказов) и
`Reserved` (зарезервировано незавершёнными заказами). Правила переходов
определены в [ADR-005](adr/ADR-005-stock-reservations.md).

### Правила покупки и оплаты

- Checkout резервирует только выбранные позиции: `Available -= quantity`,
  `Reserved += quantity`.
- Резервирование должно быть атомарным по отношению к конкурирующим покупкам.
- Резервирование разрешено, только если `Available` достаточно.
- Если нельзя зарезервировать хотя бы одну выбранную позицию, вся
  бизнес-транзакция оформления заказа завершается неудачно.
- Payment confirm уменьшает `Reserved` на оставшееся количество заказа (с учётом
  частичной отмены): `Reserved -= quantity`; `Available` не изменяется.
- Система не должна молча принимать частичную покупку.

### Правила отмены и возврата

- Отмена до оплаты (`Created`) возвращает `Reserved` в `Available`.
- Отмена после оплаты (`Paid`) увеличивает `Available`; `Reserved` уже уменьшен
  при подтверждении платежа.
- Частичная отмена использует те же правила для отменяемого количества.
- Возврат из `Delivered` увеличивает `Available`; `Reserved` не изменяется.
- Восстановление основано на количествах позиций заказа, а не на текущей
  корзине.
- Восстановление разрешено, даже если товар сейчас неактивен.
- Отмена или возврат восстанавливают запас только один раз.
- Переход статуса заказа и изменение запаса должны быть атомарными.

### Ограничения

- Резервы не имеют TTL; фоновый cleanup, автоматическое истечение и
  «освобождение зависших резервов» не вводятся. Заказ в `Created` может
  удерживать `Reserved` неограниченно долго — это осознанное ограничение MVP+.
- Admin stock устанавливает абсолютное `Available`; `Reserved` не изменяется.
  См. [ADR-009](adr/ADR-009-admin-api-and-roles.md).

Одна только блокировка корзины не защищает общий запас товаров.
Согласованность товарных остатков требует отдельного управления конкурентным
доступом на уровне базы данных.

## 12. Бизнес-инварианты

Следующие инварианты должны всегда выполняться после успешной зафиксированной
бизнес-операции.

### Идентичность и принадлежность

1. Каждая корзина принадлежит ровно одному пользователю.
2. Каждый заказ принадлежит ровно одному пользователю.
3. Пользователи не могут получать доступ к корзине или заказу другого
   пользователя.
4. Приложение определяет принадлежность по аутентифицированной идентичности.

### Корзина

5. У пользователя не более одной корзины, и одновременные первые запросы
   создают только одну корзину.
6. Корзина содержит не более одной позиции для каждого товара.
7. Каждая позиция корзины имеет положительное целое количество.
8. Неудачные операции с корзиной не изменяют корзину частично.
9. Оформление заказа очищает только выбранные позиции корзины, не удаляя
   корзину и невыбранные позиции, и делает недействительной версию корзины,
   выданную до него.
10. Неудачное оформление заказа сохраняет корзину.

### Заказы

11. Успешно созданный заказ содержит как минимум одну позицию.
12. Количества в позициях заказа — положительные целые числа.
13. Общие суммы заказов равны сумме сохранённых цен за единицу, умноженных на
    сохранённые количества.
14. Названия и цены в позициях заказа являются историческими снимками.
15. Отменённый заказ остаётся в истории.

### Товарные остатки

16. Успешная покупка не может зарезервировать больше, чем `Available`.
17. Неудачное оформление заказа не оставляет частичных резервов.
18. Отмена или возврат восстанавливает ровно те количества, которые записаны в
    позициях заказа.
19. Суммарное восстановление запаса по заказу не превышает количеств в его
    позициях; одна и та же отмена или возврат не восстанавливает запас повторно.

### Идемпотентность и транзакции

20. Один пользователь и один ключ идемпотентности идентифицируют не более одной
    логической попытки оформления заказа.
21. Повторение запроса на оформление заказа с тем же ключом и тем же запросом
    не может создать дублирующийся заказ.
22. Повторное использование ключа с другим запросом отклоняется.
23. Оформление заказа, отмена и возврат не должны оставлять частичных
    зафиксированных бизнес-изменений.
24. Операция, основанная на устаревшей версии корзины, никогда не изменяет
    корзину после успешного оформления заказа.

### Деньги

25. `Money.Amount >= 0`, `Money.Currency == USD`.
    См. [ADR-003](adr/ADR-003-money-value-object.md).

### Статусы заказа

26. Заказ может находиться только в разрешённых состояниях и переходить только
    по разрешённым переходам. См.
    [ADR-004](adr/ADR-004-order-state-machine.md).

### Выбор позиций

27. `IsSelected` является частью версии корзины; изменение выбора изменяет
    версию корзины. См. [ADR-001](adr/ADR-001-cart-concurrency.md) и
    [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md).

### Частичная отмена

28. `SUM(OrderItem.CancelledQuantity) <= OrderItem.Quantity`.
    См. [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md).

### Резервы

29. `Available >= 0`, `Reserved >= 0`; consume и release выполняются только по
    правилам [ADR-005](adr/ADR-005-stock-reservations.md).

### Платежи

30. `Payment.Status` изменяется только по допустимым переходам, а
    `Payment.RefundedAmount <= Payment.Amount`. См.
    [ADR-008](adr/ADR-008-payments-and-idempotency.md).

### Аудит

31. `AuditLog` append-only: записи не обновляются и не удаляются. См.
    [ADR-010](adr/ADR-010-audit.md).

Эти инварианты должны защищаться логикой приложения, ограничениями базы данных,
транзакциями и средствами управления конкурентным доступом в зависимости от
ситуации.

## 13. Ошибки предметной области

Слои домена и приложения должны различать отказы из-за нарушения
бизнес-правил и неожиданные технические сбои.

Примеры отказов из-за нарушения бизнес-правил:

- Недопустимое количество в корзине.
- Товар недоступен для покупки.
- Недостаточный запас.
- Оформление заказа без выбранных позиций.
- Устаревшая версия корзины.
- Отсутствует предварительное условие версии корзины.
- Конфликтующее повторное использование ключа идемпотентности.
- Повторная отмена уже отменённого заказа.

Новые коды ошибок:

- `invalid_order_transition`;
- `payment_not_found`;
- `payment_already_confirmed`;
- `payment_failed`;
- `refund_not_allowed`;
- `order_already_shipped`;
- `insufficient_reserved`;
- `admin_forbidden`.

Полный список кодов и их HTTP-соответствие — `DECISIONS.md` §8.

API сопоставляет эти отказы с задокументированными кодами состояния HTTP и
ответами `ProblemDetails`.

Модель предметной области не должна зависеть от типов HTTP-ответов или
ASP.NET Core.

## 14. Границы предметной области

Следующие аспекты находятся вне модели предметной области для MVP+:

- Реальная аутентификация JWT/OAuth; `X-Test-User` — Development-упрощение.
- Stripe, реальные вебхуки и reconciliation; платежи в MVP+ используют
  mock-провайдер.
- Outbox, брокеры сообщений и гарантированная доставка событий.
- TTL резервов, cleanup и автоматическое освобождение.
- Уведомления.
- Промо, скидки, купоны и налоги.
- Конвертация валют.
- Реальная интеграция доставки или перевозчиков; admin ship/deliver/return
  входят в домен.
- Управление идентичностью клиентов сверх `X-Test-User`.
- Admin UI.
- Частичный возврат после доставки.
- Распределённый обмен сообщениями и согласованность между сервисами.

См. `DECISIONS.md` §13. Отдельный `RATIONALE.md` будет создан позже.

Предметная область должна оставаться небольшой и сосредоточенной на
доступности каталога, состоянии корзины, оформлении заказа, заказах, платежах,
товарных остатках, отмене, событиях и аудите.

## 15. События домена

События домена описывают уже произошедшие факты. Domain не зависит от MediatR;
публикация выполняется после commit, плоско, без цепочек и без outbox.
См. [ADR-007](adr/ADR-007-domain-events.md).

События:

- `OrderPlaced`;
- `OrderPaid`;
- `OrderShipped`;
- `OrderDelivered`;
- `OrderCancelled`;
- `OrderReturned`;
- `PaymentConfirmed`;
- `PaymentRefunded`;
- `StockAdjusted`;
- `ProductDeactivated`.

`OrderCancelled` публикуется и при полной, и при частичной отмене; payload
различает эти случаи. Доставка событий — at-most-once: при сбое handler'а
событие или audit-запись может потеряться, бизнес-операция не откатывается.

## 16. Платежи

`Payment` принадлежит заказу; у заказа не более одного `Payment`. Сумма —
`Money`. Статусы: `Pending`, `Confirmed`, `Failed`, `Refunded`.
`Failed` не терминален для retry: повторное подтверждение переводит
`Failed → Pending → Confirmed`. `Refunded` терминален.
См. [ADR-008](adr/ADR-008-payments-and-idempotency.md).

`Refund` — отдельная сущность частичного или полного возврата. Несколько
частичных refund допускаются; `Payment.RefundedAmount` накапливается, а
`Payment.Status = Refunded` устанавливается только при
`RefundedAmount == Amount`. Инвариант: `RefundedAmount <= Amount`.

Платёжный провайдер в MVP+ — mock; Stripe, реальные вебхуки и reconciliation не
входят в домен.

## 17. Аудит

`AuditLog` фиксирует действия по заказам, платежам и admin-изменениям.
Записи append-only: они не обновляются и не удаляются. Аудит создаётся через
события после commit, работает at-most-once и не является источником истины для
бизнес-состояния. См. [ADR-010](adr/ADR-010-audit.md).
