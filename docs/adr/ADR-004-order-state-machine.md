# ADR-004: State machine заказа

- **Статус:** Принято
- **Дата:** 2026-10-26

## Контекст

Сейчас заказ имеет два статуса: `Created` и `Cancelled`. Отмена разрешена только
из `Created`. Этого недостаточно для жизненного цикла с оплатой, отгрузкой,
доставкой и возвратом.

Нужно явно определить:

- допустимые статусы и переходы;
- кто и в каком сценарии выполняет переход;
- какие переходы запрещены;
- как ошибки перехода представляются в Domain;
- как статусы связаны с платежом и событиями.

При этом не нужен универсальный state machine framework: состояний и переходов
мало, они специфичны для заказа, а явные методы проще тестировать и сопровождать.

## Решение

### Статусы

Заказ имеет шесть статусов:

- `Created`
- `Paid`
- `Shipped`
- `Delivered`
- `Cancelled`
- `Returned`

`Cancelled` и `Returned` — терминальные.

### Переходы

| Из | В | Сценарий |
|---|---|---|
| `Created` | `Paid` | Подтверждение платежа (`payment confirm`) |
| `Created` | `Cancelled` | Отмена до оплаты |
| `Paid` | `Shipped` | Admin ship |
| `Paid` | `Cancelled` | Отмена после оплаты с refund |
| `Shipped` | `Delivered` | Admin deliver |
| `Delivered` | `Returned` | Admin return; запас возвращается в `Available` |

Запрещены, в частности:

- `Created → Shipped`;
- `Created → Delivered`;
- `Paid → Delivered`;
- `Shipped → Cancelled`;
- `Delivered → Cancelled`;
- любые переходы из `Cancelled` и `Returned`.

После доставки допустим только `Returned`, но не `Cancelled`.

### Явные методы и guard'ы

Переходы выполняются только явными доменными методами:

- `MarkPaid()` — `Created → Paid`;
- `Ship()` — `Paid → Shipped`;
- `Deliver()` — `Shipped → Delivered`;
- `Cancel()` — `Created → Cancelled` или `Paid → Cancelled`;
- `Return()` — `Delivered → Returned`.

Методы не являются универсальным `TransitionTo(status)`. Публичной установки
статуса быть не должно.

Если текущий статус не допускает переход, выбрасывается `DomainException` с
кодом `invalid_order_transition`. Сообщение должно позволять определить текущий
и запрошенный статус. Повторный вызов перехода из неподходящего состояния также
считается ошибкой перехода; идемпотентность повторных HTTP-запросов
обеспечивается отдельно на уровне API/платежей.

`MarkPaid()` не создаёт платёж и не выполняет платёжную логику. Он вызывается
после успешного подтверждения платежа. `Cancel()` для `Paid` не выполняет refund
сам по себе: возврат денег является частью сценария отмены по ADR-008. `Return()`
не выполняет возврат денег; он меняет статус, а возврат запаса выполняется по
ADR-005.

`MarkPaid()` требует `PaymentId != null`. Попытка перевести заказ в `Paid` без
связанного платежа выбрасывает `DomainException` с кодом
`invalid_order_transition`. Отдельный код `payment_required` не вводится:
используется существующий код ошибки перехода.

`Ship()`, `Deliver()` и `Return()` инициируются admin-сценариями. Конкретные
HTTP endpoints и их включение в состав admin API определяются отдельно
(ADR-009 и `api.md`).

### PaymentId

`Order.PaymentId` — nullable-ссылка на `Payment`. Она заполняется при создании
или подтверждении платежа в соответствии с ADR-008. Наличие `PaymentId` не
заменяет guard по статусу: переход `Created → Paid` разрешён только через
`MarkPaid()`.

До этапа 19 поле существует без FK; FK добавляется вместе с таблицей `Payment`.

### События

Имена событий фиксируются здесь; механизм публикации определяется в ADR-007:

- `OrderPlaced` — заказ создан в статусе `Created`;
- `OrderPaid` — выполнен переход в `Paid`;
- `OrderShipped` — выполнен переход в `Shipped`;
- `OrderDelivered` — выполнен переход в `Delivered`;
- `OrderCancelled` — выполнен переход в `Cancelled`;
- `OrderReturned` — выполнен переход в `Returned`.

События публикуются только после успешного перехода и успешного сохранения.
Неудачный переход событие не порождает.

### Чего не делаем

- Не вводим `PendingPayment`.
- Не вводим generic state machine, конфигурируемые графы переходов или отдельный
  движок состояний.
- Не разрешаем `Delivered → Cancelled`.
- Не добавляем отдельную таблицу истории статусов в этом ADR; история может
  фиксироваться событиями и аудитом (ADR-010).

## Последствия

### Преимущества

- Жизненный цикл заказа становится явным и проверяемым.
- Недопустимые переходы обнаруживаются в Domain, а не в контроллерах.
- Отмена из `Paid` и возврат из `Delivered` получают определённое место в
  модели.
- События привязаны к успешным переходам и имеют стабильные имена.
- Нет лишней универсальной инфраструктуры.

### Компромиссы

- `OrderStatus` расширяется с 2 до 6 значений; нужны миграция, ограничение БД и
  обновление API/тестов.
- Отмена из `Paid` требует согласования с refund в ADR-008.
- Появляются admin-сценарии `Ship`, `Deliver`, `Return`, которые нужно
  согласовать с составом admin API.
- Повторные HTTP-запросы не становятся идемпотентными только за счёт Domain;
  для этого нужны механизмы API/платежей.

### Что ломается

- Текущая логика отмены, рассчитанная только на `Created`.
- Проверки и тесты, ожидающие два статуса.
- Представления заказа и frontend, отображающие только `Created`/`Cancelled`.

## Требования к реализации

- Расширить `OrderStatus` до шести значений и синхронизировать ограничение в
  базе данных.
- Реализовать `MarkPaid()`, `Ship()`, `Deliver()`, `Cancel()`, `Return()` с
  guard'ами; не добавлять публичный setter статуса.
- Выбрасывать `DomainException` с кодом `invalid_order_transition` для
  недопустимых переходов.
- Не выполнять платёжную логику, refund или изменение запаса внутри методов
  смены статуса; эти обязанности принадлежат ADR-005 и ADR-008.
- Добавить nullable `Order.PaymentId` и согласовать его заполнение с ADR-008.
- Зафиксировать имена событий `OrderPlaced`, `OrderPaid`, `OrderShipped`,
  `OrderDelivered`, `OrderCancelled`, `OrderReturned`.
- Добавить unit-тесты на каждый разрешённый переход и на каждый запрещённый
  переход, включая повторный вызов и терминальные статусы.
- Добавить интеграционные тесты на сохранение статусов, ограничение БД и
  согласованность с платежом/отменой.
- Согласовать admin-сценарии `Ship`, `Deliver`, `Return` с ADR-009 и `api.md`.
