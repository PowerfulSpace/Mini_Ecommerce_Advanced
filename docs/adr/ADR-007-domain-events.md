# ADR-007: Domain events

- **Статус:** Принято
- **Дата:** 2026-10-26

## Контекст

Заказам, платежам и admin-изменениям нужны события для аудита и будущих
уведомлений. Сейчас доменной событийной модели нет. При этом Domain не должен
зависеть от MediatR, а бизнес-операция не должна откатываться из-за сбоя
обработчика аудита.

Нужно определить:

- где определяются события;
- когда они публикуются;
- как Domain остаётся независимым от MediatR;
- какие события существуют;
- что происходит при сбое handler'а;
- почему не используется outbox.

## Решение

### Определение событий

Domain определяет доменные события как обычные неизменяемые `record`/`class` и
не ссылается на MediatR.

Application оборачивает доменное событие в `INotification`-обёртку, например
`DomainEventNotification<T>`, и публикует её через MediatR. Доменное событие
само не реализует `INotification`.

### Публикация после Commit

События публикуются только после успешного commit транзакции, а не после
`SaveChanges` и не до commit.

Если commit не состоялся, события не публикуются. Если commit состоялся, но
публикация или handler упали, бизнес-операция остаётся закоммиченной.

### Список событий

- `OrderPlaced`
- `OrderPaid`
- `OrderShipped`
- `OrderDelivered`
- `OrderCancelled`
- `OrderReturned`
- `PaymentConfirmed`
- `PaymentRefunded`
- `StockAdjusted` (admin)
- `ProductDeactivated` (admin)

`OrderCancelled` публикуется как для полной, так и для частичной отмены.
Payload различает полную и частичную отмену и содержит отменённые позиции или
количества. Отдельное событие `OrderPartiallyCancelled` не вводится.

События публикуются в порядке их возникновения в рамках операции. Отдельных
гарантий порядка между разными handler'ами нет.

### Обработчики

Handlers используются для:

- аудита (ADR-010);
- будущих уведомлений.

Handler'ы не должны порождать новые доменные события. Цепочки
«событие → событие» запрещены. Один handler не должен вызывать бизнес-команды,
которые снова публикуют события.

### At-most-once и отсутствие outbox

В MVP+ используется at-most-once:

- событие публикуется после commit;
- handler выполняется без outbox и без повторной доставки;
- если handler упал, событие/аудит теряется;
- бизнес-операция не откатывается;
- автоматический retry не выполняется.

Outbox, брокеры сообщений и гарантированная доставка не вводятся.

### Что не является событием

События не являются механизмом выполнения платежей и резервов. Подтверждение
платежа, уменьшение `Reserved`, резерв при checkout, отмена и возврат запаса
являются частью основной транзакции и не должны зависеть от асинхронных
handler'ов.

## Последствия

### Преимущества

- Domain остаётся независимым от MediatR.
- Аудит и будущие уведомления отделены от бизнес-операций.
- Сбой handler'а не ломает уже закоммиченную бизнес-операцию.
- Нет лишней инфраструктуры outbox и брокера сообщений.
- Список событий стабилен и может использоваться в аудите.

### Компромиссы

- Событие или аудит может потеряться при сбое handler'а.
- Нет гарантии доставки и повторной обработки.
- Нет строгого порядка между handler'ами.
- Будущие уведомления не могут полагаться на гарантированную доставку.
- При росте требований к надёжности потребуется outbox или другой механизм.

### Что не делаем

- Не используем outbox.
- Не добавляем брокеры сообщений.
- Не делаем цепочки событий.
- Не публикуем события до commit.
- Не откатываем бизнес-операцию из-за ошибки handler'а.
- Не используем события для платежей и резервов.

## Требования к реализации

- Определить доменные события в Domain как plain `record`/`class` без ссылок на
  MediatR.
- Реализовать в Application `INotification`-обёртку и публикацию через MediatR.
- Собирать события в рамках операции и публиковать их только после успешного
  commit.
- Не публиковать события при откате транзакции.
- Зафиксировать имена событий из списка выше.
- Реализовать handlers аудита и не допускать публикацию новых событий из
  handler'ов.
- Обеспечить at-most-once: без outbox, без retry, без отката бизнес-операции при
  сбое handler'а.
- Для `OrderCancelled` передавать признак полной/частичной отмены и сведения об
  отменённых позициях.
- Добавить тесты на:
  - публикацию после commit;
  - отсутствие публикации при rollback;
  - потерю события при сбое handler'а без отката бизнес-операции;
  - отсутствие цепочек событий;
  - имена и состав событий.
