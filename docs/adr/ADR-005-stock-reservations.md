# ADR-005: Резервы стока

- **Статус:** Принято
- **Дата:** 2026-10-26

## Контекст

Сейчас запас товара хранится в одном поле `Product.StockQuantity`. Checkout
уменьшает его, а отмена восстанавливает. Этого недостаточно, когда заказ
создаётся до оплаты: нужно отличать товар, который уже обещан конкретному
заказу, от товара, доступного для новых покупок.

Нужно также определить, что происходит с запасом при:

- частичном checkout;
- подтверждении платежа;
- отмене до и после оплаты;
- возврате после доставки;
- изменении запаса администратором.

При этом в MVP+ не вводятся TTL резервов, фоновый cleanup и автоматическое
истечение резервов.

## Решение

### Поля и инварианты

`Product.StockQuantity` заменяется двумя полями:

- `Product.Available` — количество, доступное для новых заказов;
- `Product.Reserved` — количество, зарезервированное незавершёнными заказами.

Инварианты:

- `Available >= 0`;
- `Reserved >= 0`;
- оба значения изменяются атомарно в рамках соответствующей транзакции.

Отдельного поля «общий запас» не вводится.

### Переходы запаса

| Событие | `Available` | `Reserved` |
|---|---|---|
| Checkout выбранных позиций | `-= quantity` | `+= quantity` |
| Payment confirm | без изменений | `-= quantity` (consumed) |
| Cancel до оплаты (`Created`) | `+= quantity` | `-= quantity` |
| Cancel после оплаты (`Paid`) | `+= quantity` | без изменений (уже consumed) |
| Returned из `Delivered` | `+= quantity` | без изменений |

`Reserved` при payment confirm уменьшается и не возвращается в `Available`:
товар считается проданным. При отмене после оплаты `Reserved` уже не содержит
это количество, поэтому возвращается только `Available`; возврат денег
выполняется по ADR-008.

Частичная отмена использует те же правила для отменяемого количества. Детали
инвариантов и модели данных частичной отмены определяются в ADR-006.

### Checkout

Checkout резервирует только выбранные позиции корзины, внутри транзакции
оформления заказа. Для каждой выбранной позиции атомарно:

```sql
UPDATE Products
SET Available = Available - @Quantity,
    Reserved  = Reserved  + @Quantity
WHERE Id = @ProductId
  AND Available >= @Quantity
```

Приложение проверяет количество затронутых строк. Если хотя бы одна позиция не
может быть зарезервирована, вся транзакция checkout откатывается: заказ не
создаётся, резервы не остаются.

Невыбранные позиции не резервируются и остаются в корзине.

### Payment confirm

Подтверждение платежа атомарно уменьшает `Reserved` на количество позиций
заказа:

```sql
UPDATE Products
SET Reserved = Reserved - @Quantity
WHERE Id = @ProductId
  AND Reserved >= @Quantity
```

Уменьшение `Reserved` и переход заказа в `Paid` должны происходить в одной
транзакции. Если заказ уже оплачен или отменён, повторное списание `Reserved`
недопустимо; защита обеспечивается статусом заказа и идемпотентностью платежей
по ADR-008.

### Отмена

**До оплаты (`Created`):** отмена возвращает зарезервированное количество в
доступный запас:

```sql
UPDATE Products
SET Reserved  = Reserved  - @Quantity,
    Available = Available + @Quantity
WHERE Id = @ProductId
  AND Reserved >= @Quantity
```

**После оплаты (`Paid`):** `Reserved` уже уменьшен при payment confirm, поэтому
отмена увеличивает только `Available`:

```sql
UPDATE Products
SET Available = Available + @Quantity
WHERE Id = @ProductId
```

Возврат денег при отмене после оплаты выполняется по ADR-008 и не является
частью изменения запаса.

Повторная отмена не должна возвращать запас второй раз. Переход статуса
заказа и изменение запаса должны быть атомарными; конкурентные попытки отмены
сериализуются условным переходом статуса и блокировками.

### Возврат после доставки

`Returned` из `Delivered` возвращает количество в `Available`:

```sql
UPDATE Products
SET Available = Available + @Quantity
WHERE Id = @ProductId
```

`Reserved` не изменяется. Возврат денег при `Returned` в этом ADR не
определяется; если он потребуется, это должно быть согласовано с ADR-008.

### Admin stock

`POST /api/admin/products/{id}/stock` устанавливает абсолютное значение
`Available`:

- `Available >= 0`;
- `Reserved` не изменяется;
- операция должна быть атомарной и не терять конкурентные изменения
  `Available`.

Нельзя перезаписывать `Reserved` или вычислять его из `Available`. Для защиты
от потерянных обновлений используется блокировка строки товара или эквивалентный
атомарный механизм.

### Отсутствие TTL и cleanup

Резервы не имеют TTL. Фоновый cleanup, автоматическое истечение и
«освобождение зависших резервов» не вводятся.

Резерв не считается «зависшим», пока заказ не завершён (`Cancelled`/`Returned` —
терминальные, резерв освобождён/consumed). Заказ в `Created` может удерживать
`Reserved` неограниченно долго — это осознанное ограничение MVP+. TTL, cleanup,
background service — вне MVP+.

## Последствия

### Преимущества

- Появляется различие между доступным и уже обещанным товаром.
- Checkout не продаёт один и тот же товар дважды.
- Payment confirm, отмена и возврат имеют явные правила изменения запаса.
- Частичная отмена может вернуть ровно отменяемое количество.
- Admin stock не смешивается с резервами.

### Компромиссы

- `StockQuantity` и все обращения к нему должны быть заменены.
- Checkout, оплата, отмена, возврат и admin stock становятся сложнее.
- Без TTL неоплаченный заказ может удерживать товар неограниченно долго.
- Нужны атомарные SQL-обновления и тесты на конкурентность.
- Нужна миграция данных из `StockQuantity` в `Available`/`Reserved`.

### Что ломается

- Существующая логика checkout, списывающая `StockQuantity`.
- Существующая логика отмены, восстанавливающая `StockQuantity`.
- Admin-операции, которые работали с одним полем запаса.
- Тесты и запросы, ожидающие `StockQuantity`.

### Что не делаем

- TTL резервов, cleanup, background service.
- Резервирование при добавлении товара в корзину. Резерв создаётся только на
  checkout.
- Автоматическую отмену неоплаченных заказов по таймауту.
- Отдельное поле общего запаса.
- Возврат денег внутри ADR-005; это граница ADR-008.

## Требования к реализации

- Заменить `Product.StockQuantity` на `Available` и `Reserved`; добавить
  ограничения `Available >= 0` и `Reserved >= 0`.
- Мигрировать существующие значения `StockQuantity` в `Available`, а `Reserved`
  инициализировать нулём.
- Выполнять резерв, consume, отмену и возврат атомарными условными
  обновлениями; проверять количество затронутых строк.
- Захватывать строки товаров в стабильном порядке, предпочтительно по
  `ProductId`, чтобы снизить риск взаимоблокировок.
- Выполнять checkout-резерв, payment confirm, отмену и возврат в
  соответствующих транзакциях; не оставлять частично изменённый запас.
- Не допускать повторного consume или повторного возврата запаса.
- Для admin stock использовать абсолютное `Available`, не трогать `Reserved` и
  защищаться от потерянных обновлений.
- Добавить тесты на:
  - успешный и неуспешный резерв;
  - конкурентную борьбу за последний товар;
  - payment confirm и повторный confirm;
  - отмену до и после оплаты;
  - частичную отмену;
  - возврат из `Delivered`;
  - admin stock;
  - отсутствие отрицательных `Available`/`Reserved`.
