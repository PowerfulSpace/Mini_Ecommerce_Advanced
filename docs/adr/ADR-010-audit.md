# ADR-010: Аудит

- **Статус:** Принято
- **Дата:** 2026-10-26

## Контекст

Для заказов, платежей и admin-изменений нужен минимальный аудит: кто, что и
когда сделал. Аудит должен быть отделён от бизнес-операций и не откатывать их
при сбое записи.

В MVP+ нет outbox и гарантированной доставки событий. Нужно явно принять
at-most-once и задокументировать, что при сбое handler'а аудит может потеряться.

## Решение

### AuditLog

Таблица `AuditLog`:

- `Id`;
- `OccurredAtUtc`;
- `ActorUserId?` (`null` для system);
- `Action` (`string`, например `OrderPlaced`);
- `EntityType`;
- `EntityId`;
- `Payload` (`json`, опционально);
- `CorrelationId?`.

`AuditLog` — append-only: записи не обновляются и не удаляются.

### Что аудируется

Минимальный набор:

- заказы;
- платежи;
- admin-изменения.

Корзина не аудируется: это слишком шумно и не входит в минимальный набор.

Действия соответствуют событиям ADR-007:

- `OrderPlaced`;
- `OrderPaid`;
- `OrderShipped`;
- `OrderDelivered`;
- `OrderCancelled`;
- `OrderReturned`;
- `PaymentConfirmed`;
- `PaymentRefunded`;
- `StockAdjusted`;
- `ProductDeactivated`.

Для частичной отмены `OrderCancelled` содержит в `Payload` сведения об
отменённых позициях/количествах и признак полной/частичной отмены.

### Actor

- Для действий пользователя `ActorUserId` — аутентифицированный пользователь.
- Для admin-действий — admin-пользователь.
- Для системных действий — `null`.

`CorrelationId` опционален и может использоваться для связи записей с запросом.

### Транзакции и at-most-once

Audit handler выполняется после commit бизнес-операции, в отдельной транзакции.

- Если handler аудита упал, запись аудита теряется.
- Бизнес-операция уже закоммичена и не откатывается.
- Автоматический retry не выполняется.
- Outbox не используется.

Это осознанный at-most-once. Аудит не является источником истины для бизнес-
состояния и не должен использоваться для восстановления заказа или платежа.

### Ограничения

- Нет гарантии доставки audit-записи.
- Нет фонового восстановления потерянных audit-записей.
- Нет API чтения или изменения аудита в MVP+.
- `Payload` не должен содержать секреты, пароли, платёжные данные или лишние
  персональные данные.

## Последствия

### Преимущества

- Появляется минимальная история действий по заказам, платежам и admin-
  изменениям.
- Аудит не влияет на успешность бизнес-операции.
- Append-only упрощает модель.
- Нет зависимости от outbox и брокеров.

### Компромиссы

- При сбое handler'а аудит теряется.
- Нет гарантированного порядка и доставки.
- Нет пользовательского интерфейса и API аудита.
- Для восстановления истории нельзя полагаться только на AuditLog.

### Что не делаем

- Не вводим outbox.
- Не добавляем retry или background recovery.
- Не аудируем корзину.
- Не добавляем update/delete для AuditLog.
- Не добавляем API аудита.
- Не используем AuditLog как источник истины для бизнес-решений.

## Требования к реализации

- Добавить append-only таблицу `AuditLog` с полями из этого ADR.
- Реализовать handler событий ADR-007, который пишет AuditLog в отдельной
  транзакции после commit.
- Заполнять `ActorUserId` пользователем, admin или `null` для system.
- Записывать `Action`, `EntityType`, `EntityId`, `OccurredAtUtc`, опциональные
  `Payload` и `CorrelationId`.
- Не аудировать корзину.
- Не откатывать бизнес-операцию при ошибке аудита и не выполнять retry.
- Не добавлять update/delete и API аудита.
- Добавить тесты на:
  - запись аудита для заказов, платежей и admin-изменений;
  - частичную отмену в `Payload`;
  - отсутствие аудита корзины;
  - потерю audit-записи при сбое handler'а без отката бизнес-операции;
  - append-only поведение.
