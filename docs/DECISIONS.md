# Архитектурные и продуктовые решения

Этот документ обобщает ключевые решения для MVP+ Mini E-commerce. Подробное
поведение в части конкурентности и идемпотентности определено в
соответствующих документах ADR.

## 1. Архитектура

- Использовать .NET 10 и ASP.NET Core Controllers.
- Следовать Clean Architecture с проектами Domain, Application, Infrastructure и API.
- Использовать MediatR для команд, запросов и поведений конвейера.
- Использовать SQL Server и Entity Framework Core для сохранения данных.
- Использовать FluentValidation для валидации запросов и валидации на уровне
  приложения.
- Использовать xUnit и NSubstitute для автоматизированных тестов.
- Держать бизнес-правила в Domain и Application, а не в контроллерах API.
- Отдельный проект `Common` в MVP+ не вводится. Общие типы остаются в слое,
  которому они принадлежат.
- Денежные значения в Domain представлены value object `Money` (USD,
  `decimal(18,2)`); см. [ADR-003](adr/ADR-003-money-value-object.md).
- `Money` допускает отрицательные `Amount`; неотрицательность — инвариант
  сущностей. См. [ADR-003](adr/ADR-003-money-value-object.md) (уточнение
  этапа 12).
- Жизненный цикл заказа — явная state machine из шести статусов; см.
  [ADR-004](adr/ADR-004-order-state-machine.md).
- `Order.PaymentId` — nullable `uniqueidentifier` с FK на `Payment`; введён на
  этапе 13, FK добавлен миграцией `AddPaymentsAndRefunds` на этапе 19. См.
  [data-model.md](architecture/data-model.md) §4.5, §11.
- `Payment` и `Refund` — доменные сущности, `PaymentAttempt` — инфраструктурная
  сущность идемпотентности; `IPaymentProvider` (mock) определён в Application и
  реализован в Infrastructure. См.
  [ADR-008](adr/ADR-008-payments-and-idempotency.md),
  [data-model.md](architecture/data-model.md) §4.8–4.10.
- Запас хранится как `Available` + `Reserved`; см.
  [ADR-005](adr/ADR-005-stock-reservations.md).
- Частичный checkout и частичная отмена определены в
  [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md).
- `Order.RowVersion` — shadow property EF (не публичное свойство Domain), как
  `Cart.RowVersion`; используется для `If-Match` на отмене. См.
  [ADR-006](adr/ADR-006-partial-checkout-and-cancellation.md),
  [data-model.md](architecture/data-model.md) §4.5.
- Доменные события публикуются через MediatR после commit, без outbox; см.
  [ADR-007](adr/ADR-007-domain-events.md).
- Платежи и их идемпотентность определены в
  [ADR-008](adr/ADR-008-payments-and-idempotency.md).
- Admin API и роль admin определены в
  [ADR-009](adr/ADR-009-admin-api-and-roles.md).
- `User.Role` — `Customer`/`Admin`, конвертер lowercase, CHECK
  `IN ('customer', 'admin')`, default `'customer'`; admin seed —
  `admin@example.com`. См. [ADR-009](adr/ADR-009-admin-api-and-roles.md),
  [data-model.md](architecture/data-model.md) §4.1.
- Аудит через события определён в [ADR-010](adr/ADR-010-audit.md).

### 1.1 Структура репозитория и именование

- Все имена backend- и тестовых проектов используют намеренный префикс `PS.`
  (`PS.MiniEcommerce.*`). Префикс сохраняется в именах проектов, пространствах
  имён и путях.
- Backend располагается в `src/Backend/PS.MiniEcommerce/`.
- Файл решения — `src/Backend/PS.MiniEcommerce/PS.MiniEcommerce.slnx`. Он
  использует формат `.slnx`, остаётся вложенным в каталог backend и не
  переносится в корень репозитория.
- Проекты backend: `PS.MiniEcommerce.Domain`, `PS.MiniEcommerce.Application`,
  `PS.MiniEcommerce.Infrastructure` и `PS.MiniEcommerce.API`.
- Автоматизированные тесты располагаются в `tests/PS.MiniEcommerce.UnitTests` и
  `tests/PS.MiniEcommerce.IntegrationTests`.
- `PS.MiniEcommerce.Common` не входит в согласованную структуру и удаляется на
  этапе 1. Не создавать, не ссылаться и не расширять проект `Common`.
- `CheckoutAttempt` и `CheckoutAttemptStatus` относятся к инфраструктуре, а не
  к сущностям предметной области. Сущность, её конфигурация сохранения и
  перечисление статусов находятся в `PS.MiniEcommerce.Infrastructure.Persistence`.
  Слой Application взаимодействует с идемпотентностью через
  `ICheckoutAttemptRepository` и запись `CheckoutAttemptData`.

### 1.2 Инструменты сборки и конфигурации

- `global.json` и `Directory.Packages.props` обязательны и добавляются на
  этапе 1 вместе с `Directory.Build.props`.
- Строки подключения никогда не коммитятся в репозиторий. Конкретные источники
  строк подключения, используемые во время выполнения, на этапе проектирования
  и в тестах, описаны далее в этом разделе.
- System.Security.Cryptography.Pkcs закреплён на версии 9.0.21 (транзитивная
  зависимость от Microsoft.Data.SqlClient через
  Microsoft.EntityFrameworkCore.SqlServer) для устранения CVE-2026-84008.
  Пересмотреть, когда Microsoft.Data.SqlClient обновит свою зависимость.
- Навигационные свойства Cart.Items и Order.Items настроены явно с помощью
  HasMany(x => x.Items) и UsePropertyAccessMode(PropertyAccessMode.Field), чтобы
  избежать теневых внешних ключей (OrderId1), которые EF Core иначе создал бы
  для свойств коллекций только для чтения.
- Сущности предметной области генерируют свои идентификаторы Guid в домене
  (Guid.NewGuid()). Свойство Id каждой сущности настроено с
  ValueGeneratedNever(), чтобы EF Core рассматривал сущность, добавленную через
  отслеживаемую навигацию коллекции, как Added. Без этого EF Core помечает
  дочернюю сущность с ключом, заданным приложением, добавленную к
  отслеживаемому родителю, как Modified, и SaveChanges завершается с
  DbUpdateConcurrencyException, поскольку выдаёт UPDATE для ещё не существующей
  строки.
- Папки функциональных областей Application используют имена во множественном
  числе (Products, Carts, Orders), чтобы избежать неоднозначности между
  пространством имён и типом: PS.MiniEcommerce.Application.Cart (пространство
  имён) и PS.MiniEcommerce.Domain.Cart (тип).
- Миграции на этапе проектирования читают строку подключения из переменной
  окружения MINIECOMMERCE_DB через AppDbContextFactory. Среда выполнения в
  режиме разработки читает ConnectionStrings:Default из
  appsettings.Development.json в проекте API (не коммитится; находится в
  .gitignore; в репозитории есть appsettings.Development.example.json).
  Интеграционные тесты читают MINIECOMMERCE_TEST_DB из окружения.
- Документация API использует Swashbuckle.AspNetCore для Swagger UI.
  Microsoft.AspNetCore.OpenApi удалён, поскольку у него нет интерактивного
  интерфейса, необходимого для ручной проверки на этапе 4 и последующих этапах.
- AddProblemDetails() регистрируется, чтобы удовлетворить требование
  UseExceptionHandler() к IProblemDetailsService. Исключения домена и
  приложения сначала обрабатываются пользовательским IExceptionHandler;
  встроенная служба ProblemDetails служит запасным вариантом для необработанных
  исключений.
- Ответы ProblemDetails включают поле расширения со стабильным кодом,
  определённое в architecture/api.md §4.1. Для validation_error и not_found код
  задаётся ExceptionHandler.
- NotFoundException содержит свойство Code. По умолчанию оно равно not_found и
  устанавливается в product_not_found для запросов каталога.
  DomainConflictException содержит аналогичное свойство Code. По умолчанию оно
  равно conflict и устанавливается в конкретные коды (cart_version_conflict,
  precondition_required, insufficient_stock, product_unavailable) обработчиками
  приложения; ExceptionHandler сопоставляет cart_version_conflict с 412, а
  precondition_required — с 428. IAuthorizationMiddlewareResultHandler
  возвращает ProblemDetails с code = unauthenticated для 401 и code = forbidden
  для 403. Это заменяет примечание «открытое решение для этапа 4».
- If-Match должен содержать один сильный тег сущности в форме "<base64>".
  Отсутствующее значение возвращает 428 precondition_required. Подстановочный
  знак (*) или некорректное (не Base64) значение отклоняются как 400
  validation_error. Значение, которое разбирается как Base64, но не совпадает с
  текущим rowversion корзины, возвращает 412 cart_version_conflict.
- Срок резервирования попытки оформления заказа составляет 30 секунд (см.
  раздел 10). Срок резервирования устанавливается в момент создания
  резервирования (LeaseExpiresAtUtc = utcNow + 30s) и используется для
  восстановления по требованию (TryClaimExpiredAsync), как описано ниже в этом
  документе.
- Отпечаток запроса для идемпотентности оформления заказа — это 32-байтовый хеш
  SHA-256, вычисляемый контроллером API по целевому адресу запроса и переданному
  значению If-Match. Он хранится как varbinary(32) и сравнивается побайтово.
- Сообщения FluentValidation закреплены за InvariantCulture: AddApplication
  устанавливает ValidatorOptions.Global.LanguageManager.Culture в
  CultureInfo.InvariantCulture, а Program.cs устанавливает культуру потока по
  умолчанию для хоста API в InvariantCulture. Тестовая сборка также
  устанавливает культуру менеджера языков, поскольку модульные тесты не
  запускают хост API.
- Аутентификация только для разработки использует заголовок X-Test-User со
  значениями alice, bob и admin. Обработчик определяет UserId предварительно
  созданного пользователя из базы данных и помещает его в утверждение sub. Схема
  регистрируется только в Development; в Production она недоступна. Значение
  admin даёт роль admin только для Development admin endpoints (ADR-009).
- Политика CORS Frontend разрешает http://localhost:5173 (сервер разработки
  Vite) с любыми заголовками и любым методом. Политика регистрируется
  безусловно; источники для Production выходят за рамки MVP+.
- Непрерывная интеграция отложена за пределы MVP+.
- `TreatWarningsAsErrors` и анализаторы стиля кода не включены; текущая сборка
  проходит без предупреждений. Включение — отдельное решение, зафиксированное вне
  MVP+.
- `Microsoft.AspNetCore.Mvc.Testing` входит в утверждённый стек тестирования и
  используется проектом интеграционных тестов.
- Ограниченное ожидание (3 секунды, опрос каждые 100 мс) реализовано в
  ICheckoutAttemptRepository.WaitForCompletionAsync. Одновременные запросы с
  одним и тем же ключом идемпотентности ожидают завершения активной попытки и
  воспроизводят её результат либо возвращают 503 idempotency_in_progress по
  тайм-ауту. Это устраняет прежнее отклонение от ADR-002. Восстановление
  устаревшего резервирования по требованию реализовано в CheckoutHandler: когда
  ограниченное ожидание истекает и срок резервирования попытки истёк, обработчик
  захватывает попытку посредством условного обновления (TryClaimExpiredAsync) и
  возобновляет оформление заказа. Одновременные попытки захвата сериализуются
  условным обновлением; продолжает только победитель.
- `PaymentAttempt` хранится в Infrastructure отдельно от `CheckoutAttempt` и
  покрывает confirm и refund; см.
  [ADR-008](adr/ADR-008-payments-and-idempotency.md).
- Гонка между восстановлением и уже выполняющимся оформлением заказа
  разрешается условным обновлением записи идемпотентности (ExecuteUpdateAsync
  WHERE Status = 'InProgress') в CheckoutTransactionExecutor. Завершить попытку
  может только один исполнитель; проигравшие откатывают свою транзакцию и
  воспроизводят результат победителя. Неизвестные результаты фиксации
  (исключения из SaveChangesAsync или CommitAsync) представляются как
  CheckoutCommitUncertainException и сопоставляются с 503
  idempotency_in_progress без сохранения окончательной ошибки.
- Неизвестные результаты фиксации (исключения из SaveChangesAsync или
  CommitAsync после начала транзакции) сопоставляются с 503
  idempotency_in_progress через CheckoutCommitUncertainException.

## 2. Каталог и ценообразование

- Каталог доступен для чтения; admin endpoints предоставляются только в
  Development и требуют роль admin (ADR-009).
- Эндпоинты каталога публичны и не требуют аутентификации.
- Эндпоинты каталога возвращают только активные товары.
- Неактивные товары нельзя добавить в корзину, обновить в корзине или оформить.
- Неактивные товары, уже находящиеся в корзине, остаются видимыми как
  недоступные, и их можно удалить.
- Товары деактивируются через `IsActive = false`; физическое удаление не
  поддерживается.
- Запас товара хранится как `Available` и `Reserved`; `StockQuantity` не
  используется (ADR-005).
- Admin stock устанавливает абсолютное `Available >= 0`; `Reserved` не
  изменяется.
- Цены используют value object `Money` в USD и SQL Server `decimal(18,2)`
  (ADR-003).
- Суммы корзины используют текущие цены каталога.
- Позиции заказа сохраняют снимки названия товара и цены за единицу на момент
  оформления заказа.
- Список товаров разбивается на страницы с использованием общих параметров
  списка, определённых в разделе 10.

## 3. Принадлежность корзины и жизненный цикл

- У пользователя может быть не более одной корзины и несколько заказов.
- Корзина создаётся при первом обращении во время `GET /api/cart`, когда у
  пользователя её ещё нет.
- Изменения корзины и оформление заказа никогда не создают корзину; они требуют
  существующую корзину и возвращают `404` с кодом `cart_not_found`, если её нет.
- Корзина остаётся после оформления заказа; успешное оформление удаляет только
  выбранные позиции, а не саму корзину.
- `CartItem.IsSelected` по умолчанию `true`; выбор меняется через
  `PUT /api/cart/selection` и является изменением корзины.
- `GET /api/cart` возвращает `isSelected`, `totalAmount` и
  `selectedTotalAmount`.
- Принадлежность корзины определяется контекстом аутентифицированного
  пользователя, а не идентификатором пользователя, переданным клиентом.
- В Development используется заголовок `X-Test-User` для предварительно
  созданных пользователей `alice`, `bob` и `admin`.
- Механизм аутентификации для разработки не должен быть включён в Production;
  admin endpoints также доступны только в Development.
- Количества в корзине должны быть положительными целыми числами. Нулевые и
  отрицательные значения отклоняются; для удаления позиции используется
  эндпоинт DELETE.
- Добавление товара, уже находящегося в корзине, увеличивает его количество.
- Операции с корзиной отклоняют количества, превышающие доступный запас;
  количества не усекаются молча.
- Неудачные операции с корзиной не должны частично изменять корзину.

## 4. Конкурентность корзины

Стратегия конкурентного доступа к корзине определена в
[ADR-001](adr/ADR-001-cart-concurrency.md).

- Каждое изменение корзины и оформление заказа выполняются в транзакции базы
  данных.
- Изменения корзины и оформление заказа явно блокируют хранимую строку корзины
  на время транзакции.
- Реализация должна использовать SQL Server `UPDLOCK` или эквивалентный явный
  механизм; нельзя предполагать, что обычные LINQ-запросы EF Core обеспечивают
  эту блокировку.
- SQL Server `rowversion` строки корзины возвращается клиентам как HTTP `ETag` в
  представлениях корзины и передаётся обратно через заголовок запроса `If-Match`.
  Значение `ETag` — это Base64-кодирование 8-байтового `rowversion`.
- Изменения корзины и оформление заказа должны включать `If-Match`. Отсутствие
  обязательного `If-Match` возвращает `428 Precondition Required`. Несовпадающее
  значение возвращает `412 Precondition Failed` с кодом `cart_version_conflict`.
- `PUT /api/cart/selection` изменяет `CartItem.IsSelected`, требует `If-Match`,
  сериализуется блокировкой корзины и меняет `rowversion` корзины.
- Checkout читает, резервирует и очищает только выбранные позиции в одной
  транзакции; невыбранные позиции остаются без резерва.
- Проверка версии никогда не повторяется автоматически для более нового
  состояния корзины.
- Успешные изменения корзины возвращают обновлённую корзину и её новый `ETag`.
- Блокировка корзины сериализует операции с одной корзиной; `rowversion`
  обеспечивает дополнительную защиту от устаревших запросов.
- Успешное оформление заказа должно изменить строку корзины в той же транзакции,
  чтобы ранее выданный `ETag` стал недействительным. Одновременное изменение
  корзины с устаревшим `ETag` не должно возвращать старые позиции корзины после
  фиксации оформления заказа.

## 5. Согласованность запаса

- Блокировка корзины не защищает запас, общий для разных пользователей.
- Запас хранится как `Available` и `Reserved`; инварианты `Available >= 0` и
  `Reserved >= 0` (ADR-005).
- Checkout выбранных позиций атомарно переносит количество из `Available` в
  `Reserved`.
- Подтверждение платежа списывает `Reserved`; заказ переходит в `Paid`.
- Отмена `Created` возвращает `Reserved` в `Available`; отмена `Paid`
  возвращает количество в `Available` и выполняет refund по ADR-008.
- Возврат после доставки возвращает количество в `Available`.
- TTL, cleanup и фоновое освобождение резервов не реализуются; `Created` может
  удерживать `Reserved` неограниченно долго.
- Admin stock устанавливает абсолютное `Available >= 0` и не изменяет
  `Reserved`.
- Резервирование и изменение запаса используют атомарные условные обновления
  базы данных и проверку количества затронутых строк.
- Все изменения запаса при checkout относятся к одной транзакции.
- Если какое-либо резервирование завершается неудачно, checkout откатывается
  полностью: заказ не создаётся, изменения запаса отменяются, корзина остаётся
  без изменений.
- Ошибки недостаточного запаса идентифицируют все затронутые товары по
  идентификатору и названию, прочитанным после отката неудачной транзакции
  оформления заказа. После ответа с ошибкой запас не резервируется.
- Отмена восстанавливает точные количества, записанные в заказе, даже если товар
  с тех пор стал неактивным или его запас изменился.
- Частичная отмена восстанавливает количества отменённых позиций и не меняет
  статус заказа (ADR-006).

## 6. Идемпотентность оформления заказа и платежей

Стратегия идемпотентности оформления заказа определена в
[ADR-002](adr/ADR-002-checkout-idempotency.md); идемпотентность платежей — в
[ADR-008](adr/ADR-008-payments-and-idempotency.md).

- `POST /api/orders` требует заголовок `Idempotency-Key` и заголовок `If-Match`.
- Ключи привязаны к аутентифицированному пользователю и должны соответствовать
  формату, определённому в разделе 10.
- Каждый ключ связан с отпечатком семантически значимого содержимого запроса:
  целевого адреса запроса и переданного `ETag` корзины.
- Fingerprint не включает selection явно: `IsSelected` меняет `rowversion`
  корзины, а `rowversion` уже входит в `If-Match` и fingerprint.
- Сервер проверяет наличие существующего ключа перед чтением текущей корзины.
- Один и тот же ключ и один и тот же отпечаток возвращают сохранённый результат;
  завершённый повтор не должен создавать ещё один заказ, повторно резервировать
  запас или создавать ещё один платёж.
- Повторное использование ключа с другим отпечатком возвращает `409 Conflict` с
  кодом `idempotency_key_reused`.
- Новые ключи резервируются в короткой отдельной транзакции с использованием
  устойчивой записи `InProgress`.
- Успешное создание заказа, резервирование выбранных позиций, создание `Payment`
  в `Pending`, очистка выбранных позиций, изменение версии строки корзины и
  завершение идемпотентности фиксируются атомарно.
- Окончательные бизнес-ошибки сохраняются после отката транзакции оформления
  заказа и воспроизводятся для соответствующих повторов. Новая попытка
  оформления заказа после сохранённой окончательной бизнес-ошибки требует нового
  ключа идемпотентности.
- Неожиданные инфраструктурные ошибки не сохраняются как окончательные
  бизнес-результаты.
- Неизвестный результат фиксации должен разрешаться проверкой устойчивого
  состояния; сервер не должен предполагать, что оформление заказа завершилось
  неудачно.
- Соответствующий запрос, пока попытка находится в состоянии выполнения, ожидает
  в течение ограниченного периода. Если окончательный результат не становится
  доступным вовремя, сервер возвращает `503 Service Unavailable` с кодом
  `idempotency_in_progress` и предлагает клиенту повторить запрос с тем же ключом
  и тем же запросом.
- Восстановление устаревших записей `InProgress` выполняется по требованию более
  поздним запросом с тем же ключом. Для этого требуется истёкший срок
  резервирования и проверка устойчивого состояния базы данных. Фоновый сервис
  восстановления не используется.
- Одновременные запросы и восстановление по требованию не должны независимо
  выполнять одно и то же оформление заказа.
- Идемпотентность платежей использует `PaymentAttempt`, который покрывает и
  `confirm`, и `refund`; уникальность — `(UserId, IdempotencyKey)`.
- Fingerprint платежа: для `confirm` — метод, путь и `paymentId`; для `refund` —
  метод, путь, `paymentId` и нормализованные `amount`/`reason`.
  `Idempotency-Key` не входит. Точные формулы и правила retry — ADR-008.

## 7. Заказы и отмена

- Статусы заказа — `Created`, `Paid`, `Shipped`, `Delivered`, `Cancelled`,
  `Returned` (ADR-004).
- Пользователь может просматривать только свои заказы.
- Заказ, принадлежащий другому пользователю, возвращает `404 Not Found`.
- Заказы сохраняют снимки названия товара и цены за единицу.
- `OrderItem.Quantity` — снимок исходного количества; отменённое количество
  хранится в `OrderItemCancellation`.
- `OrderItem.CancelledQuantity` вычисляется; инвариант
  `0 <= CancelledQuantity <= Quantity`.
- Эндпоинт отмены — `POST /api/orders/{id}/cancel` с optional body.
- Пустое тело отменяет заказ полностью; `items` отменяет указанные позиции
  частично.
- Полная отмена переводит заказ в `Cancelled`; частичная отмена статус не
  меняет.
- Отмена `Created` возвращает `Reserved` в `Available`; отмена `Paid`
  возвращает количество в `Available` и выполняет refund по ADR-008.
- Отмена `Cancelled` возвращает `409 order_already_cancelled`.
- Отмена `Shipped`, `Delivered` или `Returned` возвращает
  `409 invalid_order_transition`.
- Отмена требует `If-Match` с `Order.RowVersion`; отдельный `Idempotency-Key`
  не используется.
- Отмена выполняется в одной транзакции; одновременные попытки не должны
  восстанавливать запас или выполнять refund более одного раза.
- Повторная отмена после успешной отмены возвращает `409`.
- Отмена не изменяет корзину.
- Список заказов разбивается на страницы с использованием общих параметров
  списка, определённых в разделе 10.

## 8. Обработка ошибок

- Ошибки API используют `ProblemDetails` со стабильным `code`, специфичным для
  приложения.
- Полный перечень кодов и HTTP-статусов определён в
  [api.md](architecture/api.md), §4.1; здесь фиксируются только общие правила.
- Устаревшие или отсутствующие предварительные условия корзины и заказа
  используют `412 Precondition Failed` и `428 Precondition Required`; коды —
  `cart_version_conflict`, `order_version_conflict`, `precondition_required`.
- Недостаточный запас, конфликты идемпотентности, оформление заказа без
  выбранных позиций и недопустимые переходы состояния заказа используют
  `409 Conflict`.
- `cart_empty` (`409`) используется, если в корзине нет выбранных позиций.
- `invalid_order_transition` (`409`) используется для недопустимых переходов
  состояния заказа.
- `order_already_cancelled` (`409`) используется при повторной отмене уже
  отменённого заказа (ADR-006).
- `forbidden` (`403`) используется при недостатке прав, включая не-admin доступ
  к admin endpoints.
- `unsupported_media_type` (`415`) используется для непустого тела отмены с
  неверным `Content-Type`.
- Отсутствующая или недопустимая аутентификация возвращает `401 Unauthorized`.
- Отсутствующие ресурсы и ресурсы, принадлежащие другому пользователю,
  возвращают `404 Not Found`.
- Временно неразрешённая попытка идемпотентности возвращает
  `503 Service Unavailable`; это не должно сообщаться как окончательная неудача
  оформления заказа или платежа.
- Ответы с окончательными бизнес-ошибками сохраняются для идемпотентного
  воспроизведения; неожиданные инфраструктурные ошибки не сохраняются как
  окончательные бизнес-результаты.
- Известные отклонения от контракта ошибок, которые сознательно приняты и
  отложены для MVP+, перечислены в разделе 13.

## 9. Состав API

- Публичные эндпоинты: `GET /health`, `GET /api/products`,
  `GET /api/products/{id}`.
- Все остальные эндпоинты требуют аутентификации.
- Admin endpoints требуют роль admin и доступны только в Development.
- Изменения корзины, `PUT /api/cart/selection` и оформление заказа требуют
  `If-Match`.
- Отмена заказа требует `If-Match` с `Order.RowVersion`; отдельный
  `Idempotency-Key` не используется.
- `Idempotency-Key` требуется для `POST /api/payments/{id}/confirm` и
  `POST /api/payments/{id}/refund`. Fingerprint confirm включает `paymentId`;
  fingerprint refund дополнительно включает `amount` и `reason`. См.
  [ADR-008](adr/ADR-008-payments-and-idempotency.md) и
  [api.md](architecture/api.md), §6.2.
- Эндпоинты корзины: `GET /api/cart`, `POST /api/cart/items`,
  `PUT /api/cart/items/{productId}`, `DELETE /api/cart/items/{productId}`,
  `PUT /api/cart/selection`.
- Эндпоинты заказов: `POST /api/orders`, `GET /api/orders`,
  `GET /api/orders/{id}`, `POST /api/orders/{id}/cancel`.
- Эндпоинты платежей: `POST /api/payments/{id}/confirm`,
  `POST /api/payments/{id}/refund`.
- Admin endpoints: `POST /api/admin/products/{id}/deactivate`,
  `POST /api/admin/products/{id}/stock`, `POST /api/admin/orders/{id}/ship`,
  `POST /api/admin/orders/{id}/deliver`, `POST /api/admin/orders/{id}/return`.
- `GET /api/products` и `GET /api/orders` используют постраничную разбивку.
  Остальные эндпоинты в MVP+ не разбиваются на страницы.
- `GET /health` сообщает о доступности базы данных и является единственным
  эндпоинтом, тело успешного ответа которого не является представлением ресурса
  торгового процесса.

## 10. Константы MVP+

Эти значения являются единственным источником истины для числовых параметров,
общих для нескольких документов. Другие документы должны ссылаться на этот
раздел, а не повторять значения независимо.

| Параметр | Значение |
|---|---|
| Формат `Idempotency-Key` | `^[A-Za-z0-9_-]{8,128}$` |
| Ограниченное ожидание для совпадающей попытки оформления заказа в состоянии `InProgress` | 3 секунды |
| Срок резервирования или тайм-аут попытки оформления заказа в состоянии `InProgress` | 30 секунд |
| Хранение записи попытки оформления заказа | Автоматическая очистка в MVP+ не выполняется |
| Валюта `Money` | USD |
| Точность `Money` | `decimal(18,2)` |
| Округление `Money` | `MidpointRounding.AwayFromZero` при создании |
| Формат `Idempotency-Key` для платежа | Тот же формат, что и для оформления заказа |
| Отпечаток подтверждения платежа | SHA-256 от `POST /api/payments/{id}/confirm`, без `Idempotency-Key` |
| Ограниченное ожидание `PaymentAttempt` в состоянии `InProgress` | 3 секунды |
| Lease `PaymentAttempt` в состоянии `InProgress` | 30 секунд |
| Хранение `PaymentAttempt` | Автоматическая очистка в MVP+ не выполняется |
| Инварианты запаса | `Available >= 0`, `Reserved >= 0`; TTL и cleanup отсутствуют |
| Admin stock | Абсолютное `Available >= 0`; `Reserved` не изменяется |
| Пагинация списка: значения по умолчанию `page` / `pageSize` / максимум `pageSize` | `1` / `20` / `100` |
| Формат `ETag` | Заключённый в кавычки сильный тег сущности: Base64 от 8-байтового SQL Server `rowversion` |
| Уровень изоляции транзакций для MVP+ | `READ COMMITTED` в сочетании с явным `UPDLOCK` и условными обновлениями |
| Обработка взаимоблокировок для MVP+ | Автоматических повторных попыток внутри процесса нет; запрос завершается неудачно, и клиент повторяет его с тем же ключом идемпотентности или повторно получает корзину |

## 11. Вне области действия

MVP+ не включает:

- Реальную аутентификацию JWT/OAuth (M11).
- Уведомления (M9).
- Промо, скидки, купоны и налоги (M10).
- Reconciliation (M14).
- Stripe, реальные вебхуки и внешних платёжных провайдеров.
- Интеграцию доставки или перевозчиков; admin ship/deliver — не интеграция.
- Микросервисы или брокеры сообщений.
- Запасы на нескольких складах.
- Outbox.
- Фоновые процессы cleanup или recovery.
- Admin UI.
- Частичный возврат после доставки.

  списаний запаса под блокировкой строк товаров.
- D1 устранён: проверка наличия/формата `If-Match` выполняется до резервирования

- D1, исторические данные: записи `CheckoutAttempts`, созданные до устранения D1
  для запросов без `If-Match`, не удаляются и не мигрируются. Они не влияют на
  новое поведение (новые запросы без `If-Match` не резервируют ключ), но занимают
  место. Очистка не входит в MVP+.
- D2 устранён: `insufficient_stock` и `product_unavailable` перечисляют все
  затронутые товары (`id` + `name`) в `detail`, прочитанные после отката/предварительной
  проверки. Приоритет — `product_unavailable`, если есть неактивный товар.
- D2 закрыт с дополнением: если после отката `ExecuteUpdateAsync` конфликт
  запаса/активности не воспроизводится, checkout возвращает временный
  `503 checkout_retry`; попытка остаётся `InProgress` с истёкшим lease, ответ не
  сохраняется в `ResponsePayload`, а повтор с тем же ключом и fingerprint снова
  выполняет checkout.
- D2, bounded wait для `checkout_retry`: повтор с тем же ключом после `503
  checkout_retry` проходит через существующий bounded wait (3 секунды, см. §10)
  перед захватом истёкшего lease, даже если lease уже истёк. Это осознанно:
  сохраняется grace period для действительно выполняющейся попытки. Оптимизация
  (сразу захватывать истёкший lease без ожидания) — вне MVP+.
- D4 устранён: сохранённый `ResponsePayload` остаётся чистым бизнес-результатом
  без `instance`; при формировании HTTP-ответа checkout-путь добавляет
  `instance = Request.Path`, если его нет, и возвращает ошибки с
  `Content-Type: application/problem+json`.
- D10 устранён: `GET /health` при `503` возвращает стандартный `ProblemDetails`
  с `instance = /health`, `code = health_unavailable` и
  `Content-Type: application/problem+json`.
- D8 устранён: запрос с неподдерживаемым `Content-Type` к эндпоинту,
  принимающему тело, возвращает `415` с `ProblemDetails`,
  `instance = Request.Path`, `Content-Type: application/problem+json` и
  `code = unsupported_media_type`. Обработка `400`/`validation_error` не
  изменена.
- D8, ограничение `SuppressMapClientErrors = true`: параметр отключает
  автоматическое оборачивание «голых» client-error результатов MVC
  (`return NotFound()`, `return BadRequest()` без `ProblemDetails`) в
  `ProblemDetails`. Текущие контроллеры такие результаты не возвращают — все коды
  обрабатываются `ExceptionHandler`/`InvalidModelStateResponseFactory`/
  `UseStatusCodePages`. При добавлении новых контроллеров с «голыми» client-error
  результатами нужно либо возвращать `ProblemDetails` явно, либо использовать
  `IProblemDetailsService`.
- Путь unknown-commit покрыт интеграционным тестом: сбой `SaveChangesAsync`
  моделируется EF Core `SaveChangesInterceptor`; проверяются
  `503 idempotency_in_progress`, попытка `InProgress` без `ResponsePayload` и
  `OrderId`, отсутствие заказа и отсутствие второго заказа при повторе с тем же
  ключом.
- Unknown-commit, покрытие `CommitAsync`: покрыт путь сбоя `SaveChangesAsync`.
  Сбой `CommitAsync` отдельным тестом не моделировался: оба пути используют один
  `catch` и одинаковое преобразование в `CheckoutCommitUncertainException`.
  Отдельный тест — вне MVP+.

## 13. Известные проблемы

Известные ограничения и открытые вопросы MVP+:

- `X-Test-User` — учебный Development-механизм; реальная аутентификация
  JWT/OAuth не реализована.
- Admin endpoints доступны только в Development; admin UI отсутствует.
- Платежи — mock, dev-only; нет Stripe, реальных вебхуков и reconciliation.
  См. [ADR-008](adr/ADR-008-payments-and-idempotency.md).
- `Payment.Failed` не терминален: retry переводит
  `Failed → Pending → Confirmed`. См.
  [ADR-008](adr/ADR-008-payments-and-idempotency.md).
- Refund поддерживается, включая несколько частичных refund через таблицу
  `Refund`. См. [ADR-008](adr/ADR-008-payments-and-idempotency.md).
- Refund выполняется in-process через `IPaymentRefundService` (домен
  `Payment`/`Refund`); `IPaymentProvider.RefundAsync` в текущем сценарии не
  вызывается. См. `payments.md` §5, `api.md` §3.5.
- Аудит работает at-most-once: при сбое handler'а audit-запись теряется; outbox
  и retry отсутствуют.
- TTL, cleanup и фоновое освобождение резервов отсутствуют; `Created` может
  удерживать `Reserved` неограниченно долго.
- `PaymentAttempt` и `CheckoutAttempt` не очищаются автоматически.
- Уведомления, промо, скидки, купоны и налоги не реализованы.
- Частичный возврат после доставки не поддерживается.
- Replay checkout: повторный checkout возвращает сохранённый `ResponsePayload`
  (для попыток, созданных начиная с этапа 19, он содержит `paymentId` и
  `Payment` в `Pending`) и текущий `Order.RowVersion` в ETag, а не ETag из
  сохранённого payload. Для попыток без `OrderId` (созданных до этапа 15) ETag
  не возвращается. Причина: `CheckoutAttempt.ResponsePayload` не сохранял ETag
  заказа. Исправление (сохранение ETag в payload) — вне MVP+ или отдельный этап.
- `ConsumeReservedAsync` учитывает `Quantity - CancelledQuantity` для каждой
  позиции, поэтому confirm не списывает уже отменённый запас.
- `PaymentAttempt` использует lease 30 секунд, bounded wait 3 секунды и polling
  каждые 100 мс; просроченный lease может быть перехвачен повторным запросом с
  тем же ключом.
- Порядок блокировок в confirm, cancel и return — `Order`, затем `Payment`;
  admin refund блокирует только `Payment`. Единый порядок предотвращает
  взаимные блокировки.
- `refund_not_allowed` (`409`) возвращается для refund при `Pending`, `Failed`
  или `Refunded`, а также при превышении остатка.
- DTO заказа (`GET /api/orders`, `GET /api/orders/{id}` и checkout `201`)
  включает `paymentId` и `payment`; `paymentId` равен `null` для заказов,
  созданных до этапа 19.
- `OrderItemCancellation.Reason`: `Reason` не передаётся через API (body
  `api.md` его не описывает); поле nullable и заполняется `null` из API.
  Внутренние сценарии могут заполнять позже.
- `admin_stock_conflict`: реальная SQL-гонка admin stock (два параллельных
  admin stock) не покрыта integration-тестом; логика retry и
