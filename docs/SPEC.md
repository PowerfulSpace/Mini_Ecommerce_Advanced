# Функциональная спецификация

## 1. Назначение

Этот документ определяет функциональные требования и критерии приёмки для
MVP+ Mini E-commerce (M1–M14).

Он описывает ожидаемое поведение каталога товаров, корзины, оформления заказа,
платежей, заказов, отмены, admin API, аудита, аутентификации и обработки ошибок.

Требования в этом документе обязательны, если они явно не помечены как
предложенные или неразрешённые.

SPEC не дублирует ADR, модель данных и контракт API. Точные решения, схема
хранения, HTTP-контракты и коды ошибок определяются соответствующими
документами:

- `PROJECT.md` — цели и область охвата проекта.
- `DOMAIN.md` — концепции домена, бизнес-правила и инварианты.
- `DECISIONS.md` — реестр утверждённых технических решений.
- `architecture/architecture.md` — архитектура бэкенда.
- `architecture/data-model.md` — структура базы данных и ограничения.
- `architecture/api.md` — контракты HTTP API и коды ошибок.
- `architecture/payments.md` — платёжная модель и refund.
- `architecture/events.md` — доменные события и их обработка.
- `adr/ADR-001-cart-concurrency.md` — конкурентный доступ к корзине.
- `adr/ADR-002-checkout-idempotency.md` — идемпотентность оформления заказа.
- `adr/ADR-003-money-value-object.md` — `Money`.
- `adr/ADR-004-order-state-machine.md` — статусы и переходы заказа.
- `adr/ADR-005-stock-reservations.md` — резервы стока.
- `adr/ADR-006-partial-checkout-and-cancellation.md` — частичный checkout и
  частичная отмена.
- `adr/ADR-007-domain-events.md` — доменные события.
- `adr/ADR-008-payments-and-idempotency.md` — платежи и идемпотентность.
- `adr/ADR-009-admin-api-and-roles.md` — admin API и роли.
- `adr/ADR-010-audit.md` — аудит.

## 2. Область охвата MVP+

MVP+ (M1–M14) включает:

- Аутентификацию только для разработки через `X-Test-User`.
- Трёх начальных тестовых пользователей: Alice, Bob и admin.
- `Money` как доменный value object; USD и `decimal(18,2)`.
- Каталог товаров только для чтения.
- Запас в виде `Available` и `Reserved`; `Reserved` не отдаётся публично.
- Корзины покупок, отдельные для каждого пользователя.
- Добавление, обновление и удаление позиций корзины.
- `CartItem.IsSelected` и выбор позиций для частичного checkout.
- Частичный checkout только выбранных позиций.
- Резервирование выбранных позиций при checkout.
- Шесть статусов заказа.
- Mock-платежи: `Pending`, `Confirmed`, `Failed`, `Refunded`.
- Подтверждение платежа и идемпотентность платежей.
- Ручной admin refund в Development.
- Автоматический refund при отмене после оплаты и возврате после доставки.
- Полную и частичную отмену заказа.
- `OrderItemCancellation` как историю отмен.
- Admin API: deactivate, stock, ship, deliver, return.
- Доменные события и аудит at-most-once.
- Идемпотентность оформления заказа и платежей.
- Стандартизированные ошибки API с `ProblemDetails`.
- Модульные и интеграционные тесты SQL Server.
- Фронтенд, реализуемый после того, как основа бэкенда и контракты API
  определены.

MVP+ (M1–M14) исключает:

- M9 — уведомления.
- M10 — промо, купоны, скидки и налоги.
- M11 — реальную JWT/OAuth-аутентификацию и управление ролями.
- M14 — reconciliation платежей.
- Stripe и реальный платёжный провайдер.
- Вебхуки.
- Outbox и гарантированную доставку событий.
- TTL резервов и фоновый cleanup.
- Admin UI.
- Мультивалютность.
- Реальную интеграцию доставки или перевозчиков; admin ship/deliver/return
  входят в MVP+.
- Частичный возврат после доставки.
- Частичные платежи.
- API чтения аудита.
- Регистрацию клиентов, пароли и управление профилем.
- Микросервисы и брокеры сообщений.

`X-Test-User` — осознанное упрощение аутентификации. См. `DECISIONS.md`, §13;
полное обоснование — см. `../RATIONALE.md`.

## 3. Пользователи и аутентификация

### 3.1 Модель пользователя

Пользователь имеет следующие атрибуты:

- `Id`: уникальный идентификатор.
- `Email`: обязательный и уникальный адрес электронной почты.
- `CreatedAtUtc`: метка времени создания в UTC.
- Роль: `customer` или `admin`.

Приложение не предоставляет регистрацию пользователей или управление профилем.
Роль admin доступна только через Development-механизм `X-Test-User`.

### 3.2 Тестовые пользователи

Среда Development должна создавать следующих пользователей:

- Alice — `alice@example.com`, роль `customer`.
- Bob — `bob@example.com`, роль `customer`.
- admin — роль `admin`.

Начальное заполнение должно быть идемпотентным: повторный запуск приложения не
должен создавать дублирующихся пользователей. У каждого пользователя должен быть
отдельный идентификатор.

### 3.3 Аутентификация для разработки

Среда Development использует HTTP-заголовок `X-Test-User`.

Поддерживаемые значения:

- `X-Test-User: alice`
- `X-Test-User: bob`
- `X-Test-User: admin`

Заголовок выбирает одну из начальных тестовых идентичностей.

Требования:

- Схема тестовой аутентификации должна регистрироваться только в Development.
- Схема не должна быть доступна в Production.
- Отсутствующие или неизвестные значения тестового пользователя не должны
  аутентифицировать запрос.
- Защищённые конечные точки должны отклонять неаутентифицированные запросы.
- Приложение должно определять идентификатор текущего пользователя из контекста
  аутентифицированного запроса.
- Клиенты не должны выбирать владельца корзины, заказа или платежа, передавая
  идентификатор пользователя.
- Запрос от `alice` или `bob` к admin endpoint возвращает `403 Forbidden` с
  кодом `forbidden`.
- Admin endpoints доступны только в Development; в Production они не
  регистрируются и возвращают `404 Not Found`.
- Реальная JWT/OAuth-аутентификация не вводится.

`X-Test-User` — осознанное упрощение. См. `DECISIONS.md`, §13;
см. `../RATIONALE.md`.

Защищённые конечные точки — это все конечные точки, кроме `GET /health`,
`GET /api/products` и `GET /api/products/{id}`. Конечные точки каталога и
работоспособности являются публичными и должны работать без аутентификации.

### 3.4 Изоляция данных пользователей

Пользователи должны иметь доступ только к своим собственным корзинам, заказам и
платежам.

Пользователь, пытающийся получить доступ к заказу или платежу другого
пользователя, должен получить `404 Not Found`.

Операции с корзиной не должны раскрывать или изменять корзину другого
пользователя. Confirm платежа доступен только владельцу платежа.

Admin endpoints проверяют роль admin и не подменяют пользовательскую
принадлежность. Admin API не предоставляет чтение чужих заказов или платежей.

## 4. Каталог товаров

### 4.1 Атрибуты товара

Товар содержит:

- `Id`: уникальный идентификатор.
- `Name`: название товара.
- `Description`: описание товара.
- `Price`: текущая цена; `Money` в Domain, число (`decimal`) в API.
- `Available`: количество, доступное для новых заказов.
- `Reserved`: количество, зарезервированное незавершёнными заказами.
- `IsActive`: доступен ли товар для покупки.
- `CreatedAtUtc`: метка времени создания в UTC.

`Available` заменяет прежнее `StockQuantity`. `Reserved` не отдаётся в публичном
API.

База данных должна хранить денежные значения с помощью SQL Server
`decimal(18,2)`. Приложение использует USD в качестве валюты. `Money`
обеспечивает неотрицательность, округление и проверку валюты по ADR-003.

### 4.2 Поведение каталога

Каталог доступен только для чтения через публичный API. Конечные точки каталога
не требуют аутентификации.

Обязательные конечные точки:

- `GET /api/products`
- `GET /api/products/{id}`

`GET /api/products` возвращает только активные товары и пагинируется с общими
параметрами списка, определёнными в `architecture/api.md` (значения по умолчанию
и максимумы размеров страниц определены в `DECISIONS.md`).

Публичный каталог:

- содержит только активные товары;
- возвращает `available >= 0`;
- не раскрывает `reserved`;
- использует стабильный порядок между страницами.

Товары не должны физически удаляться в рамках обычного управления жизненным
циклом каталога. Деактивация представлена `IsActive = false`.

Неактивный товар нельзя купить. Получение одного неактивного или неизвестного
товара возвращает `404 Not Found` с кодом `product_not_found`.

Admin-операции каталога:

- деактивация товара;
- установка абсолютного `Available`.

Их контракты и ограничения определены в §9 и `architecture/api.md`.

### 4.3 Цены товаров

Корзина использует текущую цену товара.

Когда оформление заказа успешно, каждая позиция заказа сохраняет снимок названия
товара и цены за единицу на момент покупки. Последующие изменения товара не
должны изменять существующие снимки позиций заказа.

Налоги, скидки, стоимость доставки или конвертация валют не применяются.
Денежные значения используют `Money` и USD по ADR-003.

## 5. Корзина покупок

### 5.1 Владение корзиной и жизненный цикл

У пользователя может быть не более одной корзины.

Корзина создаётся при первом обращении во время `GET /api/cart`, когда у
пользователя её ещё нет. Изменения корзины и оформление заказа никогда не
создают корзину; когда корзины нет, они завершаются неудачно с `404 Not Found` и
кодом `cart_not_found`.

Корзина связана с аутентифицированным пользователем, а не с идентификатором
пользователя, предоставленным клиентом.

Корзина сохраняется после успешного оформления заказа. При частичном checkout
очищаются только выбранные позиции; невыбранные остаются в корзине.

Обязательная конечная точка:

- `GET /api/cart`

Повторные запросы `GET /api/cart` возвращают ту же корзину. Одновременные первые
запросы для одного пользователя должны быть безопасными: может быть создана
только одна строка корзины, а проигравший запрос должен вернуть выигравшую
корзину вместо неудачи.

### 5.2 Операции с корзиной и выбор позиций

Обязательные конечные точки:

- `POST /api/cart/items`
- `PUT /api/cart/items/{productId}`
- `DELETE /api/cart/items/{productId}`
- `PUT /api/cart/selection`

Каждое изменение корзины, включая изменение выбора, требует заголовка `If-Match`,
несущего `ETag` корзины, полученный от сервера. Запрос не имеет поля версии
корзины; `DELETE` не имеет тела запроса.

Добавление товара, уже присутствующего в корзине, увеличивает существующее
количество, а не создаёт дублирующую строку корзины.

Обновление позиции корзины устанавливает её количество в запрошенное
положительное целое число.

Удаление позиции — отдельная операция. Нулевое количество не заменяет удаление.

`CartItem.IsSelected` (`bool`, по умолчанию `true`) является частью состояния
корзины.

`PUT /api/cart/selection`:

- обновляет только перечисленные позиции;
- позиции, отсутствующие в запросе, сохраняют текущее значение `isSelected`;
- требует `If-Match`;
- изменяет `rowversion` корзины;
- не резервирует запас.

`GET /api/cart` возвращает:

- `isSelected` для каждой позиции;
- `totalAmount` — стоимость всей корзины;
- `selectedTotalAmount` — стоимость выбранных позиций.

Семантика `ETag`/`If-Match` не меняется: выбор — это мутация корзины, а не
отдельный механизм версионирования.

### 5.3 Проверка количества

Количества в корзине должны быть положительными целыми числами.

Приложение должно отклонять:

- Нулевые количества.
- Отрицательные количества.
- Дробные количества.
- Недопустимые полезные нагрузки запросов.

Ошибки валидации не должны изменять корзину.

### 5.4 Проверка запаса

Добавление товара или изменение его количества должно проверять текущее наличие.

Если запрошенное количество превышает доступный запас, вся операция должна быть
отклонена. Приложение не должно молча уменьшать запрошенное количество до
доступного объёма.

Если проверка запаса завершается неудачно, существующее состояние корзины должно
остаться неизменным.

Запас должен быть проверен повторно во время оформления заказа, поскольку
наличие могло измениться с момента добавления позиции.

### 5.5 Неактивные товары

Неактивный товар может оставаться в существующей корзине.

Для неактивной позиции корзины:

- Позиция остаётся видимой в корзине.
- Позиция определяется как недоступная.
- Её добавление или изменение её количества отклоняется.
- Её удаление разрешено.
- Checkout отклоняется, если неактивная позиция выбрана.

Невыбранная неактивная позиция не блокирует checkout и остаётся в корзине.

Неудачное оформление заказа не должно очищать корзину.

### 5.6 Пустая корзина и пустой выбор

Пустую корзину нельзя оформить в заказе.

Checkout оформляет только выбранные позиции. Если ни одна позиция не выбрана,
запрос завершается с `409 Conflict` и кодом `cart_empty`; `detail` уточняет, что
нет выбранных позиций. Отдельный код для пустого выбора не вводится.

Запрос оформления заказа должен завершиться неудачно без создания заказа,
платежа или изменения запаса.

### 5.7 Конкурентный доступ к корзине

Одновременные операции с корзиной не должны молча перезаписывать более новое
состояние.

Реализация должна использовать механизмы конкурентного доступа SQL Server,
указанные в `adr/ADR-001-cart-concurrency.md`.

Версия корзины предоставляется как `ETag` каждого представления корзины и
передаётся клиентами через заголовок `If-Match` при изменениях корзины,
изменении выбора и оформлении заказа.

- Отсутствующий обязательный `If-Match` возвращает `428 Precondition Required` с
  кодом `precondition_required`.
- Устаревшее значение `If-Match` возвращает `412 Precondition Failed` с кодом
  `cart_version_conflict`.
- Устаревшая операция не должна применяться и не должна автоматически
  повторяться для более нового состояния корзины.

Одновременные изменение корзины и оформление заказа должны давать один
согласованный результат:

- Если побеждает обновление корзины, оформление заказа использует обновлённую
  корзину.
- Если побеждает оформление заказа, одновременное устаревшее обновление не
  должно восстанавливать старые позиции корзины или изменять оформленную
  корзину.

Успешное оформление заказа должно изменить строку корзины в той же транзакции,
чтобы `ETag`, выданный до оформления заказа, стал недействительным. Без этого
изменения устаревшее изменение могло бы успешно примениться к опустошённой
корзине.

Частичное состояние корзины или заказа не допускается.

## 6. Оформление заказа

### 6.1 Конечная точка оформления заказа

Обязательная конечная точка:

- `POST /api/orders`

Конечная точка создаёт заказ из выбранных позиций корзины аутентифицированного
пользователя.

Обязательные заголовки:

- `Idempotency-Key` с форматом, определённым в `DECISIONS.md`.
- `If-Match`, несущий `ETag` корзины, которую клиент намерен оформить.

Тело запроса пустое. Клиент не должен передавать другой идентификатор
пользователя для выбора владельца корзины.

### 6.2 Предусловия оформления заказа

Оформление заказа должно отклонить запрос, если:

- У пользователя ещё нет корзины.
- В корзине нет выбранных позиций.
- Любая выбранная позиция ссылается на неактивный товар.
- Любое запрошенное количество выбранной позиции превышает доступный запас.
- Запрос недопустим, в том числе недопустимый `Idempotency-Key` или
  отсутствующий `If-Match`.
- Ключ идемпотентности конфликтует с предыдущим запросом.

Невыбранные позиции не проверяются, не резервируются и не очищаются.

Отсутствующий `If-Match` возвращает `428 Precondition Required` и не должен
резервировать ключ идемпотентности. Устаревший `If-Match` возвращает
`412 Precondition Failed`.

Неудача бизнес-правила не должна очищать корзину или частично резервировать
запас.

### 6.3 Транзакционное поведение

Операция оформления заказа должна быть атомарной.

Успешное оформление заказа должно согласованно выполнить следующие
бизнес-изменения:

1. Проверить выбранные позиции корзины и их товары.
2. Проверить текущее наличие выбранных товаров.
3. Зарезервировать выбранные позиции: `Available -= quantity`,
   `Reserved += quantity`.
4. Создать заказ в статусе `Created` и его позиции заказа.
5. Сохранить снимки названия товара и цены за единицу.
6. Рассчитать и сохранить общую сумму заказа.
7. Создать `Payment` в состоянии `Pending` и вернуть `paymentId`.
8. Очистить только выбранные позиции корзины, сохранив корзину.
9. Изменить строку корзины так, чтобы изменилась её версия.
10. Завершить запись идемпотентности.

Эти изменения должны быть зафиксированы согласованно с утверждённой стратегией
идемпотентности.

Если какое-либо резервирование завершается неудачно, транзакция должна откатить
все бизнес-изменения оформления заказа.

После неудачного оформления заказа:

- Неудачная попытка не создаёт заказ.
- Частичное резервирование не остаётся.
- Платёж не создаётся.
- Корзина остаётся неизменной.
- Неудача возвращается в соответствии с задокументированным контрактом ошибок.

### 6.4 Атомарное резервирование запаса

Резервирование запаса должно выполняться атомарно путём обновления товара
только тогда, когда его `Available` больше или равен запрошенному количеству.

Реализация должна проверять количество затронутых строк.

Строки товаров должны обрабатываться в стабильном порядке, предпочтительно по
идентификатору товара, чтобы уменьшить взаимоблокировки.

Снимки названия товара и цены за единицу для позиций заказа должны читаться,
пока строки товаров всё ещё заблокированы резервированием, чтобы снимок нельзя
было получить из состояния, которое транзакция оформления заказа не
заблокировала.

Все изменения запаса должны принадлежать одной транзакции оформления заказа.

Если какой-либо товар не может быть зарезервирован, вся транзакция оформления
заказа должна откатиться.

Список товаров с недостаточным запасом для окончательного ответа о конфликте
читается после отката неудачной транзакции оформления заказа. Он носит только
информационный характер и не должен подразумевать, что запас остаётся
зарезервированным.

### 6.5 Данные заказа

Заказ содержит:

- `Id`: уникальный идентификатор.
- `UserId`: владелец заказа.
- `Status`: текущий статус заказа.
- `CreatedAtUtc`: метка времени создания в UTC.
- `TotalAmount`: снимок общей суммы покупки.
- `PaymentId`: nullable-ссылка на платёж.
- `RowVersion`: версия заказа для `If-Match`.

Каждая позиция заказа содержит:

- `Id`: уникальный идентификатор.
- `OrderId`: идентификатор родительского заказа.
- `ProductId`: идентификатор указанного товара.
- `ProductName`: снимок названия товара.
- `UnitPrice`: снимок цены за единицу.
- `Quantity`: купленное количество; неизменяемый снимок.
- `CancelledQuantity`: вычисляется как сумма `OrderItemCancellation.Quantity`
  и не хранится отдельным полем.

Общая сумма заказа рассчитывается как:

`TotalAmount = SUM(UnitPrice × Quantity)`

Сумма выражена в USD и не включает налоги, скидки или доставку.
`TotalAmount` не уменьшается при частичной отмене; отменяемая стоимость
вычисляется по снимкам `OrderItem.UnitPrice`.

### 6.6 Идемпотентность

Конечная точка оформления заказа требует заголовка `Idempotency-Key` и заголовка
`If-Match`.

Ключ идентифицирует одну попытку оформления заказа для аутентифицированного
пользователя и должен соответствовать формату, определённому в `DECISIONS.md`.

Требования:

- Один и тот же пользователь и ключ не должны создавать более одного заказа.
- Ключ связан с отпечатком целевого запроса и переданного значения `If-Match`.
- Fingerprint не включает `selection` явно: `IsSelected` меняет `rowversion`
  корзины, а `rowversion` уже входит в `If-Match` и fingerprint.
- Повторение того же ключа с тем же отпечатком должно возвращать сохранённый
  результат.
- Повторное использование ключа с другим отпечатком должно возвращать
  `409 Conflict` с кодом `idempotency_key_reused`.
- Существующий ключ должен быть проверен до чтения текущей корзины.
- Новая попытка после окончательной неудачи бизнес-правила требует нового ключа.
- Одновременные запросы с одним и тем же ключом не должны выполнять независимые
  попытки оформления заказа.
- Совпадающий запрос, который всё ещё выполняется, ожидает в течение
  ограниченного периода. Если окончательный результат не становится доступным
  вовремя, сервер возвращает `503 Service Unavailable` с кодом
  `idempotency_in_progress`, и клиент повторяет попытку с тем же ключом и
  запросом.
- Окончательные ошибки бизнес-правил должны сохраняться для повторных запросов.
- Неожиданные внутренние ошибки сервера не должны автоматически сохраняться как
  окончательные результаты.
- Неизвестный результат фиксации транзакции должен быть разрешён повторной
  попыткой с тем же ключом и проверкой устойчивого состояния.
- Запрос не должен запускать независимое оформление заказа, пока результат
  предыдущей попытки с тем же ключом остаётся неизвестным.
- Временная ошибка конкурентного изменения может возвращать `503` с кодом
  `checkout_retry`; клиент повторяет тот же запрос с тем же ключом.

Утверждённая стратегия резервирует ключ в короткой транзакции перед выполнением
оформления заказа. Затем успешная транзакция заказа фиксирует заказ, изменения
запаса, создание платежа, очистку выбранных позиций, изменение версии строки
корзины и завершённый результат идемпотентности вместе.

Восстановление заброшенных записей `InProgress` происходит по требованию, когда
поступает повторная попытка с тем же ключом. Оно требует истёкшего срока
резервирования и проверки устойчивого состояния базы данных. Фоновая служба
восстановления не используется, и реализация не должна автоматически повторно
запускать такие попытки.

См. `adr/ADR-002-checkout-idempotency.md`.

### 6.7 Ошибки оформления заказа

Ключевые коды:

- `cart_empty` (`409`) — нет выбранных позиций;
- `insufficient_stock` (`409`) — недостаточно запаса;
- `product_unavailable` (`409`) — выбранный товар недоступен;
- `checkout_retry` (`503`) — временная ошибка конкурентного изменения;
- `idempotency_key_reused` (`409`) — ключ использован с другим запросом;
- `idempotency_in_progress` (`503`) — совпадающая попытка ещё выполняется.

Полный перечень и точные условия определены в `architecture/api.md`, §4.1.
Ответ `503` является временным и не должен сохраняться как окончательный
бизнес-результат.

## 7. Платежи

### 7.1 Модель платежа

`Payment` принадлежит заказу; у заказа не более одного платежа. `Payment.Amount`
равен сумме заказа. `Order.PaymentId` содержит ссылку на платёж.

Статусы:

- `Pending` — платёж создан, но не подтверждён;
- `Confirmed` — платёж подтверждён, заказ переходит в `Paid`;
- `Failed` — mock-провайдер вернул неудачу;
- `Refunded` — выполнен полный возврат.

`Failed` не терминален для retry подтверждения. `Refunded` терминален.

`Payment` хранит `RefundedAmount`, а каждый возврат, включая полный, создаёт
запись `Refund`. Несколько частичных refund допускаются. Отдельного статуса
`PartiallyRefunded` нет; частичный возврат оставляет `Confirmed`.

Точная модель и инварианты определены в
`adr/ADR-008-payments-and-idempotency.md` и `architecture/data-model.md`,
§4.8–4.10. Детали реализации — в `architecture/payments.md`.

### 7.2 Создание платежа

Checkout создаёт `Payment` в состоянии `Pending` в одной транзакции с заказом,
резервированием запаса и очисткой выбранных позиций.

Требования:

- `Payment.Amount` равен сумме созданного заказа;
- `Payment.OrderId` уникален;
- ответ `201 Created` содержит `paymentId`;
- заказ создаётся в `Created`, а не в `Paid`;
- `PendingPayment` в `OrderStatus` не вводится;
- повторный checkout с тем же ключом не создаёт второй заказ или второй платёж;
- при откате checkout платёж не сохраняется.

### 7.3 Подтверждение платежа

`POST /api/payments/{id}/confirm`:

- доступен только владельцу платежа;
- требует `Idempotency-Key`;
- не требует `If-Match`;
- mock-провайдер выполняет `Pending → Confirmed`;
- заказ переходит `Created → Paid` через `MarkPaid()`;
- `Reserved` уменьшается на оставшееся количество заказа с учётом
  `CancelledQuantity` (consumed);
- confirm, consume `Reserved`, переход заказа и завершение `PaymentAttempt`
  выполняются в одной транзакции.

Если `Payment.Status = Failed`, повтор с тем же ключом и fingerprint выполняет
retry `Failed → Pending → Confirmed` для того же `Payment`. С новым ключом
создаётся новая попытка на том же платеже; второй `Payment` не создаётся.

`Refunded` терминален. Повторный confirm не меняет платёж. Если платёж уже
`Confirmed` и fingerprint совпадает, возвращается сохранённый успешный ответ;
при другом fingerprint возвращается `409 payment_already_confirmed`.

Ошибки: `payment_not_found`, `payment_already_confirmed`, `payment_failed`,
`invalid_order_transition`, `idempotency_key_reused`,
`idempotency_in_progress`. См. `architecture/api.md`, §3.5 и §4.1.

### 7.4 Возврат

`POST /api/payments/{id}/refund` — admin endpoint, доступный только в
Development.

Ручной возврат:

- требует `Idempotency-Key`;
- не требует `If-Match`;
- выполняется только для `Payment.Status = Confirmed`; для `Pending`, `Failed`
  и `Refunded` возвращается `409 refund_not_allowed`;
- принимает положительный `decimal` `amount` и необязательный `reason`;
- изменяет только `Payment` и создаёт `Refund`;
- не меняет заказ и запас;
- при полном возврате переводит `Payment` в `Refunded`;
- при частичном возврате оставляет `Payment` в `Confirmed`;
- не допускает сумму больше `Payment.Amount - Payment.RefundedAmount`;
- создаёт запись `Refund` для каждой операции;
- устанавливает `RefundedAtUtc` только при полном возврате.

Автоматический refund при `Paid → Cancelled` и `Delivered → Returned`
выполняется внутренним refund-сервисом, не через endpoint, в одной транзакции с
изменением заказа и запаса. При частичной отмене после оплаты refund
рассчитывается пропорционально снимкам `OrderItem.UnitPrice`, а статус заказа
не меняется.

Если refund падает, вся транзакция отмены или возврата откатывается: платёж,
заказ, отмены и запас не остаются частично изменёнными.

Повторный refund после полного возврата или refund больше остатка возвращает
`409 refund_not_allowed`.

См. `architecture/payments.md`, §5, и `adr/ADR-008-payments-and-idempotency.md`.

### 7.5 Идемпотентность платежей

Confirm и refund используют `PaymentAttempt`:

- `(UserId, IdempotencyKey)` уникален;
- `PaymentAttempt` покрывает confirm и refund;
- для confirm fingerprint включает метод, путь и `paymentId`;
- для refund fingerprint дополнительно включает нормализованные `amount` и
  `reason`;
- `Idempotency-Key` не входит в fingerprint;
- завершённая попытка воспроизводит сохранённые статус и тело;
- тот же ключ с другим fingerprint возвращает `409 idempotency_key_reused`;
- `InProgress` использует bounded wait и lease;
- при истечении ожидания возвращается `503 idempotency_in_progress`;
- восстановление выполняется по требованию;
- окончательный `Failed` для confirm допускает retry с тем же ключом;
- для refund `Failed` не применяется, `Refunded` терминален.

Точные формулы и правила — `adr/ADR-008-payments-and-idempotency.md` и
`architecture/api.md`, §6.2.

### 7.6 Взаимодействие с OrderStatus

- `Created → Paid` — только через confirm платежа.
- `Created → Cancelled` — отмена до оплаты, без refund.
- `Paid → Cancelled` — отмена после оплаты с автоматическим refund.
- `Paid → Shipped` — admin ship.
- `Shipped → Delivered` — admin deliver.
- `Delivered → Returned` — admin return с автоматическим refund.
- Частичная отмена после оплаты не меняет статус заказа, но выполняет частичный
  refund.
- `Cancelled` и `Returned` терминальны.
- `Delivered → Cancelled` не разрешён.

См. `adr/ADR-004-order-state-machine.md`.

## 8. Заказы и отмена

### 8.1 История заказов и сведения о заказе

Обязательные конечные точки:

- `GET /api/orders`
- `GET /api/orders/{id}`

`GET /api/orders` пагинируется с общими параметрами списка, определёнными в
`architecture/api.md`. Порядок заказов должен быть стабильным между страницами,
сначала новые.

Пользователи могут просматривать только свои собственные заказы. Заказ,
принадлежащий другому пользователю, должен возвращать `404 Not Found`.

История заказов должна сохранять отменённые и возвращённые заказы.

API должен возвращать сохранённые снимки позиций заказа, а не подставлять
текущие названия или цены товаров.

`GET /api/orders/{id}` возвращает `ETag` заказа. Ответы, изменяющие заказ,
возвращают новый `ETag`.

Сведения о заказе включают:

- шесть возможных статусов;
- `paymentId` и объект платежа, если он существует;
- `cancelledQuantity` по каждой позиции;
- исходный `TotalAmount`, который не уменьшается при частичной отмене.

### 8.2 Статусы и переходы

Заказ имеет шесть статусов:

- `Created`
- `Paid`
- `Shipped`
- `Delivered`
- `Cancelled`
- `Returned`

Допустимые переходы:

| Из | В | Сценарий |
|---|---|---|
| `Created` | `Paid` | Подтверждение платежа |
| `Created` | `Cancelled` | Отмена до оплаты |
| `Paid` | `Shipped` | Admin ship |
| `Paid` | `Cancelled` | Отмена после оплаты с refund |
| `Shipped` | `Delivered` | Admin deliver |
| `Delivered` | `Returned` | Admin return с refund |

`Cancelled` и `Returned` терминальны. Недопустимые переходы, включая
`Created → Shipped`, `Paid → Delivered`, `Shipped → Cancelled`,
`Delivered → Cancelled` и любые переходы из терминальных статусов, возвращают
`409 invalid_order_transition`.

См. `adr/ADR-004-order-state-machine.md`.

### 8.3 Конечная точка отмены

Обязательная конечная точка:

- `POST /api/orders/{id}/cancel`

Обязательный заголовок:

- `If-Match` с текущим `Order.RowVersion`.

Отдельный `Idempotency-Key` для отмены не используется.

Тело необязательно:

```json
{
  "items": [
    {
      "orderItemId": "order-item-id",
      "quantity": 1
    }
  ]
}
```

Правила:

- отсутствие тела означает полную отмену;
- `items` означает частичную отмену перечисленных количеств;
- пустой массив `items: []` не является полной отменой и отклоняется как ошибка
  валидации;
- `quantity` должна быть положительным целым числом и не превышать оставшееся
  количество позиции;
- неизвестный `orderItemId` отклоняется как ошибка валидации;
- отмена доступна только владельцу заказа.

### 8.4 Правила полной и частичной отмены

- `OrderItem.Quantity` — неизменяемый снимок и не уменьшается.
- Для каждой отмены создаётся `OrderItemCancellation`.
- `CancelledQuantity` вычисляется как сумма количеств в
  `OrderItemCancellation` и не хранится отдельным полем.
- Инвариант: `SUM(CancelledQuantity) <= OrderItem.Quantity`.
- `Order.TotalAmount` остаётся снимком исходного заказа.
- Полная отмена отменяет оставшиеся (не отменённые) количества и переводит
  заказ в `Cancelled` из `Created` или `Paid`.
- Частичная отмена не меняет статус заказа; «частично отменён» определяется
  наличием записей `OrderItemCancellation`.
- Отмена до оплаты возвращает отменяемое количество из `Reserved` в
  `Available`.
- Отмена после оплаты возвращает количество в `Available` и выполняет refund.
- Отмена не изменяет текущую корзину.
- Запас восстанавливается, даже если товар теперь неактивен.
- Снимки названия и цены позиций заказа не меняются.
- Повторная отмена уже отменённого заказа возвращает
  `409 order_already_cancelled`.
- Отмена `Shipped`, `Delivered` или `Returned` возвращает
  `409 invalid_order_transition`.
- Если refund невозможен, возвращается `409 refund_not_allowed`.

### 8.5 Атомарность и конкурентность отмены

Изменение статуса, записи `OrderItemCancellation`, возврат запаса и refund
должны происходить в одной транзакции.

Переход в `Cancelled` должен выполняться успешно, только если заказ всё ещё
находится в допустимом статусе и `If-Match` соответствует текущей версии.

Когда запросы отмены конкурируют:

- только один запрос может выполнить успешный переход;
- только выигравший запрос восстанавливает запас и делает refund;
- повторная отмена не должна восстанавливать запас или делать refund второй раз;
- повторная отмена возвращает `409 order_already_cancelled`.

Отсутствующий `If-Match` возвращает `428 precondition_required`. Устаревший
`If-Match` возвращает `412 order_version_conflict`. Успешная отмена изменяет
`Order.RowVersion` и возвращает новый `ETag`.

Неудача не должна оставлять заказ отменённым с восстановлением только части
запаса или с частично выполненным refund.

## 9. Admin API

### 9.1 Роль admin и доступ

Admin API использует `X-Test-User: admin` и доступен только в Development.

- В Production admin endpoints не регистрируются и возвращают `404 Not Found`.
- Запрос от `alice` или `bob` возвращает `403 Forbidden` с кодом `forbidden`.
- Неизвестный `X-Test-User` не аутентифицирует запрос.
- Реальная JWT/OAuth-аутентификация и управление ролями не вводятся.
- Admin UI не входит в MVP+.
- Admin API не позволяет произвольно менять статусы заказа.

См. `adr/ADR-009-admin-api-and-roles.md` и `architecture/api.md`, §3.6.

### 9.2 Деактивация товара

`POST /api/admin/products/{id}/deactivate` устанавливает `Product.IsActive =
false`.

Требования:

- операция идемпотентна;
- деактивация разрешена при наличии активных заказов;
- снимки названия и цены в существующих заказах не меняются;
- деактивированный товар нельзя добавить в корзину или оформить;
- существующие позиции корзины остаются видимыми как недоступные и могут быть
  удалены;
- публикуется событие `ProductDeactivated`.

### 9.3 Admin stock

`POST /api/admin/products/{id}/stock` устанавливает абсолютное значение
`Product.Available`.

Требования:

- `Available >= 0`;
- `Reserved` не изменяется;
- `available < 0` возвращает `400 validation_error`;
- операция атомарна и не теряет конкурентные изменения;
- используется optimistic concurrency по `Product.RowVersion`;
- при исчерпании ограниченного числа повторов возвращается
  `409 admin_stock_conflict`;
- публикуется событие `StockAdjusted`.

### 9.4 Ship

`POST /api/admin/orders/{id}/ship` выполняет `Paid → Shipped`.

- Если заказ не в `Paid`, возвращается `409 invalid_order_transition`.
- Публикуется событие `OrderShipped`.

### 9.5 Deliver

`POST /api/admin/orders/{id}/deliver` выполняет `Shipped → Delivered`.

- Если заказ не в `Shipped`, возвращается `409 invalid_order_transition`.
- Публикуется событие `OrderDelivered`.

### 9.6 Return

`POST /api/admin/orders/{id}/return` выполняет `Delivered → Returned`.

Требования:

- возвращается весь заказ; частичный возврат после доставки не поддерживается;
- refund выполняется по ADR-008;
- `Available` увеличивается на оставшиеся (не отменённые) количества заказа;
- refund, изменение запаса и переход статуса выполняются в одной транзакции;
- при ошибке refund вся операция откатывается;
- если заказ не в `Delivered`, возвращается `409 invalid_order_transition`;
- если refund невозможен, возвращается `409 refund_not_allowed`;
- публикуются события `OrderReturned` и `PaymentRefunded`.

## 10. Аудит

Аудит создаётся через доменные события после успешного commit и работает
at-most-once. См. `adr/ADR-007-domain-events.md`,
`adr/ADR-010-audit.md` и `architecture/events.md`.

Требования:

- `AuditLog` append-only: записи не обновляются и не удаляются.
- Аудит пишется в отдельной транзакции после commit бизнес-операции.
- При сбое audit handler запись аудита может потеряться; бизнес-операция не
  откатывается.
- Автоматический retry, outbox и брокеры сообщений не используются.
- Минимальный набор аудита: заказы, платежи и admin-изменения.
- Корзина не аудируется.
- `OrderCancelled` для частичной отмены содержит сведения об отменённых позициях
  и количествах.
- `Payload` не содержит секретов, паролей, платёжных данных или лишних
  персональных данных.
- API чтения или изменения аудита в MVP+ отсутствует.
- `AuditLog` не является источником истины для восстановления заказа, платежа
  или запаса.

Поля `AuditLog`, ограничения и триггер `TR_AuditLog_NoUpdateDelete` определены в
`architecture/data-model.md`, §4.12.

## 11. Обработка ошибок API

Ошибки API используют ASP.NET Core `ProblemDetails` со стабильным `code` и
полем `instance`.

Полный перечень кодов и HTTP-статусов определён в `architecture/api.md`, §4.1;
здесь он не дублируется.

Ключевые новые коды:

- `order_version_conflict` (`412`) — устаревший `If-Match` заказа;
- `precondition_required` (`428`) — отсутствует обязательный `If-Match`;
- `invalid_order_transition` (`409`) — недопустимый переход заказа;
- `order_already_cancelled` (`409`) — повторная отмена;
- `payment_not_found` (`404`) — платёж не найден или чужой;
- `payment_already_confirmed` (`409`) — платёж уже подтверждён с другим
  отпечатком;
- `payment_failed` (`409`) — mock-провайдер вернул `Failed`;
- `refund_not_allowed` (`409`) — refund невозможен;
- `admin_stock_conflict` (`409`) — конкурентное изменение admin stock;
- `forbidden` (`403`) — недостаточно прав, включая не-admin доступ к admin API;
- `idempotency_key_reused` (`409`) — ключ использован с другим запросом;
- `idempotency_in_progress` (`503`) — совпадающая попытка ещё выполняется;
- `checkout_retry` (`503`) — временная ошибка конкурентного изменения checkout.

Сопоставление HTTP-статусов:

| Условие | HTTP-статус |
|---|---:|
| Недопустимый запрос, заголовок или параметр | `400 Bad Request` |
| Отсутствующая или недопустимая аутентификация | `401 Unauthorized` |
| Недостаточно прав, включая не-admin доступ к admin API | `403 Forbidden` |
| Отсутствующий ресурс или чужой ресурс | `404 Not Found` |
| Недостаточный запас, конфликт бизнес-правила или идемпотентности | `409 Conflict` |
| Устаревший `If-Match` | `412 Precondition Failed` |
| Неподдерживаемый `Content-Type` | `415 Unsupported Media Type` |
| Отсутствует обязательный `If-Match` | `428 Precondition Required` |
| Временная ошибка идемпотентности, checkout или недоступность БД | `503 Service Unavailable` |
| Неожиданная ошибка сервера | `500 Internal Server Error` |

Ответ `503` является временным. Он не должен интерпретироваться как
окончательный сбой оформления заказа или платежа и не должен сохраняться как
окончательный бизнес-результат.

Ответы об ошибках не должны раскрывать трассировки стека или конфиденциальные
сведения о реализации.

## 12. Целостность данных и сохранение

Реализация должна соблюдать следующие требования:

- Адреса электронной почты пользователей уникальны.
- У пользователя не более одной корзины, и корзина создаётся при первом
  обращении при первом `GET /api/cart`.
- Позиции корзины не могут иметь неположительные количества.
- `Money` использует USD и `decimal(18,2)`; денежные значения неотрицательны.
- `Available >= 0` и `Reserved >= 0`.
- Резервирование, consume, отмена и возврат запаса атомарны.
- Позиции заказа сохраняют название товара и цену на момент покупки.
- `OrderItem.Quantity` — неизменяемый снимок; `CancelledQuantity` вычисляется.
- `SUM(OrderItemCancellation.Quantity) <= OrderItem.Quantity`.
- `Order.TotalAmount` не уменьшается при частичной отмене.
- `Order` использует `RowVersion` для `If-Match`.
- Статусы заказа соответствуют ADR-004; недопустимые переходы невозможны.
- У заказа не более одного `Payment`; `Payment.Amount` равен сумме заказа.
- `Payment.RefundedAmount <= Payment.Amount`;
  `Payment.RefundedAmount == SUM(Refund.Amount)`.
- `Payment.Status = Refunded` только при полном возврате.
- `PaymentAttempt` уникален по `(UserId, IdempotencyKey)`.
- `CheckoutAttempt` и `PaymentAttempt` не очищаются автоматически в MVP+.
- `AuditLog` append-only; триггер `TR_AuditLog_NoUpdateDelete` защищает от
  `UPDATE`/`DELETE`.
- События публикуются после commit; audit пишется в отдельной транзакции.
- Outbox не используется; потеря события или аудита при сбое handler'а
  допускается.
- Записи товаров, на которые ссылаются исторические заказы, не должны физически
  удаляться.
- Успешное оформление заказа делает ранее выданный `ETag` корзины
  недействительным.
- Состояние идемпотентности остаётся согласованным с результатом checkout,
  confirm или refund.

Подробная схема, индексы, внешние ключи, ограничения и триггеры указаны в
`architecture/data-model.md`. Доменные инварианты — в `DOMAIN.md`. Решения —
в ADR-003…010.

## 14. Критерии приёмки

MVP+ принимается, когда выполнены все применимые критерии ниже.

### Среда и аутентификация

- Решение успешно собирается.
- API запускается с корректной локальной конфигурацией.
- `GET /health` отвечает успешно, когда база данных доступна, и `503`, когда она
  недоступна.
- Миграции базы данных могут быть применены.
- Каталог отвечает без аутентификации.
- Тестовая аутентификация для разработки работает для Alice, Bob и admin.
- Неизвестные значения тестового пользователя не аутентифицируют.
- Схема тестовой аутентификации не зарегистрирована в Production.
- Admin endpoints доступны только в Development; в Production возвращают `404`.
- Alice и Bob получают `403 forbidden` на admin endpoints.
- Повторное начальное заполнение не создаёт дублирующихся пользователей.
- Реальная JWT/OAuth-аутентификация не требуется и не вводится.

### Каталог и корзина

- API возвращает только активные товары со стабильной пагинацией.
- `Price` передаётся числом, `Money` используется в Domain.
- `Available` и `Reserved` существуют; `Reserved` не отдаётся публично.
- Admin deactivate и stock работают по §9.
- У каждого пользователя изолированная корзина, создаваемая при первом
  `GET /api/cart`.
- Операции с корзиной обеспечивают положительные количества и наличие запаса.
- `CartItem.IsSelected` по умолчанию `true`.
- `PUT /api/cart/selection` изменяет только перечисленные позиции и требует
  `If-Match`.
- `GET /api/cart` возвращает `isSelected`, `totalAmount`, `selectedTotalAmount`.
- Изменения корзины, выбор и checkout требуют `If-Match`; отсутствующие значения
  возвращают `428`, устаревшие — `412`.
- Checkout использует только выбранные позиции; невыбранные остаются.
- Пустой выбор возвращает `409 cart_empty`.
- Неактивные товары нельзя купить заново; выбранный неактивный товар блокирует
  checkout.
- Неудачные операции с корзиной сохраняют существующее состояние.
- `ETag`, выданный до успешного checkout, больше не принимается.

### Оформление заказа и идемпотентность

- Допустимую корзину с выбранными позициями можно успешно оформить.
- Заказ создаётся в `Created`, `Payment` — в `Pending`; возвращается `paymentId`.
- Резервируются только выбранные позиции: `Available → Reserved`.
- Очищаются только выбранные позиции.
- Суммы заказа и снимки позиций корректны.
- Fingerprint checkout не включает `selection` явно.
- Неудачный checkout не оставляет заказ, платёж, резерв или изменения корзины.
- Повторный checkout с тем же ключом и запросом не создаёт дублирующий заказ.
- Ключ с другим запросом отклоняется с `409 idempotency_key_reused`.
- `checkout_retry` и `idempotency_in_progress` являются временными `503`.
- Восстановление `InProgress` выполняется по требованию без второго заказа.
- Пользователи видят только свои заказы.

### Платежи

- Confirm доступен только владельцу и требует `Idempotency-Key`.
- Confirm выполняет `Pending → Confirmed`, `Order → Paid` и consume `Reserved`
  за оставшееся (не отменённое) количество в одной транзакции.
- Повторный confirm с тем же fingerprint воспроизводит результат.
- `payment_already_confirmed`, `payment_failed` и `payment_not_found`
  возвращаются по контракту.
- `Failed → Pending → Confirmed` работает с тем же ключом.
- `Refunded` терминален.
- Ручной admin refund доступен только admin в Development.
- Ручной refund не изменяет заказ и запас.
- Ручной refund для `Pending`, `Failed` и `Refunded` возвращает
  `refund_not_allowed`.
- Полный refund переводит `Payment` в `Refunded`; частичный оставляет
  `Confirmed`.
- Несколько частичных refund поддерживаются.
- Refund больше остатка или после полного возврата возвращает
  `refund_not_allowed`.
- Автоматический refund при отмене после оплаты и возврате после доставки
  выполняется в одной транзакции с заказом и запасом.
- Ошибка refund откатывает всю операцию.
- Идемпотентность refund включает `amount` и `reason`.
- Bounded wait и восстановление `PaymentAttempt` работают.

### Заказы и отмена

- Заказ имеет шесть статусов и только разрешённые переходы.
- Полная отмена из `Created` и `Paid` работает.
- Частичная отмена не меняет статус и создаёт `OrderItemCancellation`.
- `OrderItem.Quantity` не уменьшается; `CancelledQuantity` вычисляется.
- `SUM(CancelledQuantity) <= OrderItem.Quantity`.
- Отмена до оплаты возвращает `Reserved → Available`.
- Отмена после оплаты возвращает `Available` и выполняет refund.
- Отмена не изменяет корзину.
- `If-Match` отмены: `428` при отсутствии, `412 order_version_conflict` при
  устаревшем значении.
- Повторная отмена возвращает `order_already_cancelled`.
- Отмена `Shipped`, `Delivered` или `Returned` возвращает
  `invalid_order_transition`.
- Одновременная отмена не возвращает запас и не делает refund дважды.
- Снимки названия и цены не меняются.

### Admin API

- Deactivate идемпотентен и не меняет исторические заказы.
- Admin stock устанавливает абсолютное `Available`, не меняет `Reserved` и
  возвращает `admin_stock_conflict` при исчерпании повторов.
- Отрицательный `Available` возвращает `400 validation_error`.
- Ship выполняет `Paid → Shipped`.
- Deliver выполняет `Shipped → Delivered`.
- Return выполняет `Delivered → Returned`, возвращает в `Available` оставшиеся
  количества и делает refund.
- Недопустимые статусы возвращают `invalid_order_transition`.
- Ошибка refund при return откатывает всю операцию.

### События и аудит

- События публикуются после успешного commit.
- При rollback события не публикуются.
- Сбой handler'а не откатывает бизнес-операцию.
- Цепочки событий отсутствуют.
- Аудит создаётся для заказов, платежей и admin-изменений.
- Корзина не аудируется.
- `OrderCancelled` для частичной отмены содержит сведения об отменённых
  позициях.
- `AuditLog` append-only; `UPDATE`/`DELETE` запрещены триггером.
- Потеря audit-записи при сбое handler'а допустима и не откатывает бизнес-
  операцию.
- API чтения аудита отсутствует.

### Ошибки, данные и качество

- Ошибки API следуют `ProblemDetails` и `architecture/api.md`, §4.1.
- `503` для checkout и payment является временным и не сохраняется как
  окончательный результат.
- `Money`, статусы, резервы, частичная отмена, payment idempotency и аудит
  соответствуют ADR-003…010 и `architecture/data-model.md`.
- Критические бизнес-правила покрыты автоматическими тестами.
- Интеграционные тесты используют выделенную тестовую базу данных SQL Server.
- Документация и реализация остаются согласованными.

определены во время реализации:

- Точное соглашение о URI `type` в `ProblemDetails`.
- Окончательный список индексов, выбранный по измеренным шаблонам запросов.
- Клиентский механизм хранения неиспользованного ключа идемпотентности.

Ранее блокировавшие решения зафиксированы в ADR, `architecture/api.md`,
`architecture/data-model.md` и `DECISIONS.md`; здесь они не повторяются.

Известные ограничения MVP+ и осознанные упрощения перечислены в
`DECISIONS.md`, §13. К ним относятся, в частности, mock-платежи, dev-only
`X-Test-User` и admin API, отсутствие outbox, TTL резервов, reconciliation,
реальной JWT/OAuth-аутентификации, admin UI и мультивалютности.

Агент реализации не должен придумывать поведение контракта, которое уже
определено в документах выше.
