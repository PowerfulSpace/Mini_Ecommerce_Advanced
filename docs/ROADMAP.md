# План разработки

## 1. Назначение

Этот документ определяет планируемую последовательность реализации для MVP
Mini E-commerce.

Разработка должна продвигаться постепенно. Каждый этап должен давать проверяемый
результат до начала следующего этапа.

Дорожная карта — это план разработки, а не замена функциональной спецификации,
документов архитектуры или утверждённых ADR.

Если реализация выявляет нерешённое требование или конфликт между документами,
остановите работу над затронутым поведением и запросите разъяснение.

## 2. Принципы разработки

- Завершите документацию и решите блокирующие вопросы проектирования до
  реализации зависимого поведения.
- Создавайте backend раньше фронтенда.
- Предпочитайте небольшие, независимо проверяемые изменения.
- Поддерживайте собираемость решения на протяжении всей разработки.
- Добавляйте тесты вместе с проверяемым ими поведением.
- Тестируйте поведение, специфичное для базы данных, на SQL Server.
- Не заменяйте требования к транзакциям или конкурентности более простыми
  допущениями о работе в памяти.
- Не реализуйте функции за пределами объёма.
- Обновляйте документацию при изменении утверждённого решения или контракта.
- M1–M14 — согласованный диапазон вех MVP+; включены M1–M8, M12 и M13;
  M9, M10, M11 и M14 — вне MVP+.

## 4. Этап 0 — Завершение документации и проектирования

### Цели

Завершите спецификации, необходимые для реализации backend без догадок о важном
поведении.

### Задачи

- Проверьте `PROJECT.md`, `SPEC.md`, `DOMAIN.md`, `DECISIONS.md` и `FRONTEND.md`.
- Убедитесь, что `architecture/architecture.md`, `architecture/data-model.md` и
  `architecture/api.md` отражают утверждённые решения без противоречий.
- Убедитесь, что `adr/ADR-001-cart-concurrency.md` и
  `adr/ADR-002-checkout-idempotency.md` соответствуют утверждённым решениям о
  версии корзины, ограниченном ожидании и восстановлении по требованию.
- Подтвердите, что DTO API, коды состояния, стабильные коды ошибок и расширения
  `ProblemDetails` задокументированы в `architecture/api.md`.
- Определите настройку и очистку базы данных для интеграционных тестов.
- Подтвердите структуру репозитория и процесс разработки.

### Критерии выхода

- Документы не содержат нерешённых противоречий.
- Для каждого критичного для реализации бизнес-правила согласовано поведение.
- Контракт API достаточно детален для реализации как backend, так и фронтенда.
- Для блокировки корзины, валидации `If-Match`, повторных попыток оформления
  заказа и заброшенных попыток идемпотентности определено поведение.
- Ни одно критичное для production решение не делегируется молча агенту-исполнителю.

Не начинайте зависимую реализацию, пока блокирующие вопросы остаются
нерешёнными.

## 5. Этап 1 — Основа решения и проектов

### Цели

Создайте собираемое решение .NET с согласованной структурой проектов.

### Задачи

- Создайте вложенный файл решения
  `src/Backend/PS.MiniEcommerce/PS.MiniEcommerce.slnx` в формате `.slnx`. Он не
  создаётся в корне репозитория.
- Создайте проекты backend в `src/Backend/PS.MiniEcommerce/`:
  - `PS.MiniEcommerce.Domain`
  - `PS.MiniEcommerce.Application`
  - `PS.MiniEcommerce.Infrastructure`
  - `PS.MiniEcommerce.API`
- Создайте тестовые проекты:
  - `tests/PS.MiniEcommerce.UnitTests`
  - `tests/PS.MiniEcommerce.IntegrationTests`
- Зарегистрируйте все шесть проектов в решении.
- Добавьте `global.json`, `Directory.Build.props` и `Directory.Packages.props` в
  корень репозитория. Централизованные версии пакетов управляются через
  `Directory.Packages.props`.
- Добавьте ссылки между проектами в соответствии с Clean Architecture. Проект
  `Common` не существует и не создаётся.
- Добавьте `NSubstitute` в оба тестовых проекта, а
  `Microsoft.AspNetCore.Mvc.Testing` — в проект интеграционных тестов.
- Добавляйте только те другие зависимости, которые требуются для текущего
  этапа; пакеты MediatR, FluentValidation и EF Core добавляются на своих этапах.
- Настройте ссылочные типы, допускающие значение null, и другие согласованные
  параметры компилятора. `TreatWarningsAsErrors` и анализаторы стиля кода
  остаются отключёнными до этапа 3.
- Удалите шаблонный код-заглушку из созданных проектов.
- Убедитесь, что решение собирается и тесты выполняются.

### Критерии выхода

- Все проекты существуют в согласованных расположениях с префиксом `PS.`.
- `dotnet sln list` показывает все шесть проектов: четыре проекта backend и два
  тестовых проекта.
- Ссылки между проектами соблюдают границы архитектуры, и ни одна ссылка не
  указывает на проект `Common`.
- `dotnet build` успешно завершается для решения.
- Оба тестовых проекта запускаются через `dotnet test`.
- Решение остаётся в формате `.slnx` в `src/Backend/PS.MiniEcommerce/`.
- Бизнес-поведение не было добавлено преждевременно.

## 9. Этап 5 — Корзина

### Цели

Реализуйте постоянные операции с корзиной, специфичные для пользователя, и
защиту от конкурентных операций.

### Задачи

- Реализуйте получение корзины текущего пользователя, включая создание
  при первом обращении.
- Обрабатывайте одновременные первые запросы корзины через ограничение
  уникальности базы данных.
- Реализуйте добавление товара в корзину.
- Увеличивайте количество при добавлении уже присутствующего товара.
- Реализуйте обновление количества и удаление позиции без тела запроса.
- Валидируйте положительные целочисленные количества.
- Валидируйте активность товара и запас в соответствии со спецификацией.
- Реализуйте явную блокировку корзины с использованием утверждённого механизма
  SQL Server.
- Возвращайте `ETag` корзины и требуйте `If-Match` при изменениях, возвращая
  `428`, когда он отсутствует, и `412`, когда он устарел.
- Убедитесь, что запросы и изменения корзины соблюдают принадлежность
  пользователю.
- Добавьте модульные тесты и интеграционные тесты с SQL Server.

### Критерии выхода

- У каждого пользователя независимая корзина, создаваемая при первом обращении и только один
  раз при одновременных первых запросах.
- Операции с корзиной подчиняются утверждённым правилам количества и запаса.
- Неактивные товары нельзя добавить или обновить для покупки.
- Неудачные изменения не оставляют частичного состояния.
- Конкурентные операции с корзиной следуют утверждённому поведению блокировки и
  `If-Match`.
- Интеграционные тесты проверяют фактическое поведение SQL Server.

## 10. Этап 6 — Оформление заказа и идемпотентность

### Цели

Реализуйте атомарное оформление заказа с корректной обработкой запаса и
безопасными повторными попытками.

### Задачи

- Требуйте `Idempotency-Key` и `If-Match` для `POST /api/orders`.
- Валидируйте формат ключа идемпотентности и отклоняйте недопустимые ключи до
  резервирования ключа.
- Реализуйте записи идемпотентности в области пользователя и утверждённую
  начальную транзакцию резервирования.
- Вычисляйте отпечаток запроса из целевого адреса запроса и переданного значения
  `If-Match`.
- Валидируйте, что корзина не пуста.
- Валидируйте активность товара и запас.
- Захватите блокировку корзины с использованием утверждённой стратегии
  блокировки.
- Списывайте запас с помощью атомарных условных обновлений и обрабатывайте
  строки товаров в стабильном порядке.
- Читайте снимки позиций заказа, пока строки товаров заблокированы.
- Создайте заказ и его снимки позиций и вычислите сумму заказа.
- Очистите позиции корзины, сохранив запись корзины, и обновите строку корзины
  так, чтобы её версия изменилась.
- Согласованно фиксируйте создание заказа, изменения запаса, очистку корзины,
  изменение версии строки корзины и завершённый результат идемпотентности.
- Сохраняйте окончательные сбои бизнес-правил в соответствии с утверждённой
  стратегией.
- Реализуйте ограниченное ожидание и временный ответ `503` для совпадающих
  попыток в состоянии выполнения.
- Реализуйте восстановление по требованию заброшенных попыток с истёкшим сроком
  резервирования и проверкой устойчивого состояния без фоновой службы.
- Добавьте модульные тесты и интеграционные тесты с SQL Server.

### Критерии выхода

- Успешное оформление заказа создаёт ровно один заказ на попытку.
- Запас списывается атомарно и не может стать отрицательным в результате
  оформления заказа.
- Любой сбой оформления заказа откатывает все бизнес-изменения.
- Неудачное оформление заказа сохраняет корзину.
- Успешное оформление заказа очищает позиции корзины, сохраняет корзину и
  делает недействительным ранее выданный `ETag` корзины.
- Устаревший `ETag` не может изменить корзину после успешного оформления заказа.
- Повторение запроса с тем же ключом и тем же значением `If-Match` возвращает
  сохранённый результат.
- Повторное использование ключа с другим запросом приводит к утверждённому
  конфликту.
- Одновременные запросы с тем же ключом не выполняют оформление заказа дважды.
- Совпадающая попытка в состоянии выполнения ожидает, а затем возвращает `503`,
  и последующая повторная попытка с тем же ключом завершается успешно.
- Заброшенные попытки `InProgress` восстанавливаются по требованию после
  истечения срока резервирования без создания второго заказа.
- Неопределённые результаты обрабатываются без слепого создания второго заказа.
- Тесты покрывают гонки по запасу, откат транзакции, ограниченное ожидание и
  восстановление идемпотентности.

## 11. Этап 7 — История заказов и отмена

### Цели

Реализуйте получение заказов и безопасную отмену.

### Задачи

- Реализуйте историю заказов текущего пользователя с разбиением на страницы и
  стабильным порядком.
- Реализуйте сведения о заказе с использованием сохранённых снимков позиций
  заказа.
- Обеспечьте принадлежность заказа.
- Реализуйте отмену для подходящих заказов по `POST /api/orders/{id}/cancel`.
- Изменяйте статус заказа и восстанавливайте запас в одной транзакции с помощью
  условного обновления статуса.
- Восстанавливайте точные количества, записанные в заказе.
- Обрабатывайте одновременные попытки отмены.
- Определите и протестируйте поведение, когда заказ уже отменён.
- Добавьте модульные тесты и интеграционные тесты с SQL Server.

### Критерии выхода

- Пользователи могут получать только свои заказы.
- Исторические названия и цены товаров берутся из снимков заказа.
- Отменять можно только подходящие заказы.
- Отмена восстанавливает запас ровно один раз.
- Одновременные попытки отмены не могут восстановить запас более одного раза.
- Повторная отмена возвращает утверждённый ответ с конфликтом.
- Отмена не изменяет текущую корзину.

## 12. Этап 8 — Верификация backend

### Задачи

### 16.1 Этап 12 — Money VO (M1)

**Зависимости:** ADR-003.

#### Цели

Ввести `Money` как единственный денежный value object в Domain и исключить
использование «сырого» `decimal` для денежных значений, не меняя JSON-контракт
API и точность SQL.

#### Задачи

- Реализовать неизменяемый `Money` с `Amount` (`decimal`) и `Currency` (`USD`)
  и контролируемой фабрикой.
- Обеспечить инварианты: `Amount >= 0`, только `USD`, диапазон
  `decimal(18,2)`, округление `MidpointRounding.AwayFromZero`.
- Реализовать сложение, вычитание и умножение на целое количество с проверкой
  валюты и переполнения.
- Перевести `Product.Price`, стоимости строк и итоги корзины, `Order.TotalAmount`,
  `OrderItem.UnitPrice` и `Payment.Amount` на `Money`.
- Настроить EF Core value converter `Money` ↔ `decimal(18,2)` в Infrastructure;
  `Currency` не персистить.
- Отдавать в DTO и API `Money.Amount` как число, не добавляя `currency` в JSON.
- Добавить модульные тесты и round-trip тест через EF Core.

#### Критерии выхода

- В Domain нет денежных полей типа `decimal` вне `Money`.
- Неотрицательность, валюта и переполнение проверяются в Domain.
- JSON-контракт API не изменился: денежные значения передаются числом.
- Точность `decimal(18,2)` сохраняется в SQL Server.

#### Тесты

- Округление `AwayFromZero`; отрицательные значения; несовпадение валют;
  переполнение `decimal(18,2)`.
- Сложение, вычитание и умножение на целое количество.
- Round-trip `Money` через EF Core и сохранение `decimal(18,2)`.

#### Документация/ADR

### 16.8 Этап 19 — Платежи и идемпотентность платежей (M7+M13)

**Зависимости:** этап 18; ADR-004, ADR-005, ADR-008.

#### Цели

Добавить mock-платежи, confirm и refund с идемпотентностью и автоматическим
refund при отмене/возврате.

#### Задачи

- Добавить `Payment` со статусами `Pending`, `Confirmed`, `Failed`, `Refunded`,
  таблицу `Refund` и nullable `Order.PaymentId`.
- Создавать `Payment` в `Pending` в транзакции checkout и возвращать
  `paymentId` в `201 Created`.
- Реализовать `IPaymentProvider` и mock-реализацию в Infrastructure.
- Реализовать `POST /api/payments/{id}/confirm` только для владельца и с
  `Idempotency-Key`.
- Атомарно выполнять confirm: `Payment → Confirmed`, consume `Reserved`,
  `Order → Paid`, завершение `PaymentAttempt`.
- Реализовать `POST /api/payments/{id}/refund` для admin в Development с
  `Idempotency-Key` и несколькими частичными refund.
- Реализовать `PaymentAttempt` с fingerprint, lease, bounded wait и
  восстановлением по требованию.
- Выполнять автоматический refund при `Paid → Cancelled` и
  `Delivered → Returned` в одной транзакции.
- Добавить тесты идемпотентности, retry `Failed`, частичных refund и отката.

#### Критерии выхода

- Повторный confirm с тем же ключом не создаёт второй платёж.
- Повторный refund идемпотентен; refund не превышает остаток; `Refunded` только
  при полном возврате.
- Повторное использование ключа с другим fingerprint возвращает
  `409 idempotency_key_reused`.
- Confirm переводит заказ в `Paid`; refund при отмене/возврате атомарен с
  заказом и запасом.
- Retry `Failed → Pending → Confirmed` работает по ADR-008.

#### Тесты

- Создание платежа при checkout; успешный confirm и переход в `Paid`.
- Повторный confirm, `payment_already_confirmed`, `payment_failed` и retry
  `Failed`.
- Идемпотентность confirm/refund и `idempotency_key_reused`.
- Несколько частичных refund, `Refunded` только при полном возврате, запрет
  сверх остатка.
- Refund при отмене/возврате и откат при ошибке; bounded wait и lease.

#### Документация/ADR

ADR-008; `architecture/payments.md`; `architecture/api.md` §3.5 и §6.2;
`architecture/data-model.md` §4.8–4.10.

## 17. Определение готовности

Функция или этап считаются завершёнными только когда:

- Его согласованные требования реализованы.
- Код соблюдает границы архитектуры.
- Соответствующие автоматические тесты добавлены и проходят.
- Поведение, специфичное для SQL Server, проверено, где это применимо.
- Обработка ошибок следует контракту API.
- Ни один нерешённый критический вопрос проектирования не обойдён молча.
- Соответствующая документация обновлена.
- Решение остаётся собираемым.
- Для этапов 12–19 выполнены критерии выхода соответствующего этапа.
- Проверены инварианты `Available`/`Reserved`, частичный checkout/отмена и
  идемпотентность платежей.
- События публикуются после commit; аудит работает at-most-once.
- Admin endpoints недоступны вне Development и защищены ролью admin.

Успешная сборка сама по себе не доказывает, что требования к транзакциям,
конкурентности или идемпотентности выполнены.

## 18. Управление изменениями

Дорожная карта может быть переупорядочена или уточнена, когда реализация даёт
новую информацию.

Однако:

- Не пропускайте зависимость без явной причины.
- Не начинайте интеграцию фронтенда с нестабильным или придуманным контрактом
  API.
- Не ослабляйте критерии приёмки только для того, чтобы быстрее завершить этап.
- Фиксируйте значительные утверждённые изменения в `DECISIONS.md` и
  соответствующих ADR.
- Если новое требование меняет объём MVP+, получите одобрение до реализации.
