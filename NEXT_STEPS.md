# NEXT_STEPS — за границей MVP+

## 1. Статус

MVP (этапы 0–11) завершён. MVP+ (M1–M8, M12, M13; этапы 12–19) реализован; код
соответствует MVP+. M9, M10, M11, M14 — вне объёма.

Этот файл не описывает текущий MVP+ и не является списком задач. Он фиксирует,
что осталось за его границей и какие направления имеют смысл в следующем
проекте.

Связанные документы: `RATIONALE.md`, `docs/ROADMAP.md`, `docs/DECISIONS.md` §13.

## 2. Что не входит в MVP+ (осознанно)

| Область | Что осталось | Почему |
|---|---|---|
| Auth | JWT/OAuth, refresh-токены, production auth | Не про e-commerce; отдельный домен |
| Платежи | Stripe, вебхуки с подписью, retry и порядок доставки | Учебная модель; mock достаточно |
| Reconciliation | Сценарий «платёж прошёл, заказ не обновился» | Вне MVP+; требует надёжной доставки и сверки |
| Outbox | Гарантированная доставка событий | At-most-once достаточно для аудита |
| TTL резервов | Резерв с истечением, фоновый cleanup | Резерв создаётся в checkout; «зависших» нет |
| Мультивалютность | Валюты кроме USD | Отдельный домен; влияет на цены, Money и платежи |
| Уведомления | Email/push на события | Техника интеграции, не доменная концепция |
| Промо/налоги/скидки | Правила, купоны, расчёт налогов | «Правила на правилах», мало нового для ядра |
| Admin UI | Интерфейс администратора | Backend-only достаточно |
| Granular roles | Роли сверх customer/admin | Не про магазин; связаны с реальным auth |

Admin ship/deliver/return, частичный refund и аудит уже входят в MVP+
(ADR-009, ADR-008, ADR-010) и не относятся к «осталось».

## 3. Что можно добавить (проект 3, «приближенный к хорошему проду»)

| Область | Что | Ценность | Сложность |
|---|---|---|---|
| Stripe + вебхуки | Реальный провайдер, подпись, retry, порядок | Высокая: ближе всего к проду | Высокая |
| Outbox | Таблица исходящих событий и dispatcher | Высокая: гарантированная доставка | Средняя–высокая |
| Reconciliation | Сверка платежей и заказов, устранение расхождений | Высокая после outbox | Высокая |
| TTL резервов | Истечение резервов и cleanup | Средняя: реалистичнее запасы | Средняя |
| Real auth | JWT/OAuth, refresh, роли | Средняя: отдельный домен | Высокая |
| Уведомления | Email/push на доменные события | Средняя: полезно, но технически | Средняя |
| Мультивалютность | Несколько валют, курсы, округление | Средняя: отдельный домен | Высокая |
| Admin UI | UI для существующего admin API | Низкая для ядра, удобство | Средняя |
| Промо/налоги | Скидки, купоны, налоги | Низкая для ядра | Высокая |

Порядок отражает ценность на единицу работы, а не обязательный план.

## 4. Что не брать (и почему)

- **Микросервисы** — не для этого проекта; модульного монолита достаточно.
- **Event sourcing** — не для этого проекта; усложняет модель без учебной выгоды здесь.
- **CQRS с отдельными БД** — не для этого проекта; преждевременная инфраструктура.
- **Kubernetes / cloud** — не для этого проекта; не проверяет бизнес-инварианты.
- **Промо/налоги** — «правила на правилах»: много работы, мало нового, если
  не является специальной целью.

## 5. Принципы (без фанатизма)

- «Приближенный к хорошему проду» ≠ «production-grade».
- Каждая новая фича — ADR + обновление `docs/ROADMAP.md`.
- Не тащить инфраструктуру без конкретной потребности.
- Тесты — на инварианты и границы, а не на всё подряд.
