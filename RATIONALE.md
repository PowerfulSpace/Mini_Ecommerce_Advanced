# Обоснование объёма и упрощений

## 1. Статус проекта

**MVP+ (M1–M14), учебный / reference implementation.** Целевой объём MVP+:
M1–M8, M12, M13. Текущий статус: MVP+ в работе; документация завершена; код
реализуется по этапам 12–19 `docs/ROADMAP.md`; текущий код соответствует MVP.
M9, M10, M11 и M14 сознательно вынесены за пределы объёма.

Проект **не является production-системой**. Его цель — продемонстрировать
инженерные концепции backend-разработки на .NET и SQL Server, а не предоставить
готовый к эксплуатации интернет-магазин.

Связанные документы: `README.md`, `docs/DECISIONS.md`, `NEXT_STEPS.md`.

## 2. Почему проект именно такой

Цель проекта — учебная: освоить транзакции, конкурентность, идемпотентность,
явную state machine, доменные события, платежи и аудит на реалистичном, но
ограниченном сценарии интернет-магазина.

Границы выбраны осознанно. Проект не пытается воспроизвести production-grade
аутентификацию, платёжную инфраструктуру, гарантированную доставку событий или
административную панель. Вместо этого он концентрируется на корректности
бизнес-инвариантов и поведения базы данных: резервах `Available`/`Reserved`,
атомарных операциях, защите от повторных запросов и согласованных переходах
статусов.

Такой подход позволяет сохранить небольшой и проверяемый код, не подменяя
требования к транзакциям и конкурентности упрощениями «в памяти».

## 3. Что упрощено и почему

| Область | Упрощение | Почему | Где зафиксировано |
|---|---|---|---|
| Auth | `X-Test-User` (+ `admin`) вместо JWT/OAuth | Не про e-commerce; real JWT — отдельный домен | `DECISIONS.md` §13, ADR-009 |
| Платежи | Mock (`IPaymentProvider`) + `POST /api/payments/{id}/confirm` | Учебная модель, не интеграция с провайдером | ADR-008, `architecture/payments.md` |
| Вебхуки | Симуляция confirm-endpoint'ом | Не тащить подпись/retry/порядок | ADR-008, `architecture/payments.md` |
| Reconciliation | Нет | Вне MVP+, нет сценария «платёж прошёл, заказ не обновился» | `DECISIONS.md` §13 |
| Резервы | Без TTL/cleanup | Резерв внутри checkout, не «висит» | ADR-005 |
| События | `INotification`, без outbox | At-most-once для аудита; бизнес-операция не откатывается | ADR-007, `architecture/events.md` |
| Аудит | At-most-once (потеря при сбое handler'а) | Приемлемо для аудита; outbox — вне MVP+ | ADR-010 |
| Admin API | Только deactivate, stock, ship, deliver, return; dev-only | Не CRUD, не admin UI; роль через `X-Test-User` | ADR-009 |
| Мультивалютность | Только USD | Отдельный домен, не сейчас | ADR-003 |
| Уведомления | Нет | Техника, не концепция | `DECISIONS.md` §13 |
| Промо/налоги | Нет | «Правила на правилах», мало нового | `DECISIONS.md` §13 |

## 4. Границы

**Что гарантируется:**

- транзакционное оформление заказа, отмена и возврат запаса;
- идемпотентность checkout, confirm и refund;
- инварианты резервов `Available >= 0` и `Reserved >= 0`;
- явная state machine из шести статусов с запретом недопустимых переходов;
- публикация доменных событий после commit;
- аудит заказов, платежей и admin-изменений в режиме at-most-once;
- изоляция пользовательских данных и принадлежность корзины/заказа.

**Что не гарантируется:**

- реальная аутентификация и авторизация (JWT/OAuth);
- реальные платежи, Stripe, вебхуки и reconciliation;
- outbox и гарантированная доставка событий;
- TTL, cleanup и фоновое освобождение резервов;
- production-grade admin API и admin UI;
- мультивалютность, уведомления, промо и налоги.

**Это не скрытый дефект, а осознанная граница учебного проекта.**
